## 1. Что было и что изменилось

Перед доработкой был выполнен аудит подсистемы. Ниже — состояние «как было» и «как стало»;
формулировки «как было» проверялись по коду и рантайму, а не по документации.

| Вопрос | Было | Стало |
|--------|------|-------|
| Какая модель интегрирована | `gemma-3-12b-it-Q4_K_M.gguf` (Gemma 3 12B Instruct, arch `gemma3`, Q4_K_M, окно 4096 из 131072, CPU) — закреплена в `docker-compose.override.yml` | Без изменений; подсистема остаётся модель-агностичной |
| Какой RAG активен | Припоминание по скорингу из «резервного мозга» + глоссарий ISO 25010 + история периодов. Описание было рассыпано по коду | Матрица `pipeline.py` — единый источник описания, из него же питаются API и документация |
| Непрерывное дообучение | Отсутствует: веса в рантайме не меняются, уровень C — оффлайн | Тот же факт, но теперь **проверяется тестом** (`test_no_continuous_finetuning_in_runtime`), а не декларируется |
| «5 почему» | Механизм присутствовал неявно: промпт просил «последовательно спрашивать почему», глубина не фиксировалась и не проверялась | Явная лестница `ПОЧЕМУ-N`, разбор ступеней, глубина в трассе, глубина зависит от персоны |
| 14 принципов управления | Не применялись. Более того, код-ревью 2026-07-06 §D-1 зафиксировал удаление терминологии школы, а тест `test_no_methodology_jargon_in_user_facing_output` её запрещает | Применяются **по сути** как чек-лист резюме; названия школы в вывод по-прежнему не попадают — оба инварианта совместимы (см. §7) |
| Ролевое поведение | Один системный промпт на всех адресатов | Пять персон, выводятся из роли RBAC (см. §3) |
| Оценка качества самой LLM | Отсутствовала | Самооценка по всем 31 подхарактеристике ISO/IEC 25010 (см. §8) |

> **Замечание по п. «14 принципов».** Прямое требование «применять 14 принципов Toyota Way»
> конфликтует с ранее принятым и закреплённым тестом решением не выносить терминологию
> управленческих школ в промпты и пользовательский вывод. Конфликт разрешён в пользу
> **содержания без терминологии**: принципы реализованы как проверочные требования к резюме
> в нейтральных формулировках, происхождение зафиксировано в заголовке `principles.py`.
> Если заказчик потребует именно терминологию — это отдельное решение, оно потребует отмены
> §D-1 код-ревью и правки охраняющего теста.

## 2. Матрица конвейера RAG и обучения

Модуль `backend/app/modules/llm/pipeline.py`. Отвечает на три вопроса, которые раньше требовали
чтения кода: какой RAG, дообучается ли модель, откуда берётся контекст.

### 2.1. Уровни обучения

| Уровень | Название | Меняет веса | В рантайме | Смысл |
|---------|----------|-------------|------------|-------|
| A | Промпт-инжиниринг | нет | да | Знания в промптах, глоссарии, чек-листах |
| B | Заземление и самообучение контекстом (RAG) | нет | да | Контекст подбирается из накопленных данных на каждый запрос |
| C | Дообучение весов (LoRA/QLoRA) | да | **нет** | Оффлайн-процедура, из приложения не запускается |

**Инвариант:** ни один рантайм-уровень не меняет веса. Это и означает отсутствие непрерывного
дообучения — свойство проверяется тестом, а не обещанием.

### 2.2. Источники контекста

| Код | Источник | Механизм | Уровень | Состояние |
|-----|----------|----------|---------|-----------|
| `system_prompt` | Системный промпт персоны | Сборка из общих блоков по роли пользователя | A | активен |
| `glossary` | Глоссарий ISO 25010 | Лексическое сопоставление названий характеристик | A | активен |
| `principles` | Чек-лист управленческих принципов | Подмешивание требований + пост-проверка | A | активен |
| `contour_data` | Суждения, риски, меры, метрики | Выборка из БД по периоду и характеристикам | B | активен |
| `history` | История прошлых периодов ИС | Выборка по `system_id` | B | активен |
| `brain_memory` | Память рассуждений | **Припоминание по скорингу** (см. ниже) | B | активен |
| `human_feedback` | Оценки эксперта | Вердикт по отпечатку заключения | B | активен |
| `rules_gate` | Вердикт движка правил | Пороговые правила на метриках | A | активен |
| `decision_matrices` | Матрицы решений | Табличный поиск по ключам | A | активен |
| `sft_corpus` | Обучающий корпус | Экспорт в JSONL | C | по запросу |
| `lora_finetune` | Дообучение и сборка GGUF | Оффлайн на GPU | C | оффлайн |

**Механизм RAG (`brain_memory`)** — лексико-эвристическое припоминание, не векторное:
совпадение ИС `+3`, каждое пересечение характеристик `+2`, лексическое совпадение `+1`,
принятое экспертом `+2`, отклонённое экспертом исключается. Топ-3 подмешивается как история.
Память живёт в файлах вне весов (`models/llm_brain/memory.jsonl`) — поэтому смена GGUF-модели
не обнуляет накопленное.

## 3. Ролевые персоны

Модуль `backend/app/modules/llm/personas.py`.

### 3.1. Принцип сборки

Промпт персоны **не пишется с нуля**, а собирается:

```
BASE_IDENTITY  +  persona.role_block  +  BASE_HONESTY  +  persona.format_block
   (кто)          (приоритеты роли)      (правила        (формат под адресата)
                                          честности)
```

`BASE_HONESTY` — единственное место, где заданы правила против выдумывания фактов. Все персоны
наследуют его физически, поэтому ослабить правила в одной роли, не тронув остальные,
невозможно. Это и есть требуемая ТЗ синхронизация ролевых контекстов.

### 3.2. Каталог

| Персона | Роли RBAC | Линзы | Глубина «почему» | Бюджет | Чек-лист принципов |
|---------|-----------|-------|------------------|--------|--------------------|
| `TOP_MANAGER` | CEO, CTO | CIO, RISK, QUALITY | 3 | 260 | **да** |
| `QUALITY_MANAGER` | QUALITY_MANAGER, ADMIN, SUPER_ADMIN | QUALITY, CIO, RISK, SECURITY | 5 | 380 | нет |
| `RISK_MANAGER` | RISK_MANAGER | RISK, SECURITY, CIO | 5 | 380 | нет |
| `ANALYST` | TEST_ANALYST | QUALITY, CIO, SECURITY | 5 | 340 | нет |
| `AUDITOR` | AUDITOR | QUALITY, RISK, SECURITY | 5 | 340 | нет |

Персона по умолчанию — `QUALITY_MANAGER` (самый предметный нейтральный разбор): применяется
для демо-доступа и любой незнакомой роли.

Синхронность с каталогом ролей (`User.ALL_ROLES`) стережёт тест: домен `llm` намеренно не
импортирует `iam`, поэтому связь проверяется, а не создаётся зависимостью.

### 3.3. Как персона доходит до конвейера

`роль в JWT → personas.resolve() → Persona → run_reasoning(persona=…)`.
Точки внедрения: `GET /assessments/{id}/judgment-conclusion`, `POST /reports/measures-analytics`.
Кэш заключений включает код персоны — заключения разных адресатов не склеиваются.

## 4. Лестница «почему»

Этап Э2. Промпт требует задавать «почему?» к предыдущему ответу до `persona.why_depth` раз,
каждую ступень отдельной строкой `ПОЧЕМУ-N: …`, и остановиться честной строкой, если данных
для следующей ступени нет.

Разбор (`parse_why_chain`) устроен так, чтобы глубину нельзя было «накрутить»:

- ступень-заглушка «данных для следующего «почему» нет» **в глубину не засчитывается**;
- разрыв нумерации обрывает лестницу — перепутанный порядок не превращается в глубину;
- терпимость к формату мелких моделей (markdown, тире вместо двоеточия, «ПОЧЕМУ 3»);
- если ступени не распознались, содержательный ответ модели сохраняется как есть.

Глубина попадает в трассу (`why_depth`), в саморефлексию Э6 и в память «мозга».

## 5. Уточняющие вопросы

Этап Э2.5 — итеративное доуточнение контекста.

**Ключевое проектное решение: спрашивать про то, что ЕСТЬ, а не про то, чего нет.**
Вопрос об отсутствующем источнике бессмыслен — блок фактов Э0 и так печатает «данные
отсутствуют», ответ предопределён, а проход по CPU потрачен. Ценность даёт вопрос о связях
внутри переданных данных, которые в них заложены, но не выписаны:

| Предусловие | Вопрос |
|-------------|--------|
| есть карточки мер | Закрывают ли меры выявленную первопричину и что остаётся не закрытым? |
| есть риски | Какие риски подтверждаются суждениями, а какие — нет? |
| есть история | Что изменилось к прошлым периодам? |
| покрытие < 70 % | Какие подхарактеристики не измерены и как это ограничивает вывод? |
| ≥ 2 суждений | Есть ли среди суждений противоречащие друг другу? |

Вопросы формируются детерминированно (не моделью) — перечень воспроизводим и проверяем.
Не более 3 за прогон. Ответ «данные отсутствуют» фиксируется как неразрешённый пробел.
Проход не выполняется, если применимых вопросов нет.

## 6. Матрицы принятия решений

Модуль `backend/app/modules/llm/decisions.py`. Инвариант тот же, что у `gate.py`:
**решение принимает таблица, LLM его объясняет.**

### 6.1. Триаж: серьёзность × критичность ИС

| Серьёзность \ Критичность | BUSINESS OPERATIONAL | BUSINESS CRITICAL | MISSION CRITICAL |
|---|---|---|---|
| **none** | наблюдение, 90 дн. | наблюдение, 60 дн. | наблюдение, 30 дн. |
| **medium** | владелец процесса, 45 дн. | владелец процесса + владелец риска, 30 дн. | правление (информирование), 20 дн. |
| **high** | владелец процесса + владелец риска, 30 дн. | правление (решение), 14 дн. | правление (приоритетно), 7 дн. |

Проверяется монотонность: рост серьёзности или критичности никогда не смягчает уровень
решения и не удлиняет срок. Неизвестная критичность трактуется как **самый мягкий** класс —
поднимать вопрос в правление на основании отсутствия данных нельзя; отсутствие при этом
попадает в пробелы данных.

### 6.2. Доверие к выводу: уверенность × доля откатов

Определяет, можно ли опираться на вывод и допустим ли он как основание решения правления.
Низкая уверенность не допускается на уровень правления ни при какой доле откатов. Прогон,
где почти все этапы детерминированы, трактуется как сводка фактов, а не аналитический вывод.

### 6.3. Достаточность данных

Покрытие измерений (порог 70 %, общий с `gate.COVERAGE_THRESHOLD`) и наличие источников →
уровень «достаточно / частично / недостаточно» + перечень пробелов.

## 7. Управленческие принципы резюме

Модуль `backend/app/modules/llm/principles.py`. 14 принципов, происхождение —
управленческая система производственного менеджмента Toyota (свод Дж. Лайкера),
формулировки переведены в нейтральную аналитическую лексику (см. замечание в §1).

Два режима:

- **в промпт** — 8 принципов, помеченных `in_prompt`, добавляются как обязательные требования
  к управленческому резюме для персоны `TOP_MANAGER`: долгосрочная цель, вывод проблемы на
  поверхность, устранение в источнике, закрепление процедурой, видимость состояния, решение
  уровня руководителя, опора на первичные данные, срок внедрения, возврат к результату;
- **пост-проверка** — `audit()` детерминированно отмечает, по каким принципам в готовом
  резюме есть признаки отражения. Формулировка в отчёте намеренно осторожная: это
  **признак присутствия темы в тексте**, а не оценка соблюдения принципа в работе.

## 8. Самооценка по ISO/IEC 25010

Модуль `backend/app/modules/llm/selfcheck.py`. Система оценивает прикладные ИС по модели
ISO 25010 — здесь она оценивает по той же модели саму себя: 8 характеристик,
31 подхарактеристика, батарея из 31 пробы.

### 8.1. Принцип честности измерения

Тот же, что во всём контуре:

- подхарактеристика, **неприменимая** к LLM-компоненту (эстетика интерфейса, accessibility),
  помечается «невозможно измерить», а не получает выдуманный балл;
- проба, требующая инференса, при недоступной модели или в режиме `static` тоже даёт
  «невозможно измерить»;
- интегральный балл считается **только по измеренным** пробам, покрытие показывается отдельно.

### 8.2. Режимы

| Режим | Что делает | Время (замерено) | Как запускается |
|-------|-----------|------------------|-----------------|
| `static` | Только интроспективные пробы | < 1 с (без учёта загрузки модели) | синхронно из UI/API |
| `full` | Плюс сценарии инференса S1–S3 | 120 с на 0.5B; **> 50 мин** на 12B (CPU) | фоновая задача Celery |

Замеры сделаны на стенде разработки (CPU, 8 потоков, 7.7 ГиБ памяти на контейнер). Разброс
на порядок объясняется не только размером модели: 12B в Q4_K_M занимает почти всю доступную
контейнеру память, инференс упирается в подкачку и падает до ~100 % CPU вместо ~800 %.
Практический вывод: на текущем железе полный прогон для 12B — исключительно ночная операция;
для интерактивной проверки конфигурации предназначен режим `static`.

Покрытие в полном режиме — 29 измеренных проб из 31 (93.5 %); неизмеримыми честно остаются
только две подхарактеристики интерфейса, неприменимые к LLM-компоненту.

Сценарии: **S1** — штатный разбор полным конвейером; **S2** — провокация на выдуманные числа
(во входе нет ни одного процента, любой процент в ответе — выдуманный); **S3** — пустой вход,
ожидается честная констатация отсутствия данных; **S_det** — прогон без модели, проверяет
полноту детерминированного отката (выполняется всегда, инференса не требует).

### 8.3. Расписание

Еженедельно, понедельник 03:30 (`SCHEDULE_TIMEZONE`, по умолчанию Europe/Moscow). Планировщик
встроен в воркер (`celery worker --beat`) — отдельный контейнер не поднимается, воркер в стенде
один. **При масштабировании на несколько воркеров beat обязан стать отдельным процессом**,
иначе задача сработает столько раз, сколько воркеров запущено.

Ночной запуск выбран не по привычке: `llama.cpp` сериализует инференс, поэтому полный прогон
в рабочие часы блокировал бы генерацию заключений для пользователей.

**Ограничение по памяти (проверено на стенде).** Полный прогон обязан идти В ВОРКЕРЕ. Попытка
запустить его отдельным процессом внутри контейнера `backend` (`docker compose exec backend
python -c "…selfcheck.run(mode='full')"`) приводит к загрузке ВТОРОЙ копии модели в тот же
контейнер и завершается OOM (exit 137): на стенде 12B-модель в Q4_K_M занимает ~6.6 ГиБ, а
лимит контейнера — 6.6 ГиБ. Именно поэтому эндпоинт ручного запуска ставит задачу в очередь,
а не выполняет её сам. Для ручной проверки без воркера используйте режим `static`.

### 8.4. Хранение

`models/llm_brain/selfcheck/` — история (до 52 файлов, год еженедельных прогонов) и
`latest.json`. Каталог «мозга» выбран потому, что он writable и переживает смену модели,
в отличие от read-only каталога моделей.

## 9. API и права доступа

| Метод | Эндпоинт | Право | Назначение |
|-------|----------|-------|------------|
| GET | `/api/v1/reports/llm-pipeline` | аутентификация | Матрица конвейера, персоны, матрицы решений |
| GET | `/api/v1/reports/llm-quality` | `view.admin.llm_quality` | Последний отчёт + история |

Права `view.admin.llm_quality` и `llm.quality.run` внесены в
`PROTECTED_SUPERADMIN_PERMISSIONS`, из чего следует:

- они не входят в `ADMIN_PERMISSIONS` — даже ADMIN получает 403;
- `set_role_permissions` их отфильтровывает — суперадминистратор не может выдать их другой
  роли через матрицу. Это **обеспеченная** исключительность, а не настройка по умолчанию.

Дашборд: `/admin/llm-quality`, пункт меню «Качество LLM» в разделе «Администрирование»
(`frontend/src/pages/admin/LlmQualityPage.tsx`).
