## 0. Краткое резюме

Профилирование показало, что **классической утечки памяти в коде приложения нет**.
Наблюдаемые 6.2 ГиБ RSS бэкенда — это **резидентные веса LLM-модели Gemma-3-12B-Q4_K_M
(7.3 ГБ файл), загруженной внутрь процесса FastAPI**. Базовый RSS процесса без модели — 137 МиБ.

Реальные дефекты, подтверждённые замерами:

| № | Дефект | Наблюдаемое следствие |
|---|--------|----------------------|
| Д-1 | Синхронный многопроходный LLM-инференс в HTTP-запросе | 1 запрос > 900 с, `HTTP=000`, API недоступен |
| Д-2 | Инференс не отменяем при отключении клиента | CPU 764 % продолжает гореть «в никуда» |
| Д-3 | Отсутствуют лимиты ресурсов контейнеров | Бэкенд занимает 80 % RAM хоста без ограничения |
| Д-4 | LLM грузится и в Celery-воркерах (`--concurrency=2`) | Потенциально 3 копии × 6.2 ГиБ = 18.6 ГиБ при 8.27 ГБ RAM → OOM |
| Д-5 | Неограниченный кэш `_cache: dict[int, str]` | Монотонный рост RSS, эвикции нет |
| Д-6 | `uvicorn --reload` при резидентной модели 7 ГБ | Правка любого `.py` → перезагрузка модели; зависание shutdown |
| Д-7 | `brain.stats()` читает 3 JSONL целиком на каждый вызов | Дисковый I/O на каждый `GET /reports/llm-status` |

это верхняя оценка отзывчивости; узкие места по SQL следует перемерить на сидах.

### 1.4 Нагрузка на LLM-тракт — точка отказа
`POST /reports/measures-analytics` с уникальным телом (гарантированный промах кэша):
```
Запрос 1: HTTP=000  ВРЕМЯ=900.004 с   (клиент отвалился по таймауту, ответа нет)
CPU бэкенда во время:  764 %           (≈7.6 из 12 ядер)
```
После отключения клиента работа **не прекратилась**. Затем `uvicorn --reload` поймал
изменение файла и встал намертво:
```
WARNING: WatchFiles detected changes in 'app/modules/incidents/models.py'. Reloading...
INFO:     Shutting down
INFO:     Waiting for background tasks to complete. (CTRL+C to force quit)
```
Итог — полный отказ сервиса:
```
GET /health   HTTP=000  TIME=10.009 с (таймаут)
Контейнер:    Up 12 hours (unhealthy)
```
Восстановление только принудительным `docker restart`.

### 1.5 Стоимость одного запроса к LLM
Конвейер `generate_reasoned_conclusion` (`modules/llm/reasoning.py`) выполняет
**3 последовательных прохода** модели на один HTTP-запрос:

| Проход | Строка | Назначение | `max_tokens` |
|--------|--------|-----------|--------------|
| 1 | `reasoning.py:361` | Э1+Э2 — проблема и первопричина | 200 |
| 2 | `reasoning.py:385` | Ролевые линзы (4 шт.) | 60 × 4 = 240 |
| 3 | `reasoning.py:431` / `:437` | Э5 — синтез мер / заключение | 300 / 220 |

Итого до **740 токенов генерации** на 12B-модели в режиме `n_gpu_layers=0` (чистый CPU).
Всё это — внутри одного синхронного HTTP-запроса.

## 2. Почему так получилось

1. **Модель-агностичность реализована через in-process загрузку.** Требование «любой GGUF
   в каталог → система подхватила» решено самым коротким путём: `llama_cpp.Llama`
   создаётся прямо в процессе API (`modules/llm/service.py:192`). Это дало простоту
   развёртывания, но связало жизненный цикл API с жизненным циклом весов модели.

2. **Качество вывода наращивалось проходами, а не моделью.** Борьба с галлюцинациями и
   «эхом» мелких моделей (BL-005) решалась добавлением этапов E0–E7, 4 линз и
   grounding-проверок. Каждый добавленный этап — ещё один проход инференса. Цена
   в CPU-времени не была заложена в бюджет отклика.

3. **Масштаб модели вырос, архитектура вызова — нет.** В `models/llm/` лежит 45.8 ГБ
   моделей (8 файлов, до 9 ГБ каждая); закреплена 12B. Синхронный вызов, приемлемый
   для `qwen2.5-0.5b` (491 МБ), стал неприемлемым для 12B без GPU.

4. **Dev-профиль применён к тяжёлой нагрузке.** `--reload`, отсутствие лимитов и
   отсутствие таймаутов — нормальны для лёгкого CRUD-приложения и разрушительны, когда
   в том же процессе живут 7 ГБ весов.

5. **Отсутствует слой наблюдаемости.** Нет метрик длительности инференса, размера кэша,
   глубины очереди на `_infer_lock`. Деградация не диагностируется до полного отказа.

---

## 3. Корневая причина

> **Тяжёлые вычисления неограниченной длительности (LLM-инференс на CPU) выполняются
> синхронно внутри процесса и жизненного цикла HTTP-запроса веб-API, без бюджета
> времени, без отмены, без изоляции ресурсов и без ограничения параллелизма.**

Все семь дефектов Д-1…Д-7 — следствия этого одного архитектурного решения:

- держим веса в процессе API → RSS 6.2 ГиБ, перезагрузка на каждую правку (Д-6),
  риск мультикопий в Celery (Д-4);
- держим инференс в запросе → таймаут клиента без отмены (Д-1, Д-2);
- нет изоляции → один запрос выносит весь сервис, нет лимитов (Д-3);
- компенсируем медленную модель кэшем → кэш без границ (Д-5).

Мьютекс `_infer_lock` (`service.py:57`) — корректная защита (llama.cpp не потокобезопасен),
но он превращает LLM в глобальный сериализованный ресурс: при N параллельных запросах
N-й ждёт N×(время инференса) без ограничения очереди.

## 4. Пути оптимизации и ожидаемый эффект

| Мера | Что делаем | Эффект |
|------|-----------|--------|
| **О-1. Лимиты контейнеров** | `mem_limit` / `cpus` для backend и celery в compose | OOM убивает один контейнер, а не хост; предсказуемая деградация |
| **О-2. Таймаут инференса** | Бюджет времени на проход + на запрос целиком; превышение → честный детерминированный fallback | Отклик ограничен сверху; отказ API из-за одного запроса исключён |
| **О-3. Ограниченный кэш (LRU)** | `_cache` → `functools.lru_cache`/OrderedDict с maxsize | Верхняя граница RSS кэша; рост прекращается |
| **О-4. Запрет модели в Celery** | Флаг `LLM_ENABLED=false` для воркеров либо вынос LLM в отдельный сервис | Исключает 2 лишние копии весов (−12 ГиБ пикового потребления) |
| **О-5. Снять `--reload` при резидентной модели** | Отдельный профиль запуска; `--reload-dir` только по `app/` без тяжёлых модулей | Нет перезагрузки 7 ГБ на каждую правку; shutdown не виснет |
| **О-6. Асинхронный контракт LLM** | `202 Accepted` + `task_id`, результат через Celery/Redis, фронт опрашивает | HTTP отвечает за миллисекунды; тяжёлая работа вне запроса |
| **О-7. Ограничение очереди** | Семафор с `max_waiting`; при переполнении — сразу fallback (fail-fast) | Нет неограниченного роста ожидания и занятых потоков |
| **О-8. Сокращение проходов** | 3 прохода → 1 составной либо проходы 2–3 только по требованию | Время отклика ↓ примерно втрое при сопоставимом качестве |
| **О-9. Кэш `brain.stats()`** | Кэшировать по mtime файлов | Убирает 3 полных чтения JSONL на каждый `llm-status` |
| **О-10. Наблюдаемость** | Метрики: длительность инференса, размер кэша, глубина очереди, RSS | Деградация видна до отказа |

**Совокупный ожидаемый результат:** пиковое потребление памяти — с 18.6 ГиБ (потенциальных)
до ≈7 ГиБ с жёстким потолком; отказ сервиса из-за LLM-запроса — исключён; отзывчивость
API — не хуже текущих p95 ≈ 25–191 мс на не-LLM путях; LLM-результаты доставляются
асинхронно без блокировки интерфейса.

## 5. Применяемые лучшие практики

1. **Bulkhead (переборки).** Тяжёлый ресурс (веса модели) изолируется от веб-слоя:
   отдельный процесс/контейнер с собственными лимитами. Отказ LLM не является отказом API.
2. **Timeout + Cancellation на каждом внешнем/тяжёлом вызове.** Ни один вызов не может
   длиться неограниченно; отключение клиента освобождает ресурс.
3. **Backpressure и fail-fast.** Ограниченная очередь вместо неограниченного ожидания;
   при перегрузке — быстрый честный ответ (у проекта уже есть качественный
   детерминированный fallback — используем его как штатный режим деградации).
4. **Bounded caches.** Любой кэш в долгоживущем процессе имеет `maxsize` и политику вытеснения.
5. **Асинхронная обработка долгих задач.** HTTP отдаёт `202` + идентификатор; результат
   забирается опросом или пушем. Уже есть Celery + Redis — инфраструктура готова.
6. **Graceful degradation вместо отказа.** Приоритет: быстрый детерминированный ответ >
   медленный LLM-ответ > отказ. Текущий код уже умеет первое — надо сделать это
   штатным путём при превышении бюджета.
7. **Resource limits как часть манифеста.** Лимиты — в compose, а не «по факту хоста».
8. **Наблюдаемость до оптимизации.** Метрики вводятся вместе с правками, чтобы эффект
   был измерим, а регресс — заметен.
9. **Разделение dev/prod-профилей запуска.** `--reload` несовместим с резидентной моделью.
10. **Сохранение скорости:** ни одна мера не замедляет не-LLM пути. Ускорение достигается
    снятием блокировок и переносом работы, а не удешевлением вычислений; качество вывода
    LLM сохраняется за счёт бюджета времени и кэша, а не сокращения логики grounding.

## 7. Регламент внесения каждого изменения

Для каждой задачи RES-XX цикл строго одинаков:

1. **ТЗ** — правка соответствующего раздела настоящего документа (или профильного ТЗ).
2. **Разработка** — изменения в коде, минимальный диф, один предмет на задачу.
3. **Код-ревью** — самопроверка по чек-листу: обратная совместимость, поведение при
   деградации, отсутствие новых блокировок, соответствие стилю модуля.
4. **Тестирование** — прогон затронутого набора: `pytest backend/tests`.
5. **Юнит-тест** — новый тест, падающий до правки и зелёный после.
6. **MR** — отдельная ветка `perf/RES-XX-<слаг>`, коммит с описанием, merge request в `main`.

## 8. Критерии приёмки контура оптимизации

- `GET /health` отвечает `200` при любой нагрузке на LLM-тракт;
- один LLM-запрос не может занимать более `LLM_TIMEOUT_S` × (число проходов);
- RSS бэкенда ограничен сверху лимитом контейнера, OOM не затрагивает хост;
- Celery-воркеры не загружают веса модели;
- p95 не-LLM эндпоинтов не хуже базовых значений §1.3;
- все новые тесты зелёные, существующие 118 юнит + 6 e2e не сломаны.
