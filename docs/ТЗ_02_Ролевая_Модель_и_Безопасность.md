## 1. Ролевая модель

АСОК ИС использует три канонические роли, покрывающие полный цикл управления
качеством ИС: от внесения данных и оценки до принятия управленческих решений.

### 1.1. ADMIN (Топ-менеджмент)

**Целевые пользователи:** ИТ-директор (CIO), технический директор (CTO),
генеральный директор (CEO), члены правления, курирующие ИТ.

| Параметр | Значение |
|----------|----------|
| Код роли в БД/токене | `ADMIN` |
| Человекочитаемая подпись (UI) | Топ-менеджмент |
| Уровень доступа | Полный |

**Функциональные полномочия:**

- Полный доступ ко всем разделам системы без ограничений.
- Просмотр управленческих дашбордов (Executive Dashboard) с агрегатами
  качества по всем ИС организации.
- AI-инсайты: аномалии, прогнозы деградации, рекомендации.
- Утверждение или отклонение корректирующих мер (governance loop).
- Принятие решений по эскалациям.
- Редактирование метаданных мер (ответственный, приоритет, срок).
- Управление пользователями (создание, деактивация, смена роли).
- Управление справочником информационных систем.
- Доступ к полному журналу аудита.
- Настройка системных параметров (DEMO_MODE, LLM-конфигурация).
- Инициализация и пересев демо-данных.

**Управленческие сценарии:**

1. Ежеквартальный обзор качества ИТ-портфеля банка.
2. Принятие решения по мерам, предложенным менеджерами качества.
3. Анализ инцидентов и их влияния на качество ИС.
4. Стратегическое планирование программы повышения качества.

### 1.2. QUALITY_MANAGER (Менеджер по качеству)

**Целевые пользователи:** ответственные за качество ИС, владельцы процессов
оценки, руководители отделов тестирования.

| Параметр | Значение |
|----------|----------|
| Код роли в БД/токене | `QUALITY_MANAGER` |
| Человекочитаемая подпись (UI) | Менеджер по качеству |
| Уровень доступа | Операционный |

**Функциональные полномочия:**

- Создание и проведение оценок качества ИС.
- Внесение метрик (A, B, X, формула расчёта) по периодам.
- Профессиональные суждения по проблемным подхарактеристикам:
  факт, влияние, предлагаемая мера, ответственный, срок, эскалация.
- Предложение корректирующих мер с обоснованием.
- Отчёт об исполнении мер (статус выполнения, комментарий).
- Инициирование эскалаций по просроченным или критичным мерам.
- Просмотр операционных дашбордов (менеджерский уровень).
- Загрузка данных из Excel/CSV.
- Внесение данных об инцидентах (сбоях).

**Ограничения (SoD):**

- НЕ МОЖЕТ утверждать или отклонять собственные предложения мер.
- НЕ МОЖЕТ управлять пользователями.
- НЕ МОЖЕТ изменять системные настройки.
- НЕ МОЖЕТ принимать решения по эскалациям (только инициировать).

### 1.3. TEST_ANALYST (Аналитик / Тестировщик)

**Целевые пользователи:** тестировщики, младшие аналитики, специалисты
по сбору данных.

| Параметр | Значение |
|----------|----------|
| Код роли в БД/токене | `TEST_ANALYST` |
| Человекочитаемая подпись (UI) | Аналитик |
| Уровень доступа | Только чтение + загрузка данных |

**Функциональные полномочия:**

- Просмотр дашбордов в режиме «только чтение».
- Загрузка тестовых данных (Excel/CSV) для назначенных ИС.
- Просмотр отчётов и динамики качества.
- Просмотр базы рисков.

**Ограничения:**

- НЕ МОЖЕТ создавать или изменять оценки.
- НЕ МОЖЕТ предлагать корректирующие меры.
- НЕ МОЖЕТ принимать управленческие решения.
- НЕ МОЖЕТ вносить профессиональные суждения.
- Доступ ограничен назначенными информационными системами.

### 1.4. Легаси-роли (обратная совместимость)

Для совместимости с ранее выданными токенами и записями в БД система
поддерживает маппинг устаревших кодов ролей на канонические:

| Легаси-код | Каноническая роль | Уровень доступа |
|------------|-------------------|-----------------|
| `CTO` | ADMIN (Топ-менеджмент) | Полный |
| `CEO` | ADMIN (Топ-менеджмент) | Полный |
| `CIO` | ADMIN (Топ-менеджмент) | Полный |
| `EXECUTIVE` | ADMIN (Топ-менеджмент) | Полный |
| `GUEST` | --- | Нет доступа (подпись «Гость») |

Маппинг реализован:
- **Frontend:** `frontend/src/constants/roles.ts` -- единый словарь `ROLE_LABELS`.
- **Backend:** `governance/router.py` -- кортеж `DECISION_ROLES` включает все
  легаси-коды топ-менеджмента.

Легаси-токены продолжают работать без перевыпуска. При создании новых
пользователей рекомендуется использовать только канонические роли.

## 3. Разделение обязанностей (SoD)

### 3.1. Инварианты

Система обеспечивает следующие инварианты разделения обязанностей,
предотвращающие конфликт интересов:

```
ИНВАРИАНТ SoD-1: Предложивший меру != Утвердивший меру
  Лицо, создавшее предложение корректирующей меры (created_by),
  не может быть лицом, принявшим решение по ней (decided_by).
  Гарантируется разделением ролей: create = MANAGER_ROLES,
  approve/reject = DECISION_ROLES.

ИНВАРИАНТ SoD-2: Исполнитель != Контролёр
  Менеджер качества отчитывается об исполнении меры (execution),
  а топ-менеджмент контролирует и принимает результат.

ИНВАРИАНТ SoD-3: Эскалация != Решение по эскалации
  Менеджер качества инициирует эскалацию,
  топ-менеджмент принимает решение по ней.
```

### 3.2. Реализация на уровне API

```
governance/router.py:

DECISION_ROLES = ("ADMIN", "CTO", "CEO", "CIO", "EXECUTIVE")
MANAGER_ROLES  = ("QUALITY_MANAGER", "ADMIN")

POST /proposals           -> require_role(*MANAGER_ROLES)   # создание
POST /proposals/{id}/approve -> require_role(*DECISION_ROLES) # решение
POST /proposals/{id}/reject  -> require_role(*DECISION_ROLES) # решение
```

Примечание: ADMIN входит в оба кортежа (`MANAGER_ROLES` и `DECISION_ROLES`),
что позволяет ему выполнять любые действия. Однако в продуктивной среде
рекомендуется, чтобы один и тот же физический пользователь с ролью ADMIN
не создавал и не утверждал одну и ту же меру. Техническое ограничение
`created_by != decided_by` планируется к реализации на уровне сервисного слоя.

### 3.3. Governance flow (текстовая диаграмма)

```
                     Governance Loop — SoD

  QUALITY_MANAGER                           ADMIN (Топ-менеджмент)
  ===============                           =====================

  [1] Оценка выявляет
      низкое качество
          |
          v
  [2] Предлагает меру -----> [3] Система проверяет SoD
      (created_by = QM)            (proposer != approver)
                                        |
                                        v
                              [4] Уведомление ADMIN
                                        |
                                        v
                              [5] Рассмотрение:
                                  +-- approve (утвердить)
                                  +-- reject  (отклонить)
                                  +-- return  (вернуть
                                  |           на доработку)
                                  v
  [6] Мера в плане <--------- решение + обоснование
      задач (deadline)              (decided_by = ADMIN)
          |
          v
  [7] Отчёт об исполнении
      (execution_status)
          |
          v
                              [8] Контроль эффективности
                                  в следующих периодах
```

### 3.4. Правила эскалации

| Условие | Действие | Ответственный |
|---------|----------|---------------|
| Мера не рассмотрена > 5 рабочих дней | Уведомление ADMIN | Система (авто) |
| Мера просрочена (deadline < today) | QM инициирует эскалацию | QUALITY_MANAGER |
| Эскалация получена | Решение: продлить / переназначить / отменить | ADMIN |
| Критическая ИС (MISSION_CRITICAL) без мер | Автоэскалация | Система (авто) |

## 4. Аутентификация и авторизация

### 4.1. Аутентификация (JWT)

Система использует двухтокенную схему на основе JSON Web Tokens:

| Параметр | Access Token | Refresh Token |
|----------|-------------|---------------|
| Время жизни | 30 минут | 7 дней |
| Поле `type` в payload | `access` | `refresh` |
| Содержимое | sub (UUID), role, username | sub (UUID), type |
| Хранение (текущее) | `localStorage` | `localStorage` |
| Хранение (целевое) | `httpOnly` cookie | `httpOnly` cookie |

**Процесс аутентификации:**

```
1. Пользователь -> POST /api/v1/auth/login {username, password}
2. Сервер:
   a. Находит пользователя в БД по username
   b. Проверяет bcrypt-хеш пароля (cost factor = 12)
   c. Генерирует пару токенов (access + refresh)
   d. Записывает last_login
   e. Возвращает {access_token, refresh_token, user: {id, username, role}}
3. Клиент сохраняет токены
4. Все последующие запросы: Authorization: Bearer <access_token>
5. При истечении access_token: POST /api/v1/auth/refresh {refresh_token}
   -> новая пара токенов
```

**Защита от token-type confusion (S4):**

```python
# security.py
def decode_token(token: str, expected_type: str = "access") -> TokenPayload:
    payload = jwt.decode(token, settings.JWT_SECRET_KEY, algorithms=["HS256"])
    if payload.get("type") != expected_type:
        raise ValueError("Token type mismatch")
    return TokenPayload(**payload)
```

Эндпоинт `/auth/refresh` принимает только токен с `type=refresh`.
Access-токен нельзя использовать для обновления сессии.

### 4.2. Хеширование паролей

```
Алгоритм:  bcrypt
Cost factor: 12 (~ 250 мс на хеширование)
Библиотека: passlib[bcrypt]
Хранение:   поле password_hash (VARCHAR 255), только хеш
Проверка:   verify(plain, hash) — время-константная
```

### 4.3. Middleware авторизации (Backend)

```python
# iam/deps.py — ключевые зависимости

async def get_current_user(credentials) -> dict:
    """Извлекает текущего пользователя из Bearer-токена.
    В DEMO_MODE при отсутствии/невалидном токене — fallback на demo-ADMIN.
    В продуктивном режиме — строгий 401."""

def require_role(*allowed_roles: str):
    """Декоратор-фабрика для ограничения эндпоинтов по ролям.
    Проверяет пересечение ролей пользователя с допустимыми.
    Возвращает 403 Forbidden при несоответствии."""
```

### 4.4. Защита маршрутов (Frontend)

На стороне клиента реализована двухуровневая защита:

1. **Route guards** -- компонент `ProtectedRoute` проверяет наличие
   валидного токена и соответствие роли перед рендером страницы.
2. **Условный рендер UI** -- элементы управления (кнопки утверждения,
   формы создания мер) отображаются только для соответствующих ролей.
3. **API interceptor** -- axios-перехватчик добавляет `Authorization`-заголовок
   и обрабатывает 401/403 (редирект на логин, уведомление о недостатке прав).

### 4.5. Демо-аккаунты

Для демонстрационного режима (`DEMO_MODE=true`) предусмотрены встроенные учётные записи:

| Логин | Пароль | Роль | Назначение |
|-------|--------|------|------------|
| `admin` | `Admin123!` | ADMIN | Демонстрация управленческих дашбордов |
| `manager` | `Manager123!` | QUALITY_MANAGER | Демонстрация операционного цикла |
| `analyst` | `Analyst123!` | TEST_ANALYST | Демонстрация внесения данных |

Источник — словарь `DEMO_USERS` в `backend/app/modules/iam/router.py`.

**Ограничение S1:** демо-аккаунты доступны ТОЛЬКО при `DEMO_MODE=true`.
В продуктивном режиме блок `DEMO_USERS` не выполняется, аутентификация
идёт строго по записям в БД.

## 5. Безопасность: находки и их устранение

### 5.1. Реестр находок (S1-S11)

| # | Находка | Критичность | Норматив | Статус |
|---|---------|-------------|----------|--------|
| **S1** | Демо-учётки с паролями в коде работали в любом режиме | Критичная | ГОСТ 57580 (управление доступом), 152-ФЗ | Исправлено |
| **S2** | Дефолтные секреты JWT и пароль БД в конфигурации | Критичная | ГОСТ 57580 (управление секретами) | Исправлено |
| **S3** | DEMO_MODE подменяет любого на ADMIN без проверки | Критичная | ГОСТ 57580 (идентификация/аутентификация) | Снижено (только при DEMO_MODE + warning) |
| **S4** | Token-type confusion: refresh-токен принимался как access | Высокая | ГОСТ 57580 (управление сессиями) | Исправлено |
| **S5** | Эндпоинты загрузки Excel без авторизации | Высокая | ГОСТ 57580 (разграничение доступа) | Исправлено |
| **S6** | Валидация файлов только по расширению (спуфинг) | Средняя | ГОСТ 57580 (контроль ввода) | Исправлено |
| **S7** | Часть read-эндпоинтов `/reports` без auth | Средняя | ГОСТ 57580 | К доработке |
| **S8** | JWT хранится в localStorage (риск XSS) | Средняя | ГОСТ 57580 (защита сессии) | К доработке |
| **S9** | Риск утечки ПДн в логи при исключениях | Низкая | 152-ФЗ ст.19 | К доработке |
| **S10** | Отсутствие журналирования ИБ-событий | Средняя | ГОСТ 57580 (регистрация событий) | Частично (модель AuditLog есть, запись к доработке) |
| **S11** | Отсутствие rate-limiting на /login (брутфорс) | Средняя | ГОСТ 57580 | К доработке |

### 5.2. Детализация исправлений

**S1 -- Демо-учётки ограничены DEMO_MODE:**

Блок `DEMO_USERS` в `auth.py` выполняется только при `settings.DEMO_MODE == True`.
В продуктивном режиме встроенных паролей нет. Аутентификация — строго по БД (bcrypt, 12 раундов).

**S2 -- Fail-fast при дефолтных секретах:**

```python
# config.py
def security_issues(self) -> list[str]:
    issues = []
    if self.JWT_SECRET_KEY == "default-secret-key":
        issues.append("JWT_SECRET_KEY is default")
    if len(self.JWT_SECRET_KEY) < 32:
        issues.append("JWT_SECRET_KEY too short (<32 chars)")
    return issues
```

При `DEMO_MODE=false` приложение НЕ СТАРТУЕТ, если обнаружены дефолтные
или слабые секреты. Реализовано в `main.py` при запуске.

**S4 -- Проверка типа токена:**

`decode_token(token, expected_type="access")` проверяет поле `type`
в JWT-payload. Эндпоинт `/auth/refresh` вызывает `decode_token(token, expected_type="refresh")`.
Подстановка access-токена вместо refresh возвращает 401.

**S5 -- Авторизация загрузки файлов:**

Все эндпоинты загрузки защищены `require_role`:
- `/excel/upload` -- TEST_ANALYST, QUALITY_MANAGER, ADMIN
- `/import-assessment` -- QUALITY_MANAGER, ADMIN
- `/seed-project-files` -- только ADMIN

**S6 -- Валидация сигнатуры файла:**

Помимо проверки расширения (.xlsx, .xls, .csv), проверяется
магическая подпись `PK\x03\x04` (OOXML/ZIP). Лимит размера: 10 МБ.

### 5.3. Существующие защитные механизмы

| Механизм | Описание | Файл |
|----------|----------|------|
| bcrypt-хеширование | cost=12, хранится только хеш | `iam/security.py` |
| ORM-параметризация | Нет конкатенации SQL, защита от инъекций | Все модели (SQLAlchemy) |
| Path traversal | `uuid4` + `os.path.basename` для загрузок | `dataio/router.py` |
| CORS | Белый список origin, не `*` | `main.py` |
| RBAC | `require_role` на всех мутирующих эндпоинтах | `iam/deps.py` |
| Безопасный Excel | `read_only=True` при парсинге openpyxl | `dataio/excel_helpers.py` |
| Soft delete | Записи помечаются `is_deleted`, не удаляются физически | `shared/db.py` |

## 6. Нормативно-правовая база

### 6.1. 152-ФЗ «О персональных данных»

**Применимость:** система обрабатывает ФИО сотрудников (ответственные за ИС,
менеджеры качества), что является персональными данными.

| Требование | Статья | Реализация |
|------------|--------|------------|
| Правовое основание обработки | ст.6 | Трудовой договор / должностная инструкция |
| Минимизация данных | ст.5 | Только ФИО и роль; ПДн клиентов банка не обрабатываются |
| Локализация БД на территории РФ | ст.18 | PostgreSQL on-prem, данные не покидают контур |
| Защита при обработке | ст.19 | Шифрование (bcrypt, JWT), RBAC, аудит |
| Уничтожение по достижении цели | ст.21 | Soft delete + политика хранения (к доработке) |
| Уведомление Роскомнадзора | ст.22 | Обязанность оператора (организации-заказчика) |

**LLM и ПДн:** локальная модель (on-prem GGUF) -- данные не покидают контур
организации. В промпт попадают только агрегированные метрики качества,
не содержащие ПДн. Минимизация контролируется шлюзом правил (`gate.py`).

### 6.2. ГОСТ Р 57580.1-2017

**Применимость:** АСОК ИС используется финансовой организацией (банком),
следовательно, подпадает под требования стандарта.

| Группа мер | Реализация |
|------------|------------|
| Управление доступом (УД) | RBAC с тремя ролями, SoD, `require_role` |
| Управление секретами (УС) | bcrypt, fail-fast дефолтных секретов, JWT rotation |
| Идентификация/аутентификация (ИА) | JWT (access + refresh), bcrypt, token-type check |
| Защита сессий (ЗС) | TTL токенов, планируется httpOnly cookie |
| Контроль ввода (КВ) | Валидация сигнатур файлов, размера, типа |
| Разграничение доступа (РД) | Ролевые эндпоинты, фронтовые route guards |
| Регистрация событий (РС) | Модель AuditLog (таблица audit_log), к заполнению |
| Защита от НСД (ЗН) | CORS, RBAC, token validation |

### 6.3. 187-ФЗ «О безопасности КИИ»

**Применимость:** если оцениваемые ИС банка отнесены к значимым объектам
критической информационной инфраструктуры, АСОК ИС как инструмент управления
их качеством также попадает в контур КИИ.

| Требование | Реализация |
|------------|------------|
| Категорирование объекта | Определяется оператором (банком) |
| Подключение к ГосСОПКА | К доработке (задел в audit_log) |
| Реагирование на инциденты | Модуль incidents, эскалации |

## 7. Governance Loop

### 7.1. Полный цикл управленческого решения

Governance Loop -- замкнутый цикл управления качеством ИС, от обнаружения
проблемы до контроля эффективности принятых мер.

```
Период N                    Период N+1
========                    ==========

[ОЦЕНКА]                    [КОНТРОЛЬ]
    |                           ^
    v                           |
Метрики A,B,X              Повторная оценка:
    |                       мера помогла?
    v                           |
Расчёт качества                 |
(formula)                       |
    |                           |
    v                           |
Качество ниже          [8] Эффективность
порога?                    отслеживается
    |                      в следующих
    | ДА                   периодах
    v                           ^
[1] Аномалия                    |
    выявлена               [7] Мера в плане
    |                      задач с дедлайном
    v                           ^
[2] QM формирует                |
    суждение:              [6] Решение
    - факт                 записывается:
    - влияние              - timestamp
    - предложение          - decided_by
    - ответственный        - обоснование
    - срок                      ^
    |                           |
    v                      [5] ADMIN
[3] Предложение            рассматривает:
    корректирующей         +-- approve
    меры                   +-- reject
    |                      +-- return
    v                           ^
[4] Система                     |
    проверяет SoD:         ADMIN получает
    created_by != approver уведомление
    (роли разные)
```

### 7.2. Статусная модель меры (proposal)

```
                  +-- reject --> [REJECTED]
                  |
[PENDING] ---> review --+-- approve --> [APPROVED] --> [IN_PROGRESS]
    ^                   |                                    |
    |                   +-- return --> [RETURNED]        исполнение
    |                                     |                  |
    +------------- доработка <------------+                  v
                                                      [COMPLETED]
                                                           |
                                                      контроль
                                                      в периоде N+1

    В любой момент из [APPROVED]/[IN_PROGRESS]:

    [ESCALATED] <--- QM инициирует ---> ADMIN решает
         |                                    |
         +--- extend_deadline ----------------+
         +--- reassign -----------------------+
         +--- cancel -------------------------+
```

### 7.3. Поля записи governance (таблица proposals)

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | UUID | Первичный ключ |
| `system_name` | String | ИС, к которой относится мера |
| `title` | String | Краткое название меры |
| `description` | Text | Подробное описание и обоснование |
| `priority` | Enum | LOW / MEDIUM / HIGH / CRITICAL |
| `status` | Enum | PENDING / APPROVED / REJECTED / RETURNED / IN_PROGRESS / COMPLETED / ESCALATED |
| `created_by` | String | Логин предложившего (QM) |
| `decided_by` | String | Логин утвердившего/отклонившего (ADMIN) |
| `decision_comment` | Text | Обоснование решения |
| `decided_at` | DateTime | Дата/время решения |
| `deadline` | Date | Срок исполнения |
| `responsible` | String | Ответственный за исполнение |
| `execution_status` | String | Статус исполнения |
| `execution_comment` | Text | Комментарий об исполнении |
| `escalation_reason` | Text | Причина эскалации |

### 7.4. API governance (эндпоинты)

| Эндпоинт | Действие | Роль | SoD |
|-----------|----------|------|-----|
| `POST /proposals` | Создание меры | QM, ADMIN | created_by фиксируется |
