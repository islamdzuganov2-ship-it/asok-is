## 1. Концепция

### 1.1. Зачем LLM в системе оценки качества

Числовые показатели качества рассчитываются детерминированно по формулам стандарта. Но руководителю нужен не столбец процентов, а ответ на вопросы: *что именно просело, почему это важно для бизнеса, что делать*. Перевод расчёта в управленческий вывод — задача, которую традиционно выполняет аналитик вручную. LLM автоматизирует именно этот переход.

### 1.2. Базовые принципы

| Принцип | Реализация |
|---------|-----------|
| **Только локально (on-premise)** | Модель работает внутри контура банка, данные не покидают периметр. Внешние API (OpenAI, облачные сервисы) не используются в принципе |
| **Модель-агностичность** | Любая GGUF-модель, положенная в каталог, работает без изменения кода |
| **Расчёт важнее интерпретации** | Вердикт о качестве выносит детерминированный движок правил; LLM только объясняет его |
| **Честность важнее красоты** | Ответ, содержащий выдуманные числа, отбраковывается и заменяется детерминированным текстом |
| **Знания вне модели** | Накопленный опыт хранится отдельно от весов, поэтому замена модели не обнуляет обучение |
| **Аудируемость** | Каждое рассуждение сохраняется трассой: какие этапы прошли, где сработал запасной вариант |

### 1.3. Что LLM не делает

- Не выносит вердикт об уровне качества — это делает `gate.py`.
- Не рассчитывает метрики — это делает `calculation.py`.
- Не принимает решения по мерам — это делает человек с ролью `ADMIN`.
- Не имеет доступа к персональным данным — в промпт передаются только агрегированные показатели.

## 2. Архитектура LLM-подсистемы

### 2.1. Состав модуля

**Каталог:** `backend/app/modules/llm/`

| Файл | Назначение |
|------|-----------|
| `service.py` | Загрузка модели, инференс, grounding-проверки, генерация выводов |
| `gate.py` | Детерминированный движок правил — источник вердикта |
| `reasoning.py` | Многоаспектный конвейер рассуждения (BL-005) |
| `brain.py` | «Резервный мозг»: память, обратная связь, корпус |
| `prompts.py` | Системный промпт, шаблоны проходов, определения линз |
| `knowledge.py` | Доменный глоссарий ISO 25010 для смыслового раскрытия |
| `dataset.py` | Выгрузка обучающего датасета |
| `tasks.py` | Асинхронные задачи Celery |

### 2.2. Рантайм

**`llama-cpp-python` 0.3.x** — инференс GGUF-моделей внутри процесса бэкенда, без отдельного сервиса. Это упрощает развёртывание: нет сетевого взаимодействия, нет отдельного контейнера с моделью, нет проблем с недоступностью внешнего сервиса.

### 2.3. Конфигурация

Параметры в `backend/app/infrastructure/config.py`:

| Параметр | Значение по умолчанию | Описание |
|----------|----------------------|----------|
| `LLM_ENABLED` | `True` | Включение подсистемы |
| `LOCAL_LLM_MODEL_DIR` | `models/llm` | Каталог с GGUF-файлами |
| `LOCAL_LLM_MODEL_FILE` | `auto` | `auto` — автоподбор; либо явное имя файла |
| `LLM_N_CTX` | `4096` | Верхняя граница окна контекста (фактически ограничивается моделью) |
| `LLM_N_THREADS` | `8` | Потоки CPU; для крупных моделей больше |
| `LLM_N_GPU_LAYERS` | `0` | `0` — CPU; `-1` — все слои на GPU (нужна CUDA/Metal-сборка) |
| `LLM_MAX_TOKENS` | `320` | Предел длины ответа |
| `LLM_TEMPERATURE` | `0.1` | Максимум детерминизма — управленческие выводы должны быть воспроизводимы |
| `LLM_TOP_P` | `0.9` | Параметр nucleus sampling |
| `LLM_CHAT_FORMAT` | `auto` | `auto` — шаблон чата берётся из метаданных GGUF |
| `LLM_BRAIN_DIR` | `models/llm_brain` | Каталог «резервного мозга» |

> **Обоснование `temperature = 0.1`.** Управленческий вывод по одним и тем же данным не должен меняться от запуска к запуску: иначе теряется доверие к системе и невозможен аудит. Творческая вариативность здесь — недостаток, а не достоинство.

## 3. Модель-агностичность

### 3.1. Механизм автоподбора

Реализован в `service.py`:

1. Сканируется каталог `LOCAL_LLM_MODEL_DIR` по маске `*.gguf`.
2. Отфильтровываются служебные файлы: имена, содержащие `mmproj`, пропускаются — это проекторы мультимодальных моделей, которые идут в пару к основной модели и самостоятельной моделью не являются.
3. Оставшиеся файлы сортируются **по времени модификации, новейший первым**.
4. Выбирается первый файл.

При явно заданном `LOCAL_LLM_MODEL_FILE` (не `auto`) используется указанный файл. Если каталог пуст, применяется резервное имя `asok-model.gguf`.

> **Практическое следствие.** Чтобы переключить модель, достаточно положить новый GGUF-файл в каталог — он окажется новейшим по времени и будет выбран автоматически. Пересборка образа не нужна.

### 3.2. Доступные модели

| Файл | Размер | Профиль применения |
|------|--------|-------------------|
| `qwen2.5-0.5b-instruct-q4_k_m.gguf` | 469 МБ | Сверхлёгкая: отладка, слабое железо, быстрые прогоны тестов |
| `asok-model.gguf` | 5,3 ГБ | Доменная модель проекта |
| `Qwen3.5-9B-Q4_K_M.gguf` | 5,3 ГБ | Сбалансированная: качество/скорость |
| `gemma-3-12b-it-Q4_K_M.gguf` | 6,8 ГБ | Универсальная |
| `Qwen3-14B-Q4_K_M.gguf` | 8,4 ГБ | Высокое качество русского языка |
| `DeepSeek-R1-Distill-Qwen-14B-Q4_K_M.gguf` | 8,4 ГБ | Углублённое рассуждение |
| `phi-4-Q4_K_M.gguf` | 8,5 ГБ | Аналитика и структурированный вывод |
| `mmproj-model-f16.gguf` | 815 МБ | *Служебный проектор — автоматически пропускается* |

Все модели квантизованы в Q4_K_M — компромисс между объёмом памяти и качеством.

### 3.3. Профиль модели

При загрузке фиксируется профиль: имя файла, размер в мегабайтах, архитектура. Профиль доступен через `GET /api/v1/reports/llm-status` и записывается в «мозг» функцией `note_model()` — это позволяет отследить, какой моделью получен конкретный вывод.

### 3.4. Управление через API

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/api/v1/reports/llm-status` | Состояние подсистемы, профиль загруженной модели |
| GET | `/api/v1/reports/llm-models` | Список доступных GGUF-файлов с размерами |
| POST | `/api/v1/reports/llm-reload` | Перезагрузка модели без перезапуска контейнера |

## 4. Шлюз правил (Gate)

### 4.1. Назначение

`gate.py` — детерминированный движок, который выносит вердикт о качестве **до** обращения к модели. Это архитектурный барьер: LLM физически не может переопределить расчёт, потому что получает вердикт как входные данные, а не формирует его.

### 4.2. Структуры

```python
@dataclass
class RuleSignal:
    """Одно сработавшее правило: код, ярлык (как на схеме) и человекочитаемая деталь."""

@dataclass
class GateResult:
    """Итог работы движка правил: какие правила сработали и общая серьёзность."""
```

Функция `evaluate_gate()` оценивает правила на **посчитанных** метриках и возвращает вердикт. Метод `rules_block` формирует текстовый блок сработавших правил для передачи в конвейер рассуждения.

### 4.3. Роль в цепочке

```
Метрики (расчёт по формулам)
        ↓
   evaluate_gate() → вердикт + список сработавших правил
        ↓
   rules_block передаётся в промпт
        ↓
   LLM объясняет вердикт человеческим языком
```

Если модель недоступна или её ответ отбракован, вердикт всё равно есть — пользователь получит детерминированный текст. **Система не перестаёт работать без LLM**, она лишь теряет качество формулировок.

## 5. Конвейер рассуждения

### 5.1. Назначение

Реализация инициативы **BL-005** в `reasoning.py`. Вместо одного запроса «напиши вывод» выполняется многоэтапный конвейер с промежуточным контролем достоверности. Это даёт содержательный анализ вместо пересказа входных чисел.

### 5.2. Входные данные

```python
@dataclass(frozen=True)
class ReasoningInput:
    system_name: str
    period_label: str
    judgments_block: str    # профессиональные суждения
    risks_block: str        # риски из базы
    measures_block: str     # карточки мер
    metrics_block: str      # расчётные метрики
    history_block: str      # выводы прошлых периодов (преемственность)
    rules_block: str        # сработавшие правила движка
```

Три источника контура (суждения, риски, меры) плюс метрики, история и вердикт правил. `history_block` обеспечивает преемственность: вывод учитывает, что говорилось в прошлых периодах.

### 5.3. Этапы конвейера

| Код | Этап | Содержание |
|-----|------|-----------|
| **E0** | Факты входа | Фиксация исходных данных без интерпретации |
| **E1** | Постановка проблемы | Что именно является проблемой |
| **E2** | Первопричина | Почему это произошло |
| **E3** | Ролевые точки зрения | Анализ через линзы (см. 5.4) |
| **E4** | Контроль достоверности этапов | Проверка предыдущих выводов на обоснованность |
| **E5** | Синтез мер | Какие меры предлагаются |
| **E6** | Саморефлексия и оговорки | Границы применимости вывода, чего не хватает в данных |
| **E7** | Заключение для руководителя (ЛПР) | Итоговый управленческий текст |

Этап **E4** принципиален: конвейер проверяет сам себя перед тем, как перейти к синтезу мер. Этап **E6** заставляет модель явно назвать ограничения вывода — это снижает риск, что руководитель воспримет неполный анализ как исчерпывающий.

### 5.4. Ролевые линзы

Этап E3 рассматривает ситуацию с четырёх профессиональных позиций (`REASONING_LENSES` в `prompts.py`). Набор по умолчанию: `("CIO", "QUALITY", "RISK", "SECURITY")`, минимум — три линзы.

| Код | Роль | Вопрос линзы | Опора на стандарт |
|-----|------|--------------|-------------------|
| `CIO` | ИТ-директор (CIO/CTO) | Как проблема влияет на бизнес-ценность и стратегию ИТ? Что это значит для ландшафта? | ISO 38500 «Стратегия» |
| `QUALITY` | Менеджер качества | Какие характеристики и подхарактеристики ISO 25010 просели по сути суждений и почему? | ISO 25010 (модель качества) |
| `RISK` | Риск-офицер | Какие риски из переданной базы активируются? Каковы последствия и меры минимизации? | ISO 38500 «Соответствие» |
| `SECURITY` | Информационная безопасность | Затронута ли защищённость (конфиденциальность, целостность, подотчётность)? Есть ли сигналы в данных? | ISO 25010 «Защищённость» |

Каждая линза — отдельный взгляд с собственным вопросом и привязкой к стандарту. Это соответствует реальной практике: одно и то же снижение показателя по-разному выглядит для ИТ-директора и для риск-офицера.

### 5.5. Трасса рассуждения

```python
@dataclass
class StageResult:
    code: str
    title: str
    content: str
    used_llm: bool = False
    grounded: bool = True    # прошёл grounding-проверку ИЛИ детерминирован по построению
    fell_back: bool = False  # LLM-вывод отбракован → детерминированный текст

@dataclass
class ReasoningTrace:
    """Аудируемая трасса конвейера: этапы, линзы, заключение, уверенность."""
    input: ReasoningInput
    stages: list[StageResult]
    lenses: list[LensView]
    conclusion: str
    confidence: str   # низкая | средняя | высокая
```

**Уровень уверенности** рассчитывается **детерминированно из полноты входных данных**, а не запрашивается у модели. Модель не может заявить о высокой уверенности при скудных данных.

Флаги `used_llm`, `grounded`, `fell_back` на каждом этапе делают трассу аудируемой: видно, где сработала модель, а где система вернулась к детерминированному тексту.

### 5.6. Механизм отката

Для каждого этапа предусмотрен детерминированный запасной вариант: `_fallback_problem()`, `_fallback_root_cause()`, `_fallback_lens_view()`, `_fallback_measures()`. Если ответ модели отбракован проверками (`_grounded()`, `_degenerate()`, `_anchored()`), используется запасной текст, а этап помечается `fell_back = True`.

### 5.7. Два потока применения

1. **Профессиональные суждения** — формирование заключения по оценке (`generate_reasoned_conclusion()`).
2. **Карточки мер** — анализ предложенных и реализованных мер (эндпоинт `POST /api/v1/governance/measures-analytics`).

## 6. Резервный мозг (Brain)

### 6.1. Идея

Знания, накопленные системой, хранятся **вне файла модели** — в каталоге `models/llm_brain/`. Замена GGUF-файла не приводит к потере обучения. Это решает известную проблему: дообученная модель привязывает знания к конкретным весам, и переход на более новую модель обнуляет накопленный опыт.

### 6.2. Файлы

| Файл | Содержание |
|------|-----------|
| `brain_meta.json` | Профиль: метаданные, сведения об использованных моделях |
| `corpus.jsonl` | Доменный корпус: методика, эталонные примеры |
| `memory.jsonl` | Записи о прошлых выводах для припоминания |
| `feedback.jsonl` | Обратная связь пользователей по качеству выводов |

### 6.3. Программный интерфейс (`brain.py`)

| Функция | Назначение |
|---------|-----------|
| `remember(record)` | Сохранить вывод в память, вернуть отпечаток |
| `recall(system_name, chars, k=3)` | Припомнить релевантные прошлые выводы для заземления |
| `record_feedback(fingerprint_id, verdict, edited_text, user)` | Зафиксировать оценку пользователя и его правку |
| `append_corpus(example)` | Пополнить доменный корпус |
| `human_edits()` | Получить правки пользователей — материал для дообучения |
| `note_model(name, architecture)` | Отметить, какой моделью получен результат |
| `fingerprint(*parts)` | Вычислить отпечаток для связывания вывода и обратной связи |
| `load_profile()` / `save_profile()` | Работа с профилем «мозга» |

### 6.4. Цикл самообучения

```
LLM формирует вывод
        ↓
remember() → запись в memory.jsonl с отпечатком
        ↓
Пользователь оценивает вывод (компонент ConclusionFeedback)
        ↓
record_feedback() → запись в feedback.jsonl, включая исправленный текст
        ↓
recall() при следующем запросе подмешивает релевантный опыт в контекст
        ↓
human_edits() → материал для дообучения (уровень C)
```

Правка пользователя ценнее оценки «палец вверх/вниз»: она показывает не только что вывод неудачен, но и каким он должен быть.

## 7. Защита от галлюцинаций

### 7.1. Проверка процентов (grounding)

Реализована в `service.py`. После генерации:

1. Из входных данных собирается множество допустимых процентных значений (`_allowed_pcts()` по метрикам и известным рискам).
2. Из ответа модели извлекаются все упомянутые проценты (регулярное выражение `_PCT_RE`).
3. Вычисляется разность: `hallucinated = used - allowed`.
4. Если разность непуста — в журнал пишется предупреждение со списком выдуманных значений, а ответ **заменяется** детерминированным текстом `_grounded_fallback()`.

```python
if hallucinated:
    logger.warning(
        "LLM упомянула проценты вне входных данных %s — заменяю на честный fallback",
        sorted(hallucinated),
    )
    text = _grounded_fallback(system_name, period_label, metrics_block)
```

Это жёсткая гарантия: **ни одна цифра в управленческом выводе не может быть выдумана моделью**. Число либо пришло из расчёта, либо его нет.

### 7.2. Обнаружение вырожденного ответа

Слабые модели склонны возвращать «эхо» — пересказ входного перечня характеристик вместо анализа. Функция `_is_echo()` выявляет такие ответы, и они также заменяются детерминированным текстом. Аналогично работает `_degenerate()` в конвейере рассуждения.

### 7.3. Проверка привязки к входу

Функции `_grounded()` и `_anchored()` в `reasoning.py` проверяют, что текст этапа опирается на якоря из входных данных (`_input_anchors()`), а не является общими рассуждениями.

### 7.4. Итоговая гарантия

| Слой защиты | Что предотвращает |
|-------------|-------------------|
| Шлюз правил | Подмену вердикта мнением модели |
| Проверка процентов | Выдуманные числа |
| Обнаружение эха | Бессодержательный пересказ входа |
| Проверка привязки | Общие рассуждения не по делу |
| Детерминированная уверенность | Заявление о надёжности при неполных данных |
| Откат на каждом этапе | Отказ системы при недоступности модели |

## 8. Промпт-инжиниринг

### 8.1. Системный промпт

`REASONING_SYSTEM_PROMPT` в `prompts.py`:

> Ты — аналитик качества информационных систем банка (методика МК_8.1, ISO/IEC 25010, ISO/IEC 38500). Твоя главная ценность — ЧЕСТНОСТЬ и содержательность.
>
> СТРОГИЕ ПРАВИЛА (нарушать запрещено):
> 1. Используй ТОЛЬКО факты и числа из переданных данных; ничего не выдумывай.
> 2. Чего нет во входных данных — прямо пиши «данные отсутствуют».
> 3. Опирайся на переданный доменный глоссарий ISO 25010, чтобы раскрыть СМЫСЛ просевших характеристик содержательно, а не формально; но не выдумывай числа сверх переданных.
> 4. Пиши деловым русским языком, по существу, без воды и без канцелярских штампов.
> 5. Строго соблюдай запрошенные секции ответа (заголовки секций писать ЗАГЛАВНЫМИ, как в задании).
> 6. НЕ используй названия управленческих методологий и их иноязычные термины — только нейтральную аналитическую лексику.

**Комментарий к правилам.** Правило 2 разрешает модели признать нехватку данных — это снимает давление, заставляющее выдумывать. Правило 3 отделяет содержательное раскрытие смысла от изобретения чисел. Правило 6 убирает наносной управленческий жаргон, который создаёт видимость глубины при её отсутствии.

### 8.2. Шаблоны проходов

| Константа | Назначение |
|-----------|-----------|
| `REASONING_PASS_ANALYSIS` | Проход анализа (этапы E1, E2) |
| `REASONING_PASS_LENSES` | Проход по ролевым линзам (этап E3) |
| `REASONING_PASS_SYNTHESIS` | Синтез мер (этап E5) |
| `REASONING_PASS_CONCLUSION_ONLY` | Только заключение (сокращённый режим) |

### 8.3. Доменный глоссарий

`knowledge.py`, функция `relevant_terms()` — подбирает термины ISO 25010, относящиеся к обсуждаемым характеристикам, и добавляет их в контекст. Это позволяет модели раскрыть смысл характеристики содержательно, не изобретая определений.

### 8.4. Бюджет токенов

Ответ ограничен `LLM_MAX_TOKENS = 320`; для прохода по линзам бюджет рассчитывается динамически: `60 × количество_линз`. Блоки входных данных ограничиваются функцией `_cap_block(block, limit=10)`, чтобы не переполнить окно контекста.

## 9. Три уровня обучения

### 9.1. Уровень A — промпт-инжиниринг

**Что:** системный промпт, шаблоны проходов, глоссарий, параметры генерации.
**Когда применять:** всегда; это основной способ управления поведением модели.
**Стоимость изменения:** минутa — правка `prompts.py` и перезапуск.
**Текущее состояние:** реализовано полностью.

### 9.2. Уровень B — заземление и самообучение

**Что:** «резервный мозг», припоминание прошлых выводов, обратная связь пользователей, база рисков как источник организационного опыта.
**Когда применять:** для накопления опыта конкретной организации.
**Ключевое преимущество:** знания переносимы между моделями.
**Текущее состояние:** реализовано (`brain.py`, `ConclusionFeedback`, база рисков).

Векторная база данных намеренно не используется: для текущего объёма достаточно JSONL-хранилища с токенным сопоставлением, а отсутствие лишней зависимости упрощает развёртывание в закрытом контуре.

### 9.3. Уровень C — дообучение (LoRA/QLoRA)

**Что:** дообучение весов модели на данных организации.
**Когда применять:** когда уровней A и B недостаточно — например, требуется устойчивый стиль формулировок конкретного банка.

**Конвейер:**

```
export_llm_dataset.py / dataset.py
        ↓  выгрузка обучающих примеров
   (профессиональные суждения, утверждённые меры,
    правки пользователей из human_edits())
        ↓
   train_lora.py — обучение QLoRA-адаптера
        ↓
   слияние адаптера с базовой моделью
        ↓
   конвертация в GGUF + квантизация Q4_K_M
        ↓
   файл кладётся в models/llm/ → автоподбор выберет его
```

**Источники обучающих данных:**
- профессиональные суждения экспертов;
- утверждённые меры с обоснованиями;
- исправленные пользователями заключения (`human_edits()`) — наиболее ценный материал;
- доменный корпус (`corpus.jsonl`).

**Текущее состояние:** инструменты подготовлены (`backend/llm/train_lora.py`, `llm_dataset/`), применение — по решению.

## 10. Критерии приёмки

### 10.1. Функциональные

| Критерий | Проверка |
|----------|----------|
| Ответ на русском языке, ≥ 50 символов | Автоматическая проверка |
| Содержит конкретную рекомендацию | Ручная проверка эталонных кейсов |
| Отсутствуют числа, которых не было во входе | Автоматическая проверка grounding |
| Ответ не является эхом входа | Автоматическая проверка `_is_echo()` |
| Соблюдена структура секций | Разбор `_split_sections()` |
| Уровень уверенности соответствует полноте данных | Детерминированный расчёт |

### 10.2. Производительность (CPU)

| Класс модели | Ориентир времени ответа |
|--------------|------------------------|
| 0.5B | до 2 с |
| 9B | до 20 с |
| 14B | до 40 с |

Значения зависят от `LLM_N_THREADS` и оборудования. Для интерактивных сценариев рекомендуется модель до 9B либо перенос слоёв на GPU.

### 10.3. Тестовое покрытие

Тесты в `backend/tests/`: модель-агностичность, сервис, шлюз правил, «мозг», конвейер рассуждения. Тесты выполняются на сверхлёгкой модели, чтобы не требовать мощного оборудования в CI.

## 11. Эксплуатация

### 11.1. Смена модели

1. Положить новый `.gguf` в `models/llm/` (файл станет новейшим по времени).
2. Выполнить `POST /api/v1/reports/llm-reload` — либо перезапустить контейнер бэкенда.
3. Проверить `GET /api/v1/reports/llm-status`.

Пересборка образа не требуется. Каталог моделей подключён томом.

### 11.2. Работа на GPU

Установить `LLM_N_GPU_LAYERS = -1` (все слои на GPU) и использовать `docker-compose.gpu.yml` со сборкой llama.cpp с поддержкой CUDA. Подробности — в [ТЗ-07](./ТЗ_07_Развёртывание_и_Инфраструктура.md).

### 11.3. Работа при отключённой LLM

`LLM_ENABLED = False` — система продолжает работать: расчёты, вердикты движка правил, дашборды и отчёты доступны в полном объёме. Меняется только форма текстовых выводов — они становятся детерминированными.

### 11.4. Диагностика

| Симптом | Вероятная причина | Действие |
|---------|-------------------|----------|
| Выводы всегда детерминированные | Модель не загрузилась | Проверить `llm-status`, наличие файла, объём памяти |
| В журнале предупреждения о выдуманных процентах | Модель слишком слаба для задачи | Перейти на модель большего размера |
| Ответ — перечень характеристик | Вырожденный ответ (эхо) | Аналогично: модель большего размера |
| Медленный ответ | Недостаточно потоков или крупная модель | Увеличить `LLM_N_THREADS` либо перейти на GPU |

## 12. Развитие

| Направление | Состояние | Комментарий |
|-------------|-----------|-------------|
| Векторный поиск (pgvector) | Отложено (T-20) | Текущего механизма припоминания достаточно для имеющегося объёма |
| Кэширование выводов в Redis по `(period_id, hash(metrics))` | Предложено | Снизит нагрузку при повторных открытиях дашборда |
| RAG над методикой МК_8.1 | Предложено | Расширит доменное заземление |
| Ансамбль моделей | Идея | Сопоставление выводов нескольких моделей как индикатор надёжности |
| Дообучение на корпусе организации | Инструменты готовы | Применять при устойчивой потребности в стиле |
