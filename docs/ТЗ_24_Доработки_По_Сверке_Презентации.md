## 1. Метод и легенда

Для каждого утверждения слайда: (1) найден первоисточник в ТЗ; (2) найден код и проверен
фактическим чтением, не по маркерам; (3) определён тип разрыва; (4) там, где ТЗ нет или оно
не описывает поведение, требование **дописано в этом документе** — раздел «ТЗ (дописано)».

**Тип разрыва.**
- **К** — ТЗ есть, код отсутствует или реализует его частично.
- **Т** — ТЗ нет; требование сформулировано здесь.
- **Р** — ТЗ противоречит другому ТЗ или требованию заказчика (БТ); здесь зафиксировано решение.
- **Д** — документация расходится с кодом.
- **Дф** — дефект: код есть, но ведёт себя не так, как требует ТЗ.

**Критичность.**
- **P0** — блокирует пилот «на данных заказчика» (слайды 22, 28) или делает утверждение
  ключевого слайда ложным.
- **P1** — заявленная функция работает частично, небезопасно или методологически неверно.
- **P2** — заявлено, но отсутствует; не на критическом пути пилота.
- **P3** — формулировки, документация, дорожная карта.

**Размер:** `S` ≤ 1 дня · `M` 2–4 дня · `L` 1–2 недели · `XL` > 2 недель.

## 4. ТЗ по задачам

### Блок A. Сбой → рубли (слайды 7, 11, 15, 22)

<a id="dp-01"></a>
### ДП-01. Экономические поля сбоя в API и актуальность стоимости

| | |
|---|---|
| Критичность / размер / тип | **P0** · M · К, Дф |
| Слайды | 7 («цена каждого сбоя»), 11 (формула ущерба), 15 («считается автоматически») |
| Первоисточник | RE-05 (поля карточки), RE-06 (деградация), RE-07 (движок C_ТС); риск-экон. §2.1–2.2 |
| Зависимости | нет; на ней стоят ДП-02, ДП-04, ДП-05, ДП-06 |

**Как сейчас (проверено в коде).**
- Поля экономики есть только в модели `TechIncident` (`backend/app/modules/incidents/models.py:107-127`):
  `incident_type`, `degradation_type`, `downtime_minutes`, `k_impact`, `t_reaction_min`,
  `t_resolution_min`, `t_target_min`, `root_cause_fixed_at`, `labor_l1_hours…l3_hours`,
  `vendor_involved`, `cost_total`.
- **Ни одна схема API их не несёт:** `TechIncidentCreate`, `TechIncidentUpdate`, `TechIncidentOut`,
  `IncidentImportRow` (`incidents/schemas.py:18-105`). На реальных данных экономику сбоя нельзя
  записать даже через API — она появляется только из сидов.
- `cost_total` кэшируется при первом расчёте (`econ/service.py:417`, вызов из
  `risk/event_service.py:249`) и **никогда не сбрасывается**: ни при правке сбоя
  (`incidents/service.py:210-217`), ни при правке ставок и стоимости минуты.
- Хелперы расчёта K деградации (`k_performance_degradation`, `k_functional_degradation`,
  `k_throughput_degradation`, `degradation_counts_as_downtime` — `econ/economics.py:83-121`)
  нигде не вызываются, кроме тестов. K берётся только из ручного `k_impact`.
- `GET /incidents` открыт праву `view.dashboard.incidents` (`incidents/router.py:34-43`), которое есть
  у `EXECUTOR`, а `TechIncidentOut.cost_total` — деньги. Это нарушает инвариант ДЕФ-42/УК-58
  («деньги — только с `view.risk_economics`»). Заведено как **ИБ-47**.

**ТЗ (дописано).**
1. Схемы `TechIncidentCreate`, `TechIncidentUpdate`, `TechIncidentOut` получают поля (camelCase):
   `incidentType` (`DOWNTIME|DEGRADATION`), `degradationType` (`FUNCTIONAL|PERFORMANCE|THROUGHPUT|null`),
   `degradationParam`, `kImpact`, `kImpactSource` (`MANUAL|CALC`), `downtimeMinutes`,
   `tReactionMin`, `tResolutionMin`, `tTargetMin`, `rootCauseFixedAt`, `laborL1Hours`,
   `laborL2Hours`, `laborL3Hours`, `vendorInvolved`, а также поля вторичного ущерба из ДП-05.
2. Новая колонка `degradation_param` (Numeric 8,4) — один параметр на тип деградации:
   `PERFORMANCE` — кратность роста времени отклика (≥ 1); `FUNCTIONAL` — доля веса недоступных
   функций (0…1); `THROUGHPUT` — отношение фактической пропускной способности к требуемой (0…1).
   Новая колонка `k_impact_source` (String 8). Миграция Alembic — следующая свободная.
3. Правило K: если пользователь задал `kImpact` — `MANUAL`; иначе при заданных `degradationType`
   и `degradationParam` K считается хелпером соответствующего типа — `CALC`; для `DOWNTIME` K = 1.
4. Валидация сервиса: `kImpact` ∈ [0; 1]; часы и минуты ≥ 0; `degradationType` обязателен при
   `DEGRADATION` и запрещён при `DOWNTIME`; `tTargetMin ≥ tResolutionMin`, если оба заданы.
   Ошибка — 422 с названием поля по-русски.
5. Актуальность стоимости: в `econ_config` вводится счётчик `econ_refs_version` (int);
   его увеличивают все мутаторы ставок, стоимости минуты БП, связей ИС↔БП, `k_time`, `k_overhead`.
   У сбоя — колонка `cost_refs_version`. Стоимость пересчитывается, если `cost_total IS NULL` или
   `cost_refs_version ≠ econ_refs_version`. `update()` обнуляет `cost_total` при изменении любого
   входа стоимости. Так `econ` остаётся нижним слоем и не импортирует `incidents`.
6. **Деньги по праву (ИБ-47):** `costTotal` и поля вторичного ущерба в `GET /incidents`,
   `GET /incidents/{id}` заполняются только при праве `view.risk_economics`; иначе `null`. Та же
   проверка — в новом `GET /incidents/{id}/cost`.
7. Новый эндпоинт `GET /incidents/{id}/cost` (право `view.risk_economics`): раскладка
   `recovery` (по линиям: часы, ставка, K_время, источник ставки), `downtime` (по БП: минуты,
   ₽/мин, K, доля), `secondary`, `reputational` (справочно), `total`, `countsAsDowntime`
   (правило §2.2 через `degradation_counts_as_downtime`) и `gaps` — человекочитаемые причины
   нулевых компонент: «нет ставки L2 для ИС …», «ИС не связана ни с одним БП», «не задана
   длительность простоя». Для раскладки движок получает функцию, возвращающую компоненты,
   а не только сумму (`econ/economics.py:68`).

### ДП-12. Возврат эффекта в оценку: фактические ΔALE и ΔScore

| | |
|---|---|
| Критичность / размер / тип | **P1** · M · К, Т |
| Слайды | 8 («Δ балла и Δ ₽ — эффект возвращается в оценку»), 16 |
| Первоисточник | риск-экон. §0 (цепочка «⟲ обратно к подхарактеристике»), §4.2 (устраняющая мера растит Score, компенсирующая — нет), §7.1 (результативность), §7.2 (ΔALE — по оценке, зафиксированной до меры) |
| Зависимости | ДП-07, ДП-06; решение В-ДП-9 |

**Как сейчас.** `delta_score_confirmed` вводит аудитор вручную (`nonconformity/router.py:138`), и
значение **нигде не используется**. ALE после верификации не пересчитывается; ALE до решения не
фиксируется; снимков ALE по периодам нет (`econ/portfolio_trend_service.py:13-16` честно
возвращает пустой ряд).

**ТЗ (дописано).**
1. **Фиксация «до».** При решении по несоответствию сохраняется `ale_at_decision` (ALE
   связанного события на момент решения) — защита §7.2 от завышения исходной оценки.
2. **Окно наблюдения.** При «Верифицировано» у рисковых событий, привязанных к несоответствию и
   к его мере, выставляется `mitigation_applied_at = executed_at`. Параметр
   `econ_config.effect_observation_months` (по умолчанию 6, В-ДП-9).
3. **Фактический ΔALE.** Ночная задача: для событий, у которых окно истекло, ARO считается
   только по сбоям после `mitigation_applied_at`, ALE пересчитывается, у несоответствия
   записываются `ale_after`, `delta_ale_actual = ale_at_decision − ale_after`,
   `effect_confirmed_at`. До истечения окна в карточке — «эффект наблюдается до {дата}».
4. **Фактический ΔScore.** При верификации устраняющей меры сервер предлагает
   `delta_score_suggested` = X подхарактеристики этой ИС в первом завершённом периоде после
   `executed_at` минус X в последнем периоде до решения. Нет периода «после» — «ожидает оценки
   следующего периода», предложение появится ночной задачей. Аудитор подтверждает или правит
   (`delta_score_confirmed`), правка требует комментария. Для компенсирующей меры ΔScore не
   предлагается — пометка «компенсирующая мера не меняет балл (§4.2)».
5. **Потребители.** Метрики руководителей (`econ/manager_metrics_service.py`): «результативность»
   = доля верифицированных с `delta_score_confirmed > 0` или `delta_ale_actual > 0`;
   «ΔALE под управлением» — по `delta_ale_actual`, а где его ещё нет — по плану с пометкой «план».

**Критерии приёмки.** После верификации устраняющей меры и завершения следующего периода
в карточке появляется предложенный ΔScore; через окно наблюдения — фактический ΔALE; метрики
руководителей различают план и факт.

**Тесты.** pytest: фиксация `ale_at_decision`, расчёт ARO после даты применения меры,
предложение ΔScore при наличии и отсутствии периода «после», компенсирующая мера.

**ТЗ (дописано).**
1. **Модель данных.**
   - `checklist_templates`: название, версия, область (классы ИС), статус (черновик/действует/архив).
   - `checklist_items`: шаблон, характеристика, подхарактеристика, вопрос, тип ответа
     (`YES_NO|SCALE_0_4|NUMBER|TEXT`), обязательность вложения, тип доказательства (`D|E`),
     связанная метрика (`metric_id`) и правило перевода ответа в A/B (`YES_NO`: да → A=1,B=1;
     нет → A=0,B=1; `SCALE_0_4`: A=ответ, B=4; `NUMBER`: A=ответ, B — из поля пункта).

     статус проверки `NOT_SAMPLED|SAMPLED|VERIFIED|REJECTED`, проверяющий.
2. **Права** (каталог +3): `checklist.manage` (шаблоны и рассылка — `QUALITY_MANAGER`),
   `checklist.answer` (заполнение своих назначений — `EXECUTOR`, `QUALITY_MANAGER`,
   `TEST_ANALYST`), проверка — существующее `assessment.review`.
3. **Процесс.** Менеджер по качеству рассылает шаблон по ИС периода → владелец получает задачу в
   «Моих задачах» и уведомление (ДП-31) → отвечает, прикладывает документы → «Отправить» →
   сервер формирует выборку: **все** ответы по подхарактеристикам ИС Mission Critical со
   значением ниже порога плюс случайные 20 % остальных (`checklist_sample_share`, В-ДП-10) →
   аналитик проверяет только выборку → «Принять» переносит ответы в значения оценки
   (`data_source = CHECKLIST`, тип доказательства из пункта) или «Вернуть» с комментариями.
4. **Приоритет доказательств** (§4.1): если у подхарактеристики есть значение типа A/B, ответ
   чек-листа его не перезаписывает, а сохраняется как дополнительное свидетельство.
5. **Продуктовая метрика** (§6.2): время от рассылки до принятия и человеко-часы аналитика на
   проверку — по ИС и классу, в отчёт менеджера по качеству.
6. **Вложения:** хранение как у загрузок `dataio`; лимит 10 МБ; до промышленной эксплуатации —
   проверка антивирусом (ИБ-21).

**Критерии приёмки.** Владелец ИС без доступа к оценкам других систем заполняет чек-лист своей
ИС; аналитик проверяет только выборку; после принятия значения появляются в периоде оценки с
типом доказательства.

**Тесты.** pytest: переходы статусов, правило выборки, перевод ответов в A/B, изоляция чужих ИС.
