**Р-6 — как именно это работает.** Веса подхарактеристик из файла применяются **одинаково ко всем
ИС**: балл отдельной ИС считается по единому весовому вектору. Критичность влияет **на следующем
уровне** — с каким весом балл этой ИС входит в интегральную цифру по ландшафту:

```
Балл_ИС      = Σ(вес_подхар × X_подхар) / 100        ← веса из файла, одни для всех ИС
Балл_портфеля = Σ(вес_критичности_ИС × Балл_ИС) / Σ(вес_критичности_ИС)
```

Это разводит два разных вопроса, которые в текущем коде смешаны: «что важно **внутри** системы»
(отвечает файл) и «какая система важнее **для бизнеса**» (отвечает критичность). Дозапрашивать
у заказчика ничего не нужно — файл применяется как есть.

**Открытый подвопрос В-6а:** числовые веса классов критичности для второй формулы.
Предлагаю Mission Critical 3 / Business Critical 2 / Support 1 — простая и объяснимая шкала.
Требует подтверждения.

**Р-7 — существенная оговорка.** Сбор бенчмарков из открытых источников означает, что качество
цифр ограничено качеством публичных данных: обзоры зарплат и отраслевая статистика различаются
методикой, годом и регионом. Прежде чем закладывать числа в расчёты, **перечень источников
выносится на отдельное согласование** (В-30а), а в интерфейсе у каждого бенчмарка показывается
источник и дата. Механика при этом строится независимо от наполнения, поэтому пункты 9 и 10
не блокируют разработку.

**Решение:** ключ сшивки — пара **(характеристика, английский термин ISO)**, а не русское имя.
Английская колонка есть в обоих файлах и однозначна. Реализуется как справочник соответствия
с тестом-стражем на полноту (31 из 31), по образцу существующего `canonical_characteristic`.

### Р-3. Веса уже написаны, но намеренно отключены от Score

`backend/app/modules/econ/weights_service.py` — гибридные веса по классу критичности уже
реализованы (профиль по классу ИС + фактика по доле в ALE, α по достаточности данных).
Но в шапке модуля, строки 19-20, зафиксировано:

> Отдаётся как СОВЕТЧИК: `GET /econ/weights?criticality=` показывает объяснённые веса,
> но интегральный Score по ним НЕ пересчитывается **(решение заказчика)** — существующие оценки целы.

Пункт 2 отменяет это решение. Это нормально, но надо зафиксировать явно, потому что
пересчёт меняет **все** исторические цифры на всех дашбордах.

**Решение (15.08.2026): пересчитываем всю историю.** Все прошлые периоды пересчитываются по
весам из файла. Динамика «период к периоду» остаётся сравнимой, разрыва методики в графиках нет.

Обязательные условия пересчёта:

- **версия весов хранится вместе с оценкой** — иначе откат невозможен и нельзя объяснить,
  почему цифра за прошлый квартал изменилась;
- **отчёт «до / после»** по каждому периоду и каждой ИС формируется до применения и сохраняется;
- **пересчёт обратим** — старое значение не затирается, а остаётся доступным как предыдущая версия.

⚠️ Если какие-то цифры прошлых периодов уже ушли во внешние отчёты руководству, их значения
изменятся. Нужен ответ: были ли такие выгрузки и требуется ли сопроводительная справка о смене
методики (**В-3а**).

### Р-4. Нет сущности «предприятие» — решено профилем установки

В `backend/app/modules/` нет ни `Organization`, ни `Company`, ни поля «размер предприятия».
Система неявно однопользовательская по организации: одна установка = одна компания.

**Решение (15.08.2026): одно предприятие — профиль установки.** Вводится не справочник
организаций, а **профиль предприятия** — единственная запись с атрибутами: размер, отрасль,
численность, регион. Мультиарендность не делается; права доступа и фильтрация не затрагиваются.

Размер предприятия работает как **параметр подстановки** для среднерыночных ставок (п. 10)
и бенчмарков по бизнес-процессам (п. 9), а не как измерение данных. Это минимальный по объёму
вариант, снимающий блокировку пунктов 8, 9, 10 без нового фундамента.

**В-28 остаётся открытым:** критерий размера — 209-ФЗ (микро / малое / среднее / крупное),
по выручке, по численности или своя шкала.

**Строки 14 и 16 выделены намеренно.** Обе называются «Доступность», веса различаются в 10 раз
(0,5 против 5). Сшивка по русскому имени их перепутает и тихо исказит балл надёжности —
поэтому ключ только английский.

**Инварианты, которые закрепляются тестом-стражем:**

1. Σ весов характеристик = 100;
2. Σ весов подхарактеристик = 100;
3. для каждой характеристики Σ весов её подхарактеристик = вес характеристики (8 из 8);
4. справочник покрывает ровно 31 пару `QUALITY_MODEL`, без сирот с обеих сторон.

**Ключевое следствие для формулы.** Вес подхарактеристики **уже включает** вес своей
характеристики (5 + 3 + 2 = 10 = вес «Функциональной пригодности»). Умножать на вес
характеристики второй раз **нельзя** — это даст двойной учёт. Правильная свёртка одноуровневая:

```
Балл_ИС = Σ(вес_подхар × X_подхар) / Σ(вес_подхар применённых)
```

Знаменатель — сумма весов **фактически измеренных** подхарактеристик, а не всегда 100:
при `unmeasurable` веса перенормируются на измеренные (см. В-5).

`weights_service.py:55-59` (20/20/20/10/10/10/5/5 против 22/20/16/14/10/8/6/4), но не совпадают
с ним и заметно расходятся с профилями `BUSINESS_CRITICAL` и `SUPPORT`. По решению Р-6 файл
заменяет **все три** профиля как весовой вектор подхарактеристик; распределение внутри
характеристики теперь неравномерное (в коде было поровну) — это содержательное уточнение,
которого в системе не было.

4. **Признак `[адаптировано]`** — маркер «официальной меры в 25023:2016 ещё нет». Важен для

### Пункт 1. Почему средняя цифра качества ИТ-ландшафта такая, и сколько — хорошо или плохо

**Коды:** УК-01, УК-02, УК-03

#### Как считается сейчас

`backend/app/modules/assessment/router.py:247`:

```python
"globalHealthScore": round(sum(measured_x) / len(measured_x), 4) if measured_x else 0.0
```

`measured_x` — плоский список **всех** значений `calculated_x` по всем подхарактеристикам всех
активных ИС за последний период каждой ИС. То есть цифра — это невзвешенное среднее
арифметическое по всем измеренным ячейкам теплокарты.

#### Почему цифра именно такая — шесть причин, ни одна из которых не видна пользователю

1. **Все подхарактеристики равны.** «Конфиденциальность» mission-critical ERP весит столько же,
   сколько «Тестируемость» вспомогательной вики.
2. **Все ИС равны.** Класс критичности в расчёт не входит вообще.
3. **Скрытый вес по полноте заполнения.** ИС с 31 заполненной метрикой даёт в среднее 31
   слагаемое, ИС с 5 — пять. Чем лучше документирована система, тем сильнее она тянет
   общую цифру. Это вес «по усердию аналитика», а не по важности.
4. **`unmeasurable` молча выпадает.** Не ноль, а исключение из базы. ИС, где защищённость
   измерить нельзя, выглядит так же, как ИС с идеальной защищённостью.
5. **Две разные «средние» цифры на одном экране.** `globalHealthScore` — среднее по значениям
   (стр. 247). А балл ИС (`sys_meta[...]["score"]`, стр. 184) — среднее средних по
   характеристикам. На одних и тех же данных это **разные числа**, и в UI не сказано, какое где.
6. **Нет базы сравнения.** Пороги `map_to_level` (0.81/0.61/0.41/0.21) применяются к отдельной
   метрике, а к интегральной цифре не объявлены. На экране ничего не отвечает на вопрос
   «0.62 — это хорошо?».

#### Что делаем

**УК-01. Панель «Из чего сложилась цифра».** Раскрытие интегрального Score:
вклад каждой характеристики (вес × балл), топ-5 подхарактеристик, тянущих вниз, топ-5 ИС по
абсолютному вкладу, число измеримых / неизмеримых / незаполненных ячеек и явная строка
«база расчёта: N значений из M возможных».

**УК-02. Единая цифра.** Убрать расхождение (5): один способ свёртки на всех экранах.
Переход на трёхуровневую свёртку по §1 п.1 — среднее становится взвешенным и
детерминированным на всех уровнях.

**УК-03. Шкала прочтения.** Объявить, как читать цифру: цветовая полоса с порогами,
подпись уровня словами, дельта к предыдущему периоду, отметка целевого значения.

#### Критерии приёмки

- По клику на интегральную цифру открывается разложение, сумма вкладов сходится с цифрой
  (расхождение ≤ 0.5 п.п.).
- На экране видно, сколько ячеек участвовало в расчёте и сколько выпало как неизмеримые.
- Цифра на дашборде CEO, на теплокарте и в Excel-отчёте совпадает.
- Рядом с цифрой — уровень словами и дельта к прошлому периоду.

#### ❓ Вопросы

- **В-5.** Что делать с `unmeasurable`: исключать из базы (как сейчас), считать нулём или
  показывать двумя цифрами — «Score по измеримым» и «покрытие измерением, %»?
  *Рекомендация: третье — одна цифра не может нести оба смысла.*

  (б) цель, заданная компанией на год; (в) прошлый период; (г) отраслевой бенчмарк

### Пункт 2. Настроить веса относительно критичности (по приложенному файлу)

**Коды:** УК-04, УК-05, УК-06, УК-07

#### Как сейчас

`weights_service.py` уже считает вес каждой подхарактеристики:

```
α(i) = max(α_min, N₀/(N₀+N(i)))
вес(i) = α(i)·профиль(i, класс ИС) + (1−α(i))·фактика(i, доля в ALE)
```

Профили заданы на уровне характеристик и делятся **поровну** между подхарактеристиками
(`weights_service.py:93-104`). Внутри характеристики различий нет: «Конфиденциальность» и
«Подотчётность» весят одинаково.

Результат отдаётся как советчик и в Score не входит (Р-3).

#### Что делаем

**УК-04. Трёхуровневая свёртка по схеме файла.** Ввести явные `v` (метрика → подхарактеристика),
`w` (подхарактеристика → характеристика), `u` (характеристика → интегральный Q), с
нормировкой Σ=1 на каждом уровне и валидацией при сохранении.

**УК-05. Веса на уровне подхарактеристик.** Отказаться от деления поровну: задать `w`
индивидуально, минимум для трёх профилей критичности.

**УК-06. Применение к Score.** Перевести веса из режима «советчик» в режим расчёта.
Версионирование набора весов: у каждого периода — ссылка на версию весов, по которой он посчитан.

**УК-07. Редактор весов.** Экран администратора: правка `v`/`w`/`u` по профилям, предпросмотр
«как изменится Score портфеля», история изменений, кто и когда менял.

#### Критерии приёмки

- Σ весов = 1 на каждом уровне, при нарушении — отказ сохранения с указанием строки.
- Смена класса критичности ИС меняет её Score предсказуемо и объяснимо в панели УК-01.
- У каждой сохранённой оценки видно, по какой версии весов она посчитана.
- Старые периоды не «переписываются» задним числом без явного действия администратора.

#### ❓ Вопросы

- **В-1 (блокирующий).** Источник числовых весов. Варианты:
  - **(а)** взять текущие `PROFILES` из `weights_service.py:53-72` как утверждённую базу и

### Пункт 7. Связь риска и мер в деньгах

**Коды:** УК-19, УК-20

#### Как сейчас

Считающая часть **есть** и она сильная: `economics.py` — `annual_loss_expectancy`, `rosi`,
`sle_from_incidents`, коэффициенты деградации; `Proposal` хранит `capex`, `opex_per_year`,
`implementation_months`, `delta_ale_cash/deferred/capacity`, `rosi`, `recommended_verdict`;
`RiskEventMeasure.ale_reduction_share` умеет учитывать перекрытие мер.

Чего нет: **сквозного управленческого представления** «риск стоит X ₽ → мера стоит Y ₽ →
снимает Z ₽ → окупается за T». Цифры разложены по разным экранам.

#### Что делаем

**УК-19. Экран «Риск → мера → эффект».** Одна таблица сквозной цепочки: риск, ALE, меры,
CAPEX/OPEX, ΔALE, ROSI, срок окупаемости, вердикт. Разворачивается в обе стороны:
от риска к мерам и от меры к рискам (одна мера закрывает несколько рисков).

**УК-20. Портфельный итог.** «Всего под риском ₽ / покрыто мерами ₽ / остаточный риск ₽ /
требуемые вложения ₽ / ожидаемый эффект ₽» с раскрытием до конкретных карточек.

#### Критерии приёмки

- Σ ΔALE по мерам не превышает ALE рисков, которые они закрывают (перекрытие учтено).
- Меняем `ale_reduction_share` — портфельный итог пересчитывается, расхождений нет.
- Каждая цифра раскрывается до исходных карточек за ≤ 2 клика.

### Пункт 9. По бизнес-процессам — понять среднее относительно рынка

**Коды:** УК-23, УК-24

#### Как сейчас

`BusinessProcess` + `BusinessProcessCost` с тремя методами расчёта `C_мин` (ресурсный,
транзакционный, экспертный) — `econ/models.py:40-96`. Всё считается **по своим данным**.
Сравнения с рынком нет ни в каком виде.

#### Существенное ограничение

«Среднее относительно рынка» требует внешних данных, которых у системы нет и которые она
не может получить сама. Это не задача разработки — это задача **источника данных**.
Без ответа на В-30 пункт не реализуем: мы можем построить механику сравнения, но подставлять
в неё будет нечего.

#### Что делаем

**УК-23. Справочник бенчмарков.** Эталонные значения по типу процесса × отрасль × размер
предприятия: стоимость минуты простоя, длительность, стоимость выполнения. Источник и дата
актуальности — обязательные поля (иначе цифре нельзя верить).

**УК-24. Сравнение «мы / рынок».** На карточке процесса — своё значение, эталон, отклонение
в % и словами («дороже рынка на 40%»), с явной пометкой источника эталона.

#### Критерии приёмки

- Ни один бенчмарк не отображается без источника и даты.
- Отсутствие эталона для процесса показывается как «нет данных для сравнения», а не как 0%.
- Сравнение учитывает размер предприятия (пункт 8) и отрасль.

### Пункт 13. Критичность и количество мер на исполнителях с учётом весов

**Коды:** УК-31, УК-32, УК-33

#### Как сейчас

Меры назначаются на `Proposal.owner` — строку. Ни трудоёмкости, ни сложности, ни веса
у меры нет. `implementation_months` есть, но это **длительность внедрения**, а не
трудозатраты и не сложность. Посчитать «15 лёгких против 5 сложных» сейчас не из чего.

`EmployeeEffectivenessCard.tsx` и `manager_metrics_service.py` считают эффективность по
числу и просрочкам — то есть по количеству, без учёта тяжести.

#### Что делаем

**УК-31. Вес меры.** Ввести оценку тяжести меры, складывающуюся из:
- веса подхарактеристики, на которую мера направлена (пункт 2);
- класса критичности ИС;
- трудоёмкости в часах — **проставляет исполнитель вручную** при переводе меры «в работу»
  (решение по В-41, см. вопросы ниже); поле необязательно на более ранних статусах;
- (опционально) денежного масштаба — ΔALE и CAPEX.

**УК-32. Нагрузка на исполнителя.** Показатель загрузки = Σ весов открытых мер исполнителя,
с разложением: сколько мер, какой суммарный вес, сколько просрочено, сколько по критичным ИС.
Ровно то, что просит формулировка «на одном 15 лёгких, на другом 5 сложных».

**УК-33. Балансировка.** Экран распределения: кто перегружен, кто свободен, рекомендация
по перераспределению; предупреждение при назначении меры перегруженному исполнителю.

#### Критерии приёмки

- Два исполнителя с одинаковым числом мер, но разной тяжестью, имеют разную загрузку —
  и разница объяснима на экране.
- Загрузка пересчитывается при закрытии/переназначении меры.
- Видно, из чего сложился вес конкретной меры.
- Меры без проставленной трудоёмкости (ещё не взяты «в работу») показаны в загрузке отдельным
  счётчиком «без оценки часов» — не пропадают и не считаются нулевыми молча.

#### ❓ Вопросы

- ~~В-41~~ **Закрыто (15.08.2026).** Трудоёмкость в часах проставляет **исполнитель вручную**
  при переводе меры в статус «в работу» — поле на карточке, не отдельный справочник. Самый
  быстрый старт: не требует расширения `measure_catalog.py` и не зависит от согласования
  нормативов по типам мер. Ограничение принимается осознанно: пока мера не взята в работу,
  вес по трудоёмкости не участвует в загрузке — УК-32 показывает это явно (см. критерии),
  а не подставляет 0 молча.
- **В-42.** Что считать нормой загрузки? Без норматива «перегружен» не определить.
  Норматив на роль, на человека или от размера предприятия (пункт 8)?
- **В-43.** Учитывать ли занятость исполнителя вне АСОК (проекты, отпуска)? Если да —
  нужен источник (пункт 6, интеграция с менеджером задач).
- **В-44.** Загрузка считается по календарю (меры, попадающие в период) или по остатку
  (все открытые)? Это разные цифры.

### Пункт 14. Наполнение мер и карточек на языке топ-менеджмента

**Коды:** УК-34, УК-35

#### Как сейчас

Карточки говорят языком стандарта и инженера: «Функциональная целесообразность»,
«X = 1 − A/B (INVERSE)», «Узнаваемость уместности». LLM генерирует `rationale` и
`expectation` (`governance/models.py:62-63`), но целевая аудитория текста нигде не задана —
промпт не различает читателя-инженера и читателя-CEO.

Есть готовый актив: колонка «Описание (что показывает; артефакты и данные подтверждения)»
из приложенного файла — управленческие формулировки по всем подхарактеристикам.

#### Принципы управленческого языка — выведены анализом, не запрошены отдельным файлом

Заказчик явно указал (15.08.2026): готовых эталонов «как надо / как не надо» не будет —
задача сформулировать принципы самостоятельно, через анализ проблематики, «без формул, без
переписываний вслепую». Ниже — восемь принципов и разбор того, почему это должно быть именно
анализом конкретного случая, а не механической заменой терминов.

1. **Вывод — первым предложением** (принцип BLUF / пирамиды Минто). Топ понимает суть, не
   дочитывая до конца: что случилось и чем грозит.
2. **Деньги и срок — числом, не оценочным словом.** Не «существенный риск», а «₽3,1 млн/год»;
   не «в ближайшее время», а дата или «3 недели».
3. **Причина — в терминах бизнес-последствия, не технической природы дефекта.** Не
   «недостаточное покрытие тестами API», а «риск простоя платёжного сервиса до N часов
   при следующем релизе».
4. **Действие — глагол + срок + ответственный**, а не описание процесса.
5. **Один тезис — одна карточка.** Мера, закрывающая несколько проблем, — списком по
   приоритету, не слитным абзацем.
6. **Сравнение вместо голого числа.** «Хуже среднего по отрасли на 15 п.п.» информативнее,
   чем «62%» само по себе (раскрывается полностью, когда появятся бенчмарки п. 9–10).
7. **Жёсткий лимит длины** — не более 60–80 слов на описательный блок. Это управленческое
   чтение, а не отчёт.
8. **Явный запрет:** без формул расчёта, без DIRECT/INVERSE, без служебных терминов
   стандарта — они остаются в техническом режиме за переключателем.

**Разбор на реальных данных, а не абстрактный пример.** Обе строки взяты из уже существующего
каталога — не придуманы для документа (`backend/app/modules/econ/measure_catalog.py:131,153`).
Цифры условны по форме, в системе подставляются из фактических данных карточки (ALE, SLA, срок,
ответственный из `risk_events`/`proposals`):

| Связка из каталога | Как есть сегодня (технический вывод) | Как надо (по восьми принципам) |
|---|---|---|
| Надёжность → Доступность (uptime); риск «Недостижение SLA доступности» | «Подхарактеристика: Доступность (uptime). X = A/B; A — время доступности; B — общее плановое время. X = 0,942.» | «Платёжный шлюз простаивал 42 часа за квартал — на 5,3 п.п. ниже согласованного SLA (99,5%), это ≈ 3,1 млн ₽ упущенной выручки. Причина — единая точка отказа в балансировщике. Решение: резервирование N+1, 3 недели, отв. [ФИО]. Результат: SLA восстановлен, риск повторения исключён.» |
| Защищённость → Конфиденциальность; риск «Утечка персональных данных → 152-ФЗ и репутация» | «Подхарактеристика: Конфиденциальность. X = A/B; A — объекты с корректным разграничением доступа; B — всего объектов, требующих защиты. X = 0,61.» | «39% хранилищ персональных данных клиентов без разграничения доступа — при инциденте это основание для санкций по 152-ФЗ. Решение: шифрование + ролевой доступ по минимальным привилегиям, 6 недель, отв. [ФИО]. Результат: канал утечки закрыт, готовность к проверке подтверждена.» |

Правая колонка использует данные **конкретного случая** — какая именно ИС, сколько именно
часов, кто отвечает. Их нет и не может быть в статичном «Описании» из файла весов: та колонка
отвечает на вопрос «что вообще означает эта подхарактеристика», это словарь термина, а не
готовый текст карточки. Подставить его как есть в карточку — и есть то самое слепое
переписывание, которого просили избежать.

#### Что делаем

**УК-34. Управленческий слой номенклатуры** (уточнена роль, объём не меняется). Описания из
файла весов подключаются как словарь ЗНАЧЕНИЯ термина — контекст для генерации, а не готовый
текст карточки. Переключатель языка интерфейса «технический / управленческий».

**УК-35. Генерация через анализ конкретной карточки.** Промпт LLM перестраивается вокруг
восьми принципов выше и структуры «что не так → чем грозит в деньгах и сроках → что
предлагается → сколько стоит → что изменится и когда → кто отвечает», заполняемой из
фактических данных карточки, а не из статического текста файла. Встраивается в существующий
пайплайн рассуждения (BL-009 — `personas/decisions/principles/pipeline/selfcheck`), не
отдельным механизмом.

**УК-35а (новая). Тест-страж формата** — по образцу уже работающего `_FORBIDDEN_TERMS`
(`backend/tests/test_reasoning.py:352`, запрет терминологии Toyota в выводе LLM):

- запрещены в управленческом режиме фрагменты `"X ="`, `"A/B"`, `"DIRECT"`, `"INVERSE"`,
  `"подхарактеристика"`;
- обязательны: денежная сумма или % изменения, срок (дата или «N недель/дней»), ответственный;
- лимит длины описательного блока — 80 слов.

#### Критерии приёмки

- В управленческом режиме на экране нет формул, аббревиатур стандарта и слов
  DIRECT/INVERSE — вместо них следствия для бизнеса; проверяется тестом УК-35а, не только
  вычиткой.
- Каждая карточка содержит: причину в бизнес-терминах, сумму/срок, действие с ответственным
  и сроком.
- Каждое утверждение в карточке подкреплено ссылкой на данные (артефакт подтверждения).
- Технический режим сохраняет полную детализацию — ничего не удаляется, только скрывается.

### Пункт 15. Эффекты в разрезе сроков; везде отражать временные рамки

**Коды:** УК-36, УК-37

#### Как сейчас — техническая проблема в основании

(`TaskPlanDashboard.tsx:142`: если дата не разобралась — «+30 дней»).

По эффектам: `implementation_months` (лаг внедрения) и `delta_ale_*` (годовой эффект) есть,
но эффект нигде не разложен по времени — не видно, когда он начнётся и как накопится.

#### Что делаем

**УК-36. Даты как даты.** Перевести `due_date` в тип даты с миграцией существующих строк,
единый формат отображения, единый разбор. Это предусловие для пунктов 12 и 16.

**УК-37. Эффект во времени.** По каждой мере — горизонт: дата старта, лаг внедрения,
дата выхода на эффект, накопленный эффект по кварталам, точка окупаемости. Портфельно —
кривая «когда придут деньги». На всех карточках — явные временные рамки: «за какой период»,
«на какую дату», «эффект в течение N месяцев».

#### Критерии приёмки

- Ни один срок и ни один эффект не отображается без указания периода/даты.
- Точка окупаемости считается с учётом лага внедрения, а не с даты создания карточки.
- Сортировка по датам корректна во всех таблицах.
- Миграция дат не теряет ни одной записи; неразобранные значения помечены и вынесены в отчёт.

### Пункт 16. Переписывание меры под исполнителя и перенос на Гант из карточки

**Коды:** УК-38

#### Как сейчас

Диаграмма Ганта есть (`TaskPlanDashboard.tsx:257+`), строится по `Proposal` со сроками.
Кнопки «отправить на Гант» из карточки меры нет; связь односторонняя и неявная — мера
попадает на диаграмму, только если у неё оказался разобранный `dueDate`.
Переформулирования меры под исполнителя нет: тексты `rationale`/`expectation` пишутся
для согласующего, а не для того, кто будет делать.

#### Что делаем

**УК-38. Кнопка «В работу» на карточке меры.** По нажатию:
1. LLM переписывает меру под исполнителя: из «что не так и почему важно» в
   «что конкретно сделать» — шаги, критерий готовности, требуемые доступы;
2. открывается форма назначения: исполнитель, срок, трудоёмкость (пункт 13),
   предупреждение о перегрузке;
3. мера появляется на диаграмме Ганта — как внутренняя запись АСОК (см. решение по п. 6:
   внешний менеджер задач пока не подключаем, поле `suz_link` остаётся ручной ссылкой);
4. если в будущем появится интеграция через `TaskSyncPort` (пункт 6) — тот же шаг создаст
   задачу во внешней системе автоматически, без изменений в этом сценарии.

Управленческая формулировка при этом **не затирается**: сохраняются обе версии —
для топа (пункт 14) и для исполнителя.

#### Критерии приёмки

- Переход из карточки на Гант — одно действие, без ручного повторного ввода данных.
- Обе формулировки доступны на карточке и видно, кто/когда сформировал исполнительскую.
- Исполнитель видит задачу в своём разделе (`AssigneeTasksPage.tsx`) сразу после назначения.
- Недоступность LLM не блокирует назначение — форма открывается с исходным текстом.
