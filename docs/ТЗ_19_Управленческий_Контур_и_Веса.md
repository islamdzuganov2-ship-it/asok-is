**Р-6 — как именно это работает.** Веса подхарактеристик из файла применяются **одинаково ко всем
ИС**: балл отдельной ИС считается по единому весовому вектору. Критичность влияет **на следующем
уровне** — с каким весом балл этой ИС входит в интегральную цифру по ландшафту:

```
Балл_ИС      = Σ(вес_подхар × X_подхар) / 100        ← веса из файла, одни для всех ИС
Балл_портфеля = Σ(вес_критичности_ИС × Балл_ИС) / Σ(вес_критичности_ИС)
```

Это разводит два разных вопроса, которые в текущем коде смешаны: «что важно **внутри** системы»
(отвечает файл) и «какая система важнее **для бизнеса**» (отвечает критичность). Дозапрашивать
у заказчика ничего не нужно — файл применяется как есть.

### Р-5. 16 названий расходятся: файл — дословный ГОСТ, код — обиходные ⚠️ НОВОЕ

Структурно модели идентичны, но подписи разные — файл использует дословную терминологию
таблицы 4 ГОСТ, код — обиходные формулировки:

| В коде | В файле весов | Англ. ISO (ключ сшивки) |
|---|---|---|
| Производительность *(характеристика)* | Уровень производительности | Performance efficiency |
| Ёмкость (пропускная способность) | Потенциальные возможности | Capacity |
| Интероперабельность | Функциональная совместимость | Interoperability |
| Узнаваемость уместности | Определимость пригодности | Appropriateness recognizability |
| Зрелость (плотность дефектов) | Завершённость | Maturity |
| Доступность (uptime) | Готовность | Availability |
| Неотказуемость | Неподдельность | Non-repudiation |
| Подотчётность (аудит) | Отслеживаемость | Accountability |
| Аутентичность | Подлинность | Authenticity |
| Повторное использование | Возможность многократного использования | Reusability |
| Заменяемость | Взаимозаменяемость | Replaceability |
| *+ 5 расхождений в скобочных уточнениях* | | |

**Ловушка, которую нельзя пропустить.** Слово «Доступность» в коде встречается **дважды**:
`Доступность (accessibility)` в «Удобстве использования» (вес **0,5**) и `Доступность (uptime)`
в «Надёжности» (вес **5**, в файле — «Готовность»). Разница в весе — **десятикратная**.
Сшивка по одному названию подхарактеристики их перепутает.

**Решение:** ключ сшивки — пара **(характеристика, английский термин ISO)**, а не русское имя.
Английская колонка есть в обоих файлах и однозначна. Реализуется как справочник соответствия
с тестом-стражем на полноту (31 из 31), по образцу существующего `canonical_characteristic`.

### Р-3. Веса уже написаны, но намеренно отключены от Score

`backend/app/modules/econ/weights_service.py` — гибридные веса по классу критичности уже
реализованы (профиль по классу ИС + фактика по доле в ALE, α по достаточности данных).
Но в шапке модуля, строки 19-20, зафиксировано:

> Отдаётся как СОВЕТЧИК: `GET /econ/weights?criticality=` показывает объяснённые веса,
> но интегральный Score по ним НЕ пересчитывается **(решение заказчика)** — существующие оценки целы.

Пункт 2 отменяет это решение. Это нормально, но надо зафиксировать явно, потому что
пересчёт меняет **все** исторические цифры на всех дашбордах.

**Решение (15.08.2026): пересчитываем всю историю.** Все прошлые периоды пересчитываются по
весам из файла. Динамика «период к периоду» остаётся сравнимой, разрыва методики в графиках нет.

Обязательные условия пересчёта:

- **версия весов хранится вместе с оценкой** — иначе откат невозможен и нельзя объяснить,
  почему цифра за прошлый квартал изменилась;
- **отчёт «до / после»** по каждому периоду и каждой ИС формируется до применения и сохраняется;
- **пересчёт обратим** — старое значение не затирается, а остаётся доступным как предыдущая версия.

⚠️ Если какие-то цифры прошлых периодов уже ушли во внешние отчёты руководству, их значения
изменятся. Нужен ответ: были ли такие выгрузки и требуется ли сопроводительная справка о смене
методики (**В-3а**).

### Р-4. Нет сущности «предприятие» — решено профилем установки

В `backend/app/modules/` нет ни `Organization`, ни `Company`, ни поля «размер предприятия».
Система неявно однопользовательская по организации: одна установка = одна компания.

**Решение (15.08.2026): одно предприятие — профиль установки.** Вводится не справочник
организаций, а **профиль предприятия** — единственная запись с атрибутами: размер, отрасль,
численность, регион. Мультиарендность не делается; права доступа и фильтрация не затрагиваются.

Размер предприятия работает как **параметр подстановки** для среднерыночных ставок (п. 10)
и бенчмарков по бизнес-процессам (п. 9), а не как измерение данных. Это минимальный по объёму
вариант, снимающий блокировку пунктов 8, 9, 10 без нового фундамента.

**Строки 14 и 16 выделены намеренно.** Обе называются «Доступность», веса различаются в 10 раз
(0,5 против 5). Сшивка по русскому имени их перепутает и тихо исказит балл надёжности —
поэтому ключ только английский.

**Инварианты, которые закрепляются тестом-стражем:**

1. Σ весов характеристик = 100;
2. Σ весов подхарактеристик = 100;
3. для каждой характеристики Σ весов её подхарактеристик = вес характеристики (8 из 8);
4. справочник покрывает ровно 31 пару `QUALITY_MODEL`, без сирот с обеих сторон.

**Ключевое следствие для формулы.** Вес подхарактеристики **уже включает** вес своей
характеристики (5 + 3 + 2 = 10 = вес «Функциональной пригодности»). Умножать на вес
характеристики второй раз **нельзя** — это даст двойной учёт. Правильная свёртка одноуровневая:

```
Балл_ИС = Σ(вес_подхар × X_подхар) / Σ(вес_подхар применённых)
```

Знаменатель — сумма весов **фактически измеренных** подхарактеристик, а не всегда 100:
при `unmeasurable` веса перенормируются на измеренные (см. В-5).

`weights_service.py:55-59` (20/20/20/10/10/10/5/5 против 22/20/16/14/10/8/6/4), но не совпадают
с ним и заметно расходятся с профилями `BUSINESS_CRITICAL` и `SUPPORT`. По решению Р-6 файл
заменяет **все три** профиля как весовой вектор подхарактеристик; распределение внутри
характеристики теперь неравномерное (в коде было поровну) — это содержательное уточнение,
которого в системе не было.

### Пункт 1. Почему средняя цифра качества ИТ-ландшафта такая, и сколько — хорошо или плохо

**Коды:** УК-01, УК-02, УК-03

#### Как считается сейчас

`backend/app/modules/assessment/router.py:247`:

```python
"globalHealthScore": round(sum(measured_x) / len(measured_x), 4) if measured_x else 0.0
```

`measured_x` — плоский список **всех** значений `calculated_x` по всем подхарактеристикам всех
активных ИС за последний период каждой ИС. То есть цифра — это невзвешенное среднее
арифметическое по всем измеренным ячейкам теплокарты.

#### Почему цифра именно такая — шесть причин, ни одна из которых не видна пользователю

1. **Все подхарактеристики равны.** «Конфиденциальность» mission-critical ERP весит столько же,
   сколько «Тестируемость» вспомогательной вики.
2. **Все ИС равны.** Класс критичности в расчёт не входит вообще.
3. **Скрытый вес по полноте заполнения.** ИС с 31 заполненной метрикой даёт в среднее 31
   слагаемое, ИС с 5 — пять. Чем лучше документирована система, тем сильнее она тянет
   общую цифру. Это вес «по усердию аналитика», а не по важности.
4. **`unmeasurable` молча выпадает.** Не ноль, а исключение из базы. ИС, где защищённость
   измерить нельзя, выглядит так же, как ИС с идеальной защищённостью.
5. **Две разные «средние» цифры на одном экране.** `globalHealthScore` — среднее по значениям
   (стр. 247). А балл ИС (`sys_meta[...]["score"]`, стр. 184) — среднее средних по
   характеристикам. На одних и тех же данных это **разные числа**, и в UI не сказано, какое где.
6. **Нет базы сравнения.** Пороги `map_to_level` (0.81/0.61/0.41/0.21) применяются к отдельной
   метрике, а к интегральной цифре не объявлены. На экране ничего не отвечает на вопрос
   «0.62 — это хорошо?».

#### Что делаем

**УК-01. Панель «Из чего сложилась цифра».** Раскрытие интегрального Score:
вклад каждой характеристики (вес × балл), топ-5 подхарактеристик, тянущих вниз, топ-5 ИС по
абсолютному вкладу, число измеримых / неизмеримых / незаполненных ячеек и явная строка
«база расчёта: N значений из M возможных».

**УК-02. Единая цифра.** Убрать расхождение (5): один способ свёртки на всех экранах.
Переход на трёхуровневую свёртку по §1 п.1 — среднее становится взвешенным и
детерминированным на всех уровнях.

**УК-03. Шкала прочтения.** Объявить, как читать цифру: цветовая полоса с порогами,
подпись уровня словами, дельта к предыдущему периоду, отметка целевого значения.

#### Критерии приёмки

- По клику на интегральную цифру открывается разложение, сумма вкладов сходится с цифрой
  (расхождение ≤ 0.5 п.п.).
- На экране видно, сколько ячеек участвовало в расчёте и сколько выпало как неизмеримые.
- Цифра на дашборде CEO, на теплокарте и в Excel-отчёте совпадает.
- Рядом с цифрой — уровень словами и дельта к прошлому периоду.

### Пункт 2. Настроить веса относительно критичности (по приложенному файлу)

**Коды:** УК-04, УК-05, УК-06, УК-07

#### Как сейчас

`weights_service.py` уже считает вес каждой подхарактеристики:

```
α(i) = max(α_min, N₀/(N₀+N(i)))
вес(i) = α(i)·профиль(i, класс ИС) + (1−α(i))·фактика(i, доля в ALE)
```

Профили заданы на уровне характеристик и делятся **поровну** между подхарактеристиками
(`weights_service.py:93-104`). Внутри характеристики различий нет: «Конфиденциальность» и
«Подотчётность» весят одинаково.

Результат отдаётся как советчик и в Score не входит (Р-3).

#### Что делаем

**УК-04. Трёхуровневая свёртка по схеме файла.** Ввести явные `v` (метрика → подхарактеристика),
`w` (подхарактеристика → характеристика), `u` (характеристика → интегральный Q), с
нормировкой Σ=1 на каждом уровне и валидацией при сохранении.

**УК-05. Веса на уровне подхарактеристик.** Отказаться от деления поровну: задать `w`
индивидуально, минимум для трёх профилей критичности.

**УК-06. Применение к Score.** Перевести веса из режима «советчик» в режим расчёта.
Версионирование набора весов: у каждого периода — ссылка на версию весов, по которой он посчитан.

**УК-07. Редактор весов.** Экран администратора: правка `v`/`w`/`u` по профилям, предпросмотр
«как изменится Score портфеля», история изменений, кто и когда менял.

#### Критерии приёмки

- Σ весов = 1 на каждом уровне, при нарушении — отказ сохранения с указанием строки.
- Смена класса критичности ИС меняет её Score предсказуемо и объяснимо в панели УК-01.
- У каждой сохранённой оценки видно, по какой версии весов она посчитана.
- Старые периоды не «переписываются» задним числом без явного действия администратора.

### Пункт 4. Связь мер, рисков, денег и тепловой карты

**Коды:** УК-10, УК-11

#### Как сейчас

Связи в БД **есть**, но на теплокарте не видны:
- `RiskEventSubchar` — риск ↔ подхарактеристика;
- `RiskEventMeasure` — риск ↔ мера, с долей снятия ALE (`risk/models.py:126-141`);
- `RiskEvent.ale_avg` — деньги риска;
- `Proposal.delta_ale_cash / delta_ale_deferred / delta_ale_capacity`, `rosi` — деньги меры.

Теплокарта (`LevelHeatmap.tsx`, `assessment/router.py:227-231`) строится по одному числу —
уровню характеристики. Ни риска, ни денег, ни мер в ней нет.

#### Что делаем

**УК-10. Ячейка теплокарты как точка входа.** По клику на ячейку (ИС × характеристика) —
панель: подхарактеристики с баллами, привязанные риск-события с ALE, меры по ним с ΔALE и
ROSI, суммарные «деньги под ячейкой».

**УК-11. Денежный слой теплокарты.** Переключатель режима отображения:
«балл качества» / «ALE под риском, ₽» / «ΔALE, снимаемый мерами, ₽» / «покрытие мерами, %».
Цветовая шкала перестраивается под выбранный режим.

#### Критерии приёмки

- Сумма ALE по ячейкам одной ИС сходится с ALE этой ИС на риск-дашборде.

### Пункт 7. Связь риска и мер в деньгах

**Коды:** УК-19, УК-20

#### Как сейчас

### Пункт 9. По бизнес-процессам — понять среднее относительно рынка

**УК-24. Сравнение «мы / рынок».** На карточке процесса — своё значение, эталон, отклонение

### Пункт 13. Критичность и количество мер на исполнителях с учётом весов

**Коды:** УК-31, УК-32, УК-33

#### Как сейчас

Меры назначаются на `Proposal.owner` — строку. Ни трудоёмкости, ни сложности, ни веса
у меры нет. `implementation_months` есть, но это **длительность внедрения**, а не
трудозатраты и не сложность. Посчитать «15 лёгких против 5 сложных» сейчас не из чего.

`EmployeeEffectivenessCard.tsx` и `manager_metrics_service.py` считают эффективность по
числу и просрочкам — то есть по количеству, без учёта тяжести.

#### Что делаем

**УК-31. Вес меры.** Ввести оценку тяжести меры, складывающуюся из:
- веса подхарактеристики, на которую мера направлена (пункт 2);
- класса критичности ИС;
- трудоёмкости в часах — **проставляет исполнитель вручную** при переводе меры «в работу»
  (решение по В-41, см. вопросы ниже); поле необязательно на более ранних статусах;
- (опционально) денежного масштаба — ΔALE и CAPEX.

**УК-32. Нагрузка на исполнителя.** Показатель загрузки = Σ весов открытых мер исполнителя,
с разложением: сколько мер, какой суммарный вес, сколько просрочено, сколько по критичным ИС.
Ровно то, что просит формулировка «на одном 15 лёгких, на другом 5 сложных».

**УК-33. Балансировка.** Экран распределения: кто перегружен, кто свободен, рекомендация
по перераспределению; предупреждение при назначении меры перегруженному исполнителю.

#### Критерии приёмки

- Два исполнителя с одинаковым числом мер, но разной тяжестью, имеют разную загрузку —
  и разница объяснима на экране.
- Загрузка пересчитывается при закрытии/переназначении меры.
- Видно, из чего сложился вес конкретной меры.
- Меры без проставленной трудоёмкости (ещё не взяты «в работу») показаны в загрузке отдельным
  счётчиком «без оценки часов» — не пропадают и не считаются нулевыми молча.

- ~~В-41~~ **Закрыто (15.08.2026).** Трудоёмкость в часах проставляет **исполнитель вручную**

### Пункт 14. Наполнение мер и карточек на языке топ-менеджмента

**Коды:** УК-34, УК-35

#### Как сейчас

Карточки говорят языком стандарта и инженера: «Функциональная целесообразность»,
«X = 1 − A/B (INVERSE)», «Узнаваемость уместности». LLM генерирует `rationale` и
`expectation` (`governance/models.py:62-63`), но целевая аудитория текста нигде не задана —
промпт не различает читателя-инженера и читателя-CEO.

Есть готовый актив: колонка «Описание (что показывает; артефакты и данные подтверждения)»
из приложенного файла — управленческие формулировки по всем подхарактеристикам.

#### Принципы управленческого языка — выведены анализом, не запрошены отдельным файлом

Заказчик явно указал (15.08.2026): готовых эталонов «как надо / как не надо» не будет —
задача сформулировать принципы самостоятельно, через анализ проблематики, «без формул, без
переписываний вслепую». Ниже — восемь принципов и разбор того, почему это должно быть именно
анализом конкретного случая, а не механической заменой терминов.

1. **Вывод — первым предложением** (принцип BLUF / пирамиды Минто). Топ понимает суть, не
   дочитывая до конца: что случилось и чем грозит.
2. **Деньги и срок — числом, не оценочным словом.** Не «существенный риск», а «₽3,1 млн/год»;
   не «в ближайшее время», а дата или «3 недели».
3. **Причина — в терминах бизнес-последствия, не технической природы дефекта.** Не
   «недостаточное покрытие тестами API», а «риск простоя платёжного сервиса до N часов
   при следующем релизе».
4. **Действие — глагол + срок + ответственный**, а не описание процесса.
5. **Один тезис — одна карточка.** Мера, закрывающая несколько проблем, — списком по
   приоритету, не слитным абзацем.
6. **Сравнение вместо голого числа.** «Хуже среднего по отрасли на 15 п.п.» информативнее,
   чем «62%» само по себе (раскрывается полностью, когда появятся бенчмарки п. 9–10).
7. **Жёсткий лимит длины** — не более 60–80 слов на описательный блок. Это управленческое
   чтение, а не отчёт.
8. **Явный запрет:** без формул расчёта, без DIRECT/INVERSE, без служебных терминов
   стандарта — они остаются в техническом режиме за переключателем.

**Разбор на реальных данных, а не абстрактный пример.** Обе строки взяты из уже существующего
каталога — не придуманы для документа (`backend/app/modules/econ/measure_catalog.py:131,153`).
Цифры условны по форме, в системе подставляются из фактических данных карточки (ALE, SLA, срок,
ответственный из `risk_events`/`proposals`):

| Связка из каталога | Как есть сегодня (технический вывод) | Как надо (по восьми принципам) |
|---|---|---|
| Надёжность → Доступность (uptime); риск «Недостижение SLA доступности» | «Подхарактеристика: Доступность (uptime). X = A/B; A — время доступности; B — общее плановое время. X = 0,942.» | «Платёжный шлюз простаивал 42 часа за квартал — на 5,3 п.п. ниже согласованного SLA (99,5%), это ≈ 3,1 млн ₽ упущенной выручки. Причина — единая точка отказа в балансировщике. Решение: резервирование N+1, 3 недели, отв. [ФИО]. Результат: SLA восстановлен, риск повторения исключён.» |
| Защищённость → Конфиденциальность; риск «Утечка персональных данных → 152-ФЗ и репутация» | «Подхарактеристика: Конфиденциальность. X = A/B; A — объекты с корректным разграничением доступа; B — всего объектов, требующих защиты. X = 0,61.» | «39% хранилищ персональных данных клиентов без разграничения доступа — при инциденте это основание для санкций по 152-ФЗ. Решение: шифрование + ролевой доступ по минимальным привилегиям, 6 недель, отв. [ФИО]. Результат: канал утечки закрыт, готовность к проверке подтверждена.» |

Правая колонка использует данные **конкретного случая** — какая именно ИС, сколько именно
часов, кто отвечает. Их нет и не может быть в статичном «Описании» из файла весов: та колонка
отвечает на вопрос «что вообще означает эта подхарактеристика», это словарь термина, а не
готовый текст карточки. Подставить его как есть в карточку — и есть то самое слепое
переписывание, которого просили избежать.

#### Что делаем

**УК-34. Управленческий слой номенклатуры** (уточнена роль, объём не меняется). Описания из
файла весов подключаются как словарь ЗНАЧЕНИЯ термина — контекст для генерации, а не готовый
текст карточки. Переключатель языка интерфейса «технический / управленческий».

**УК-35. Генерация через анализ конкретной карточки.** Промпт LLM перестраивается вокруг
восьми принципов выше и структуры «что не так → чем грозит в деньгах и сроках → что
предлагается → сколько стоит → что изменится и когда → кто отвечает», заполняемой из
фактических данных карточки, а не из статического текста файла. Встраивается в существующий
пайплайн рассуждения (BL-009 — `personas/decisions/principles/pipeline/selfcheck`), не
отдельным механизмом.

**УК-35а (новая). Тест-страж формата** — по образцу уже работающего `_FORBIDDEN_TERMS`
(`backend/tests/test_reasoning.py:352`, запрет терминологии Toyota в выводе LLM):

- запрещены в управленческом режиме фрагменты `"X ="`, `"A/B"`, `"DIRECT"`, `"INVERSE"`,
  `"подхарактеристика"`;
- обязательны: денежная сумма или % изменения, срок (дата или «N недель/дней»), ответственный;
- лимит длины описательного блока — 80 слов.

#### Критерии приёмки

- В управленческом режиме на экране нет формул, аббревиатур стандарта и слов
  DIRECT/INVERSE — вместо них следствия для бизнеса; проверяется тестом УК-35а, не только
  вычиткой.
- Каждая карточка содержит: причину в бизнес-терминах, сумму/срок, действие с ответственным
  и сроком.
- Каждое утверждение в карточке подкреплено ссылкой на данные (артефакт подтверждения).
- Технический режим сохраняет полную детализацию — ничего не удаляется, только скрывается.

### Пункт 15. Эффекты в разрезе сроков; везде отражать временные рамки

#### Как сейчас — техническая проблема в основании

текст, сравнения ненадёжны, диаграмма Ганта строится на подстраховке
(`TaskPlanDashboard.tsx:142`: если дата не разобралась — «+30 дней»).

По эффектам: `implementation_months` (лаг внедрения) и `delta_ale_*` (годовой эффект) есть,
но эффект нигде не разложен по времени — не видно, когда он начнётся и как накопится.

**УК-36. Даты как даты.** Перевести `due_date` в тип даты с миграцией существующих строк,
единый формат отображения, единый разбор. Это предусловие для пунктов 12 и 16.

**УК-37. Эффект во времени.** По каждой мере — горизонт: дата старта, лаг внедрения,
дата выхода на эффект, накопленный эффект по кварталам, точка окупаемости. Портфельно —
кривая «когда придут деньги». На всех карточках — явные временные рамки: «за какой период»,
«на какую дату», «эффект в течение N месяцев».

#### Критерии приёмки

- Ни один срок и ни один эффект не отображается без указания периода/даты.
- Точка окупаемости считается с учётом лага внедрения, а не с даты создания карточки.
- Сортировка по датам корректна во всех таблицах.
- Миграция дат не теряет ни одной записи; неразобранные значения помечены и вынесены в отчёт.

### Пункт 16. Переписывание меры под исполнителя и перенос на Гант из карточки

**Коды:** УК-38

#### Как сейчас

Диаграмма Ганта есть (`TaskPlanDashboard.tsx:257+`), строится по `Proposal` со сроками.
Кнопки «отправить на Гант» из карточки меры нет; связь односторонняя и неявная — мера
попадает на диаграмму, только если у неё оказался разобранный `dueDate`.
Переформулирования меры под исполнителя нет: тексты `rationale`/`expectation` пишутся
для согласующего, а не для того, кто будет делать.

#### Что делаем

**УК-38. Кнопка «В работу» на карточке меры.** По нажатию:
1. LLM переписывает меру под исполнителя: из «что не так и почему важно» в
   «что конкретно сделать» — шаги, критерий готовности, требуемые доступы;
2. открывается форма назначения: исполнитель, срок, трудоёмкость (пункт 13),
   предупреждение о перегрузке;
3. мера появляется на диаграмме Ганта — как внутренняя запись АСОК (см. решение по п. 6:
   внешний менеджер задач пока не подключаем, поле `suz_link` остаётся ручной ссылкой);
4. если в будущем появится интеграция через `TaskSyncPort` (пункт 6) — тот же шаг создаст
   задачу во внешней системе автоматически, без изменений в этом сценарии.

Управленческая формулировка при этом **не затирается**: сохраняются обе версии —
для топа (пункт 14) и для исполнителя.

#### Критерии приёмки

- Переход из карточки на Гант — одно действие, без ручного повторного ввода данных.

### Пункт 17. Карточка поручения: маршрутизация по критичности, состав и цена неисполнения (Ц_ОМ)

**Коды:** УК-39…УК-60
**Происхождение:** не входил в исходные 16 пунктов заказчика. Возник 17.08.2026 из проверки
восьми утверждений заказчика о работе управленческого контура против кода и из разбора двух
рукописных схем заказчика — матрицы стоимости (Мера / ТС / Риски / Цена) и цикла
«Аудит качества (К) → Мера (М) → Риск (Р) → ТС → Поручение выполнено? → Мера окончена (МО)».
Обе схемы почти дословно совпали с уже существующей моделью БД (`Proposal`, `RiskEvent`,

#### 17.1. Роль «топ-менеджер» и владение мерой (ОМ = исполнитель)

##### Как сейчас

`governance.decide` выдаётся только `CTO`/`CEO` в редактируемой матрице
(`iam/permissions.py:120-129`) + встроенным `ADMIN`/`SUPER_ADMIN`. Отдельной роли `CIO` в
`User.ALL_ROLES` нет — `governance/router.py:38` упоминает `CIO`/`EXECUTIVE` только в мёртвой
константе `DECISION_ROLES`, которая нигде не проверяется. Матрица «роль → право» уже
редактируема через `PUT /iam/permissions/matrix` (BL-008) — конструктор прав, о котором
говорит заказчик, **уже существует**, вопрос только в том, какая роль в нём получает
`governance.decide`. На карточке `Proposal` уже раздельные поля: `owner`/`owner_user_id`
(кто отвечает) и `executed_by`/`executed_by_user_id` (кто исполнил) —
`governance/models.py:68-95`.

##### Что делаем

**УК-39. Утверждающая роль — через существующий конструктор прав.** Ничего нового в RBAC
не строим: право `governance.decide` остаётся привязанным к роли(-ям) в уже готовой матрице.
Открытый вопрос — какая конкретно роль в матрице соответствует «ИТ-директору» заказчика
(см. В-54).

**УК-40. Схлопывание ОМ = исполнитель на уровне представления.** Поля `owner_user_id` и
`executed_by_user_id` в БД не трогаем (историческая целостность, УК-12/13 уже опираются на
них), но на карточке вводим правило: при создании меры `executed_by_user_id` по умолчанию
= `owner_user_id`, и в интерфейсе оба показываются одной строкой «Ответственный (ОМ)» —
без двух отдельных полей, если это один и тот же человек.

**УК-41. Делегирование — вне АСОК.** Явно фиксируем: в системе не строится оргструктура
«руководитель → подчинённые» для распределения задач (это закрывает В-18 из Пункта 5).
Делегирование и распределение на нижестоящих сотрудников происходит в СУЗ; мост между
системами — уже существующее поле `Proposal.suz_link` (`governance/models.py:117`), новых
полей не требуется.

##### Критерии приёмки

- Право `governance.decide` управляется исключительно через `/iam/permissions/matrix`, без
  хардкода ролей в коде governance.
- На карточке меры, где `owner_user_id == executed_by_user_id`, интерфейс показывает одно
  поле «Ответственный (ОМ)», а не два одинаковых ФИО.
- Ни одна новая таблица/поле оргструктуры не появляется в БД в рамках этого пункта.

##### ❓ Вопросы

- **В-54.** Какая роль в текущей матрице соответствует «директору информационных технологий»
  заказчика — существующая `CTO` (переиспользовать как есть) или заводить отдельную роль
  `CIO`? *Рекомендация: переиспользовать `CTO` — по названию и объёму прав это и есть тот же

#### 17.2. Маршрутизация по критичности (минор → без эскалации, критично → к топ-менеджеру)

##### Как сейчас

Классификация тяжести **уже существует**, но на другой сущности: `Nonconformity.level`
(`MINOR`/`MAJOR`/`CRITICAL`, `nonconformity/models.py:36-40`) влияет на свёртку Score
(75%/40%/0% вклада + флаг `is_blocking` для Mission Critical), однако `governance/service.py`
её **не читает вообще** (0 совпадений по `level`/`Nonconformity` в файле) — `Proposal` идёт
одной и той же веткой одобрения независимо от тяжести (`decide()`,
`governance/service.py:100-113`). Связь риск ↔ мера (`RiskEventMeasure`,
`risk/models.py:126-140`) существует, но необязательна — `Proposal` можно завести без
`risk_event` вообще.

##### Что делаем

**УК-42. Обязательная привязка меры к risk_event.** `Proposal` без связанного `RiskEvent`
больше не сохраняется (кроме мер, явно помеченных как процессные/не риск-ориентированные —
уточнить состав исключений в исполнении). Обоснование: без риск-события неоткуда взять
денежный порог для маршрутизации.

**УК-43. Денежный порог маршрутизации.** При создании/переводе меры в работу считается
`ale_risk = RiskEvent.ale_avg × RiskEventMeasure.ale_reduction_share` по всем связанным
рискам. Порог — новый параметр в `EconConfig` (по образцу уже существующих `r`/`T`/α).
Ниже порога — мера подтверждается QUALITY_MANAGER (или самим ОМ на своё направление, см.
17.1) без выхода на `governance.decide`. Выше порога — обязательная эскалация к
топ-менеджеру.

**УК-44. `is_blocking` — переопределяет порог.** Несоответствие с `is_blocking=True`
(Mission Critical под угрозой) эскалируется всегда, вне зависимости от суммы — правило то
же, что уже действует для Score (§4.1 существующей модели), не изобретаем новое.

**УК-45. Двойной контроль исполнения по всем мерам.** По всем мерам без исключения контроль
и фиксация решения производится: (1) `QUALITY_MANAGER` — как сейчас, вручную; (2) LLM —
параллельно делает маппинг меры на возникающие или ранее зафиксированные технические сбои
(`TechIncident.linked_measure_id`, `incidents/models.py:101` + `RiskEventIncident`) и
сигнализирует о рассинхроне (например, мера отмечена исполненной, а по её риску продолжают
регистрироваться сбои той же природы). LLM здесь не принимает решение — только сверяет и
предупреждает, решение остаётся за QUALITY_MANAGER.

##### Критерии приёмки

- Ни одна новая мера не создаётся без `risk_event_id`, кроме явно помеченных исключений.
- Мера с `ale_risk` выше порога не может получить статус `APPROVED` иначе как через
  `governance.decide`.
- Мера с `is_blocking=True` эскалируется даже при `ale_risk` ниже порога — тест-страж на
  этот случай отдельно (аналогично уже существующим тестам-стражам покрытия каталога/
  запрещённых терминов).
- LLM-сигнал о рассинхроне (мера DONE, но сбои продолжаются) виден QUALITY_MANAGER на его
  дашборде, не только в логах.

##### ❓ Вопросы

- **В-56.** Порог маршрутизации — фиксированная сумма в рублях, % от риск-аппетита
  (`RiskEvent.risk_appetite`) или зависит от класса критичности ИС (Mission/Business/
  Support)? *Рекомендация: % от риск-аппетита — фиксированная сумма быстро устаревает,
  риск-аппетит уже есть в модели и по смыслу это ровно то же самое разграничение.*
- **В-57.** Если у меры несколько связанных `risk_event` с разной критичностью — маршрут
  определяется по максимальному `ale_risk` среди них, или по сумме?
  *Рекомендация: максимум — сумма может искусственно завысить маршрут для меры, закрывающей
  много мелких рисков разом.*

#### 17.3. Состав карточки при эскалации

##### Как сейчас

`Proposal` содержит `owner`, `due_date`/`due_on`, `rationale`, `expectation`, `risk_title` —
но не содержит: поля «системность» (сколько систем затронуто, прямо или косвенно), поля
«направление» (оргструктурная принадлежность — в IAM нет справочника подразделений вообще),
списка альтернативных вариантов решения. LLM (`reasoning.py:12`) заземлён на переданные
данные и не делает отдельного шага анализа системности.

##### Что делаем

**УК-46. LLM-анализ системности.** Новый шаг в пайплайне рассуждения: помимо прямых связей
(сколько систем через `RiskEventIncident`/`system_id` фактически задействовано), LLM ищет
**косвенные** признаки — совпадение `RiskBase.keywords`/`category` у риска на других
системах, не связанных напрямую с текущим риск-событием. Если QUALITY_MANAGER уже провёл
ручной анализ системности (заполнил поле сам) — LLM его **не переписывает**, а добавляет
рекомендательную пометку рядом («LLM: возможно также затронуты ещё N систем по признаку X»)
как оговорку поверх ручного ввода, не взамен него.

**УК-47. Временный справочник направлений.** Без интеграции с AD полноценная оргструктура
не строится. Вместо неё — простой ручной справочник «направление ↔ характеристики/
подхарактеристики, за которые оно отвечает» (условное деление, как решил заказчик), который
подставляет поле «направление» на карточке автоматически по характеристике проблемы.
Задел: справочник проектируется так, чтобы при появлении интеграции через AD (реальная
оргструктура сотрудников) его можно было заменить без переделки карточки — то же
архитектурное решение, что уже применено для `NotificationPort`/`TaskSyncPort` (Пункт 6).

**УК-48. Расширенный состав карточки эскалации.** Добавляются поля: список альтернативных
вариантов решения (не одна мера, а варианты с их CAPEX/OPEX/ROSI для сравнения топ-
менеджером), и Ц_ОМ (см. 17.4) — цена промедления, видимая прямо на карточке в момент
принятия решения, а не только на дашборде исполнителя постфактум.

##### Критерии приёмки

- Карточка эскалации показывает: системность (прямая + косвенная LLM-пометка при наличии
  ручного анализа), направление, минимум один альтернативный вариант решения (может
  совпадать с основным), Ц_ОМ на дату рассмотрения.
- Ручной анализ системности QUALITY_MANAGER никогда не перезаписывается LLM автоматически.
- Справочник направлений редактируется без деплоя (админ-экран, по аналогии с редактором
  весов УК-07).

##### ❓ Вопросы

- **В-58.** Кто ведёт временный справочник направлений — `SUPER_ADMIN`, `QUALITY_MANAGER`,
  или его нужно предзаполнить самим при внедрении и дальше редко менять?
- **В-59.** Сколько альтернативных вариантов решения обязательно показывать — минимум один
  (сам предложенный), рекомендованный диапазон 2–3, или без ограничения?

#### 17.4. Цена неисполнения — Ц_ОМ

##### Как сейчас

Все составляющие для расчёта уже есть в БД: `RiskEvent.ale_avg`/`ale_p90`/`max_sle`
(`risk/models.py:83`), `RiskEventMeasure.ale_reduction_share` (`risk/models.py:135`),
`Proposal.execution`/`due_on` (`governance/models.py:80,89`). Но сам расчёт нигде не
производится: `manager_metrics_service.py:144-160` суммирует `delta_ale_cash` только для
мер со статусом `DONE`; для просроченных (`overdue`) считается лишь штука, без единого
рубля рядом. Витрины для самого ОМ-исполнителя нет: `AssigneeTasksPage.tsx` не содержит ни
одного денежного поля, а `EXECUTOR` не имеет права `view.risk_economics`
(`iam/permissions.py:155-159`).

##### Что делаем

**УК-49. Расчёт и хранение Ц_ОМ — снимок + ежедневный пересчёт.** Момент фиксации
просрочки (`due_on` прошёл, `execution ≠ DONE`) создаёт **снимок** —
`Ц_ОМ_на_просрочку = Σ(RiskEvent.ale_avg × RiskEventMeasure.ale_reduction_share)` по связанным
рискам, сохраняется неизменным. Параллельно фоновая задача Celery ежедневно пересчитывает
**текущее** значение по тем же связям (риск мог быть переоценён, ALE — измениться). На
карточке показываются обе цифры рядом: «на момент просрочки: X ₽» и «на сегодня: Y ₽» —
не подменяются друг другом.

**УК-50. Отдельная формула для компенсирующих мер.** `MEASURE_COMPENSATING`
(`governance/models.py:37`) не убирает вероятность риска, а гасит последствия — поэтому
Ц_ОМ для неё считается **не** через `ale_reduction_share`, а как накопленная фактическая
стоимость реализовавшихся `TechIncident.cost_total` по связанным рискам за период с
`due_on` (когда компенсирующая мера должна была снижать ущерб, но не снижала, потому что не
исполнена).

**УК-51. Переключатель горизонта.** На карточке ОМ-исполнителя и на дашборде руководителя —
переключатель «сегодня» / «за квартал». Это не два разных расчёта, а два среза одного и
того же ежедневного ряда (УК-49) — квартальный вид агрегирует дневные точки, не пересчитывает
заново.

##### Критерии приёмки

- Ц_ОМ виден ОМ-исполнителю на его собственной странице «Мои задачи», не только менеджменту.
- Снимок на момент просрочки не меняется задним числом при последующей переоценке ALE риска.
- Для `COMPENSATING`-мер в интерфейсе явно видно, что используется другая формула (не
  смешивается визуально с `ELIMINATING` в одной цифре без пометки).
- Переключатель день/квартал не создаёт расхождения между суммой дневных точек и квартальной
  цифрой.

##### ❓ Вопросы

- **В-60.** Частота фонового пересчёта текущей Ц_ОМ — раз в сутки ночным батчем, или
  при каждом открытии карточки (дороже, но всегда актуально)? *Рекомендация: ночной батч
  + принудительный пересчёт по кнопке — дешевле и достаточно точно для управленческого
  решения.*
- **В-61.** Что считать «периодом просрочки» для компенсирующей меры при накоплении
  фактического ущерба — от `due_on` до сегодня, или от `due_on` до фактического исполнения
  (если исполнена позже с опозданием)?

#### 17.5. Веса как двигатель приоритизации

##### Как сейчас

`weights_service.py` — советчик, `GET /econ/weights` ни на что не влияет программно
(`weights_service.py:20`, `router.py:82`). Список мер сортируется по `created_at desc`
(`governance/service.py:66-78`), диаграмма Ганта — по сроку (`TaskPlanDashboard.tsx:142`).

##### Что делаем

**УК-52. Очередь мер по весу.** Порядок в списках мер (governance-очередь, Гант) считается
по составному ключу `вес_подхарактеристики (файл ГОСТ, §1.0) × вес_критичности_ИС × Ц_ОМ`
вместо `created_at`. Переиспользует уже существующие `weights_service` и Ц_ОМ (17.4), новой
модели не требует.

**УК-53. Взвешенный порог эскалации.** Порог из 17.2 (В-56) домножается на вес
подхарактеристики: мера на менее весомой подхарактеристике требует более высокого `ale_risk`
для эскалации, и наоборот — то есть один и тот же порог в рублях по факту неодинаков для
разных характеристик.

**УК-54. Приоритизация бюджетных заявок.** При конкурирующих заявках на CAPEX сортировка
предложений — по тому же составному весу. Сам процесс распределения бюджета остаётся вне
системы (это не бюджетирование, а приоритизация списка для тех, кто бюджет распределяет).

##### Критерии приёмки

- Два риска с одинаковой Ц_ОМ, но разным весом ГОСТ, занимают разное место в очереди —
  разница объяснима в интерфейсе (по аналогии с критерием УК-32).
- Как подтвердил заказчик (5.2): случай «мера с большим Ц_ОМ обгоняет по порогу эскалации
  мера с высоким весом, но малой Ц_ОМ» штатно возникать не должен — система его не
  блокирует, но помечает как «нетипичный порядок» для проверки человеком, а не скрывает.

##### ❓ Вопросы

- **В-62.** Точная формула составного веса — простое произведение трёх множителей, или
  нужна нормировка/логарифмирование (чтобы один экстремально большой Ц_ОМ не забивал вес
  подхарактеристики полностью)?

#### 17.6. LLM-рекомендации мер и маппинг на риски/ТС

##### Как сейчас

`measure_catalog.py` — статичный хардкод, 44 связки «риск → мера», правится релизом, без LLM
(`measure_catalog.py:10`). `risk/embeddings.py` — детерминированный лексический поиск, LLM не
задействован (`embeddings.py:4-7`). `reasoning.py` на этапе синтеза мер жёстко заземлён на
уже переданные меры/риски (`reasoning.py:12`, `_fallback_measures` — `reasoning.py:484-493`);
шаг «чего не хватает» — детерминированная проверка полноты данных, не LLM-логика
(`reasoning.py:711`).

##### Что делаем

**УК-55. Оба режима одновременно, с меткой.** (1) Переиспользование существующего каталога
как сейчас — без изменений. (2) Когда каталог не покрывает конкретный кейс, LLM предлагает
новую формулировку меры по паттерну существующих связок. В обоих случаях, если текст
сгенерирован или переформулирован LLM, на карточке ставится явная неубираемая метка
«рекомендация LLM», отличимая от меры, введённой человеком.

**УК-56. Обязательное ревью перед эскалацией.** LLM-рекомендация не может попасть в карточку
эскалации топ-менеджеру без явного ревью `QUALITY_MANAGER` или `RISK_MANAGER` — до ревью она
существует только как черновик, видимый ревьюеру.

Пункт 6.3 исходного пула вопросов («что именно означает "может быть упущено" — пробелы
покрытия каталога или конкретный кейс») заказчик снял с рассмотрения — реализуется только
явный сценарий «каталог не покрывает конкретный кейс» (УК-55.2), отдельный анализ пробелов
покрытия каталога как функция не строится.

##### Критерии приёмки

- Любой текст меры, к которому прикасался LLM (сгенерирован или переформулирован), несёт
  метку источника — тест-страж по образцу `_FORBIDDEN_TERMS` (`test_reasoning.py:352`).
- Ни одна LLM-рекомендация не доходит до `governance.decide` без записи о ревью
  QUALITY_MANAGER/RISK_MANAGER в `history` карточки.

#### 17.9. SLA и автоэскалация

##### Как сейчас

`Nonconformity.sla_due` задокументирован (`nonconformity/models.py:97`: «>30 дней в
"Оценено" без решения → автоэскалация»), но нигде не читается в `service.py` — автоэскалации
физически нет, несмотря на докстринг.

##### Что делаем

**УК-59. Дифференцированный SLA.** Срок до автоэскалации зависит от критичности (тот же
признак, что маршрутизация в 17.2, не отдельный критерий): минор — 30 дней, критично —
3 дня.

**УК-60. Воркер автоэскалации.** Задача Celery по расписанию находит несоответствия/меры,
просроченные по SLA, и на срабатывание: (1) шлёт уведомление через `NotificationPort`
(заглушка на старте, Пункт 6); (2) поднимает статус/маршрут карточки к топ-менеджеру по
той же схеме эскалации, что и 17.2 — автоэскалация не меняет ответственного и не считается
отдельно от Ц_ОМ, а поднимает уже существующую карточку по существующему маршруту.

##### Критерии приёмки

- Просроченная минорная мера эскалируется автоматически на 31-й день, критичная — на 4-й.
- Факт автоэскалации записывается в `history` карточки (кто/что/когда — «эскалировано
  автоматически по SLA»), не только в журнале уведомлений.

##### ❓ Вопросы

- **В-64.** Критерий «критично» для целей SLA — тот же порог/`level`, что в 17.2, или нужен
  отдельный (более узкий) критерий именно для срабатывания эскалации по времени?
  *Рекомендация: тот же — два разных критерия критичности в одной системе будут постоянно
  расходиться и потребуют объяснения, почему они разные.*
