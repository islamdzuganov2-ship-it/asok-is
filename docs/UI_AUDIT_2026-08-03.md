# Аудит UI: реестр дефектов (2026-08-03)

Инициатива BL-007, блок «визуальное качество». Заказчик: интерфейс не выглядит premium —
воспринимается как непричёсанный pet-project. Задача: найти и устранить причины этого
восприятия, зафиксировав их как проверяемые дефекты.

## Как проводился аудит

**Инструмент:** `frontend/scripts/check-ui.mjs` — статический аудит исходников по визуальным
инвариантам (`npm run check:ui`). Проверяются исходники, а не рантайм: правило должно
срабатывать на ревью, до сборки. Дополняет `npm run check:contrast` (WCAG, 74 проверки).

**Почему кодом, а не глазами.** «Премиальность» ломается не одной крупной ошибкой, а десятками
мелких расхождений: карточка с другой тенью, число, выровненное по левому краю, свой оттенок
мимо палитры. Глазами такое ловится невоспроизводимо и возвращается через два спринта.
Инвариант, проверяемый кодом, держится сам.

**Ограничение этого прогона (важно).** В сессии аудита панель браузера не композитилась:
`innerWidth`/`clientWidth` возвращали 0, скриншоты недоступны. Поэтому **чисто визуальные
характеристики — баланс воздуха, оптическое выравнивание, «дорого/дёшево» — не оценивались**.
Проверено то, что измеримо: структура DOM, вычисленные стили, исходники. Пункты, требующие
живого вьюпорта (адаптивность, переполнение), вынесены в отдельный блок «Не проверено».

## Приоритизация: критичность × стоимость правки

Приоритет — не только «насколько заметно», но и «сколько кода задевает и чем рискует».

**P0 — высокий эффект, ограниченный риск.** Правка локальна (объект колонки, пропсы карточки),
результат виден сразу на всех дашбордах.

**P1 — высокий эффект, широкая правка.** Механическая замена в 25+ файлах. Риск не в логике,
а в объёме: вслепую, без возможности посмотреть глазами, легко сдвинуть вёрстку.

**P2 — низкий эффект на восприятие, разбор каждого случая.** Часть «нарушений» законна
(оттенок графика, служебный цвет), поэтому автоматом не чинится — нужен разбор.

## UI-02 · Числовые колонки не выровнены вправо (критический, P0)

**Суть.** Ни одна из 16 таблиц не выравнивает числа вправо. Разряды не встают друг под друга,
колонку нельзя просмотреть взглядом сверху вниз — числа приходится читать каждое отдельно.

**Почему это главный дефект.** Продукт — аналитический, таблицы с процентами и счётчиками есть
на каждом экране. Левое выравнивание чисел — самый узнаваемый признак «сделано на скорую руку»
в интерфейсах с данными. Один этот дефект даёт больше вклада в ощущение «pet-project», чем
любой другой пункт списка.

**Где:** `DashboardPage` (6), `MeasuresAiAnalyticsCard` (3), `AiAssessmentPage` (2),
`ExecutiveDashboard` (2), `IncidentsAnalyticsPage` (2), `ManagerDashboard`, `TechDebtCard`,
`AssessmentCorrectionPanel`, `NewAssessmentPage`, `ExcelReportsPage`.

**Решение.** Хелпер `numericColumn()` — колонка получает `align: 'right'` и табличные цифры
по построению, а не по внимательности автора. Закрывает UI-02 и UI-08 одной правкой.

## UI-08 · Числа без табличных цифр (P0, чинится вместе с UI-02)

**Суть.** В пропорциональном шрифте цифры имеют разную ширину: «11%» уже «88%». При обновлении
данных колонка дёргается, при сравнении строк цифры не совпадают по вертикали.

**Решение.** `fontVariantNumeric: 'tabular-nums'` в том же хелпере.

## UI-01 · Карточки вне premium-слоя (критический, P0)

**Суть.** 7 карточек в 6 файлах не используют `premiumCard`: у них другая рамка, тень, радиус и
шапка. На «Внесении данных» и в отчётах они стоят рядом с premium-карточками — разнобой виден
в пределах одного экрана.

**Где:** `NewAssessmentPage` (2), `ExcelUploadBlock`, `AiAssessmentPage`, `ExcelReportsPage`,
`ExpertReviewPage`, `LoginPage`.

**Замечание по `LoginPage`.** Это первый экран, который видит пользователь, и он полностью вне
слоя: своя тень `0 4px 12px`, радиус 8 против 16, нет золотого акцента. Первое впечатление о
«премиальности» формируется именно здесь.

## UI-09 · Палитра уровней объявлена в компоненте (значимый, P0)

**Суть.** `LEVEL_COLORS` и `LEVEL_TAG_COLORS` (12 оттенков) живут в `components/LevelHeatmap.tsx`,
тогда как остальная палитра — в `theme/ragPalette.ts`. Компонент импортируется страницами ради
цветов, а не ради разметки; аудит цветов даёт на нём 21 срабатывание.

**Решение.** Перенести палитру уровней в `theme/`, компонент оставить разметкой.

## UI-07 · Таблицы без пустого состояния (значимый, P1)

**Суть.** 6 таблиц не задают `emptyText`: на пустых данных пользователь видит голую разметку
со стандартной англоязычной заглушкой antd вместо объяснения, что делать.

**Где:** `AssessmentCorrectionPanel`, `IncidentsAnalyticsPage`, `TechDebtCard`,
`MeasuresAiAnalyticsCard`, `ExecutiveDashboard`, `AiAssessmentPage`.

## UI-04 · Размер шрифта мимо шкалы (значимый, P1)

**Суть.** 119 мест задают `fontSize` числом мимо шкалы `TYPE`, введённой в T-58. Шкала есть,
но соблюдается только на экранах МК — остальное продолжает дрейфовать.

## UI-03 · Цвет мимо палитры (значимый, P2)

**Суть.** 110 литералов цвета вне `theme/`. Из них ~33 — определения палитры (снимается
дефектом UI-09), остальное — служебные и графические оттенки, требующие разбора: часть законна
(цвет линии графика), часть — случайный оттенок.

## UI-05 · Отступ вне сетки (мелкий, P2)

13 мест мимо сетки 4px, преимущественно в компонентах вне экранов МК.

## UI-10 · Предупреждения antd в консоли (значимый, P1) — закрыт

**Суть.** `<Spin tip="Загрузка...">` в `PageLoader` использовался вне вложенного/полноэкранного
режима: antd на каждой ленивой загрузке страницы писал в консоль `[antd: Spin] tip only work in
nest or fullscreen pattern`. Четыре предупреждения на один вход в приложение.

**Почему это в списке.** Само по себе не видно пользователю, но открытая консоль с
предупреждениями — первое, что смотрит любой технический приёмщик. Для продукта, который
позиционируется как premium, это прямой сигнал «недоделано».

**Решение.** Подпись выводится своим элементом рядом со спиннером (ступень `TYPE.caption`,
цвет `BRAND.inkSoft`), проп `tip` убран.

## Не проверено (требует живого вьюпорта)

Эти пункты не закрыты аудитом и остаются открытыми:

- **Адаптивность** (<768px): фикс-ширины колонок графиков, поведение таблиц и Ганта.
- **Переполнение по горизонтали** на узких экранах.
- **Оптическое выравнивание и баланс воздуха** — требует взгляда человека или скриншот-тестов.

Рекомендация: прогнать `npm run check:ui` и визуальную проверку в окружении с рабочим
браузером; при необходимости добавить скриншот-тесты (Playwright) как отдельную задачу.

## Регресс

Проверки включены в стандартный пул:

```
npm run check          # типы + юниты + контраст + UI-инварианты
npm run check:ui       # только визуальные инварианты
npm run check:contrast # только WCAG
```

`check:ui` по умолчанию валит сборку на критических дефектах (`--fail-on=critical`);
значимые и мелкие показываются, но не блокируют — порог повышается по мере расчистки.
