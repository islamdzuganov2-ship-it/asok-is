# АСОК ИС — Заключение по всем тестовым данным (эталонный анализ) · 2026-07-06

> Полноценный анализ ВСЕХ тестовых данных (моки фронтенда + БД) после пересоздания с ролевым
> подходом. На основе этого анализа выведена **инструкция для LLM** (последовательность шагов) —
> закреплена в `docs/LLM_TRAINING.md §10` и продублирована ниже.

## 1. Охват данных (что анализировалось)

**БД (live-режим):** 4 ИС × 6 кварталов (Q1-2025…Q2-2026) × 55 метрик каталога = 1320 значений;
147 профсуждений МК (Q2-2026); контур СИИ — 16 значений ГОСТ 59898. 2 метрики «невозможно
измерить» (HR Portal, нет базы B). **Моки (демо-режим):** 30 ИС × 8 характеристик × 31
подхарактеристика ISO 25010; 47 мер качества; 92 аномалии динамики (8 причин предзаполнено МК).

## 2. Заключение по качеству ландшафта (по данным БД)

**Интегральный уровень:** средний (глобальный индекс ≈ 74% по последнему периоду Q2-2026;
демо-ландшафт моков — 65%).

**По системам (динамика 6 кварталов):**
- **АБС Core (MISSION CRITICAL) — 86%, стабильна.** Единственная аномалия — Q4-2025: просадка
  «Надёжности» на ~30 п.п. (инцидент P1, деградация СУБД после релиза 2.14) с полным
  восстановлением в Q1-2026. Вывод: инцидент отработан, процесс стабилизации работает;
  контроль — плановый.
- **CRM ОПК (BUSINESS CRITICAL) — 51%, ДЕГРАДАЦИЯ 73→51 (−4…−5 п.п./квартал).** Главный
  приоритет ландшафта. Драйверы: «Функциональная пригодность» 40% (выпуск MVP без полного
  приёмочного цикла, Q3-2025 −15 п.п.) и «Сопровождаемость» 40% (рост техдолга). Суждения МК
  заполнены частично (36 из 55) — есть слепые зоны. Требуются меры уровня CTO: остановить
  деградацию, выделить ресурс на приёмочный контур и рефакторинг.
- **HR Portal (BUSINESS OPERATIONAL) — 77%, РОСТ 51→77.** Программа качества работает
  (аномальный рост «Надёжности» Q2-2026 +14 п.п. — сокращение MTTR). Позитивный кейс для
  тиражирования практик. 2 метрики без базы измерения — подключить источники.
- **АОКИС (BUSINESS CRITICAL) — 81%, слабое место «Функциональная пригодность» (≈60%,
  Q1-2026 −12 п.п.).** Суждения МК по ФП заполнены (17) — фактура для мер есть.
- **Скоринг-ML (СИИ), контур ГОСТ 59898:** Q = 49%, 3 из 16 метрик вне допуска эталона
  (0.88 ± 0.10) — требуется дообучение/калибровка модели по несоответствующим субхарактеристикам.

**Петля управления (по мокам, governance):** 47 мер: 35 ожидают решения (перегруз ЛПР —
рекомендация: приоритизация по критичности), 8 одобрено, 4 отклонено; 3 эскалации срыва
сроков (бюджет), по 2 приняты решения «запросить меры». Ответственные распределены по
компетенциям (разработка/эксплуатация/ИБ/тестирование), эскалации — по критичности ИС
(CIO/CTO/руководитель ИТ-блока).

**Слепые зоны:** незаполненные суждения CRM (19), незаполненные причины аномалий (84 из 92 в
демо; уведомления МК работают), 2 неизмеримые метрики HR.

## 3. Инструкция для LLM — последовательность качественного заключения

Канонический текст: `docs/LLM_TRAINING.md §10`. Кратко (порядок обязателен):

1. **Инвентаризация охвата** — сколько ИС/периодов/метрик, сколько «невозможно измерить».
2. **Интегральный уровень и распределение** ИС по RAG-уровням.
3. **Динамика, а не срез** — тренд каждой ИС за ≥4 квартала (стабильна/растёт/деградирует).
4. **Аномалии и причины** — |Δ|≥12 п.п.; причина МК есть → контекст; нет → «требуется
   расследование», не спекулировать.
5. **Драйверы вниз до формулы** — характеристика → подхарактеристика → метрика (A/B).
6. **Суждения МК как фактура** — цитировать/агрегировать, не выдумывать; пробелы → слепые зоны.
7. **Меры и петля управления** — статусы, выполнение, эскалации; где петля разорвана.
8. **Ролевая подача** — МК: операционно (метрики, формулы, что заполнить); CIO/CTO/CEO:
   3–5 приоритетов (критичность × деградация × невыполненные меры), ответственные, решения.
9. **Хансей** — самопроверка: числа из данных, охват указан, СИИ — по 59898, рекомендации адресные.

Согласовано с конвейером BL-005 (`modules/llm/reasoning.py`): шаги 1–2 = Генти Генбуцу,
3–5 = постановка проблемы и 5 Почему, 6–7 = линзы/Немаваси, 8 = контракт ЛПР, 9 = Дзидока+Хансей.
