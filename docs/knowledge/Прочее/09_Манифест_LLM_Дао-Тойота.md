# 🧭 Манифест: многоаспектное рассуждение LLM (Дао Тойота × IT × ISO)

> **Цель.** Заставить встроенную LLM АСОК ИС **мыслить не однобоко**: по карточкам мер, по
> профессиональным суждениям и по рискам из базы — рассуждать с нескольких точек зрения,
> искать первопричину, встраивать качество, и **только после этого** выносить заключение
> руководителю (ЛПР). Принципы менеджмента **Дао Тойота (Toyota Way)** переложены на
> производство ПО так, чтобы **не противоречить ISO/IEC 25010** (качество ИС) и
> **ISO/IEC 38500** (корпоративное управление ИТ).
>
> **Статус:** `draft-v1` — концептуальная заготовка (методология). Реализация движка —
> `backend/app/modules/llm/reasoning.py`, задача **BL‑005** (см. [[ТЗ_Модульный_Монолит_v13]]).

---

## 0. Проблема «однобокости»

Сейчас заключение формируется «в один проход» (`generate_judgment_conclusion`): модель
получает суждения+риски и сразу пишет вывод. Это **однобоко** — нет разложения на аспекты,
нет поиска первопричины, нет разных ролевых линз, нет саморефлексии. Манифест вводит
**конвейер рассуждения** между входными данными и заключением ЛПР.

Вход конвейера (три источника, как в контуре АСОК ИС):
- **Карточки мер** (`MeasureDecisionModal` / governance): что предлагается сделать, кому, к сроку.
- **Профессиональные суждения** (`professional_judgments`): экспертные оценки по подхарактеристикам.
- **Риски из базы** (`risk_base`): известные риски и типовые меры минимизации (grounding).

## ЧАСТЬ I. 14 принципов Дао Тойота → призма IT → привязка к ISO

Модель Лайкера (4P: *Philosophy, Process, People, Problem Solving*), переложенная на
производство ПО и на рассуждение LLM.

| # | Принцип Toyota Way | Перекладка на IT / АСОК ИС | ISO 25010 / 38500 |
|---|---|---|---|
| 1 | Долгосрочная философия важнее краткосрочной выгоды | Решения по качеству ИС — от долгосрочной ценности, не «замазать метрику» | 38500 «Стратегия» |
| 2 | Непрерывный поток, выявляющий проблемы | Прозрачный поток оценки: проблема всплывает на дашборде, а не прячется | 25010 «Анализируемость» |
| 3 | Вытягивание (pull), без перепроизводства | Меры генерируются под реальную просадку метрики, а не «на всякий случай» | 38500 «Производительность» |
| 4 | Хейдзунка — выравнивание нагрузки | Приоритизация мер по критичности ИС и охвату, без перегруза одной команды | 38500 «Человеческий фактор» |
| 5 | **Дзидока** — остановись и встрой качество (не пропускай дефект) | **Grounding-контроль**: заключение не выходит, если факты/числа не из входа | 25010 «Функц. корректность» |
| 6 | Стандартизованные задачи — основа кайдзен | Единый формат заключения и мер (контракт вывода, ниже) | 38500 «Соответствие» |
| 7 | Визуальный контроль — ничего не скрыто | Теплокарта, RAG-палитра, реестр мер — проблемы видны | 25010 «Узнаваемость уместности» |
| 8 | Проверенная, надёжная технология | Детерминизм (temperature 0.1), on-prem модель в банковском контуре | 38500 «Приобретение» |
| 9–10 | Воспитывать лидеров и людей, живущих философией | Ролевые «линзы» рассуждения (ниже) отражают реальные роли контура | [[АОК ИС/АСОК_ИС/07_ТЗ/01_Ролевая_модель]] |
| 11 | Уважать партнёров, помогать им расти | Меры — с ответственным и сроком, помощь исполнителю, а не «наказание» | 38500 «Ответственность» |
| 12 | **Генти Генбуцу** — иди и смотри сам | Рассуждение стартует от первичных данных (суждения/риски/меры), без домыслов | 25010 «Достоверность данных» |
| 13 | **Немаваси** — решение через консенсус, рассмотреть все варианты | **Многоролевые линзы**: несколько точек зрения ДО заключения | 38500 «Ответственность» |
| 14 | **Хансей + Кайдзен** — саморефлексия и постоянное улучшение | Этап саморефлексии: что не учтено, какова уверенность | 25010 «Модифицируемость» |

**Итог I:** три принципа — несущие для «не однобоко»: **Генти Генбуцу** (иди к данным),
**Немаваси** (несколько точек зрения), **Дзидока** (встроенное качество/grounding);
плюс **5 Почему** (инструмент поиска первопричины, ядро Toyota Problem Solving).

## ЧАСТЬ II. Конвейер многоаспектного рассуждения (перед выводом ЛПР)

```
Вход: карточки мер + профсуждения + риски из базы
   │
   ├─ Э0. ГЕНТИ ГЕНБУЦУ — «иди и смотри»: собрать только фактические данные из входа
   │        (никаких выдуманных чисел/названий; чего нет — «данные отсутствуют»)
   │
   ├─ Э1. ПОСТАНОВКА ПРОБЛЕМЫ — что именно просело (характеристика/подхарактеристика), масштаб
   │
   ├─ Э2. 5 ПОЧЕМУ — первопричина, а не симптом (цепочка «почему» до корня)
   │
   ├─ Э3. НЕМАВАСИ — прогон через РОЛЕВЫЕ ЛИНЗЫ (несколько точек зрения, часть III):
   │        ИТ-директор · менеджер качества · риск-офицер · владелец ИС · ИБ · тестирование
   │        (для каждой линзы: как выглядит проблема и что она рекомендует)
   │
   ├─ Э4. ДЗИДОКА — встроенное качество (poka-yoke): grounding-проверка (числа только из входа),
   │        отсев противоречий между линзами, привязка к рискам из base
   │
   ├─ Э5. КАЙДЗЕН — синтез мер: связать первопричину → меры → риски (минимизация), приоритет
   │
   ├─ Э6. ХАНСЕЙ — саморефлексия: что осталось неучтённым, какова уверенность, где нужны данные
   │
   └─ Э7. ЗАКЛЮЧЕНИЕ ЛПР — вынести руководителю ТОЛЬКО после Э0–Э6 (контракт вывода, часть V)
```

Ключ: заключение — **последний** шаг. До него модель обязана пройти разложение, первопричину,
многоролевой прогон и самопроверку. Это и есть «не однобоко».

## ЧАСТЬ III. Ролевые линзы (немаваси-многоаспектность)

Каждую проблему LLM обязана рассмотреть минимум с этих точек зрения (перекладка ролей контура):

| Линза | Вопрос линзы | Опора (ISO) |
|---|---|---|
| **ИТ-директор (CIO/CTO)** | Влияние на бизнес-ценность и стратегию ИТ? | 38500 «Стратегия» |
| **Менеджер качества** | Какая подхарактеристика 25010 просела и почему? | 25010 (модель качества) |
| **Риск-офицер** | Какие риски из базы активируются, вероятность/последствия? | 38500 «Соответствие» |
| **Владелец ИС** | Стоимость меры, ответственный, срок, реалистичность? | 38500 «Ответственность» |
| **Информационная безопасность** | Затронуты ли защищённость/152-ФЗ/ГОСТ Р 57580? | 25010 «Защищённость» |
| **Тестирование/эксплуатация** | Подтверждают ли метрики надёжности/тестируемости вывод? | 25010 «Надёжность» |

Правило: если линзы **противоречат** — это фиксируется в Э6 (саморефлексия), а не сглаживается.

## ЧАСТЬ IV. Соответствие ISO (чтобы «не противоречило»)

- **ISO/IEC 25010.** Рассуждение оперирует официальными характеристиками/подхарактеристиками
  модели качества; Дзидока = «функциональная корректность» вывода (grounding); многоролевой
  прогон повышает «анализируемость» и «достоверность» заключения.
- **ISO/IEC 38500.** Конвейер реализует 6 принципов ИТ-управления: ответственность (роли/меры),
  стратегия (долгосрочность), приобретение (обоснованные меры), производительность (pull, без
  перепроизводства мер), соответствие (grounding + аудитируемость), человеческий фактор (уважение
  к исполнителю меры). Заключение ЛПР = «управление, а не исполнение»: рекомендация, а не приказ.

## ЧАСТЬ V. Контракт вывода (структура заключения руководителю)

```
1. Рассмотренные аспекты   — какие линзы применены (немаваси подтверждён)
2. Первопричина            — итог 5 Почему (корень, не симптом)
3. Активируемые риски      — из base, со ссылкой (grounding)
4. Предлагаемые меры       — кайдзен: мера → ответственный/срок → минимизируемый риск
5. Рекомендация ЛПР        — 1–2 управленческих действия (уровень топ-менеджмента)
6. Уверенность и оговорки  — хансей: чего не хватает, где данные отсутствуют
```

Guardrails (сохраняются из текущего `llm_service`): только переданные числа; при отсутствии
данных — прямо сообщить; детерминизм (temperature 0.1); пост-проверка процентов.

## ЧАСТЬ VI. Обновление знаний по обучению LLM

Принципы кодируются на трёх уровнях «обучения» (см. [[LLM_TRAINING]], уровни A/B/C):

| Уровень | Как внедряется многоаспектность |
|---|---|
| **A. Поведение промптом** | Системный промпт задаёт конвейер Э0–Э7 и ролевые линзы; few-shot с примером многоаспектного рассуждения; temperature 0.1 |
| **B. Самообучение (RAG)** | В `history_block` добавляются прошлые заключения + активированные риски → преемственность линз между периодами |
| **C. Дообучение (LoRA)** | Датасет `judgments_sft.jsonl` расширяется полем «reasoning» (Э1–Э6), а не только output → модель учится проходить этапы, а не сразу отвечать |

Практический вывод для обучения: **эталонный пример теперь содержит трассу рассуждения**
(первопричина + линзы + самопроверка), а целевой `output` — заключение по контракту части V.
Это меняет форму SFT-корпуса (`export_llm_dataset`) — задел под BL‑005.

## ЧАСТЬ VII. Статус и критерии приёмки

**Статус:** заготовка методологии (v1). **Реализация:** `backend/app/modules/llm/reasoning.py`
(после миграции домена llm в модульную структуру — задачи #15/#16, BL‑005).

**Критерии приёмки движка рассуждения:**
1. Заключение формируется только после прохождения Э0–Э6 (трасса доступна для аудита).
2. Минимум 3 ролевые линзы применены к каждой проблеме (немаваси).
3. Grounding сохранён: чисел вне входа нет (Дзидока); при недостатке данных — честная оговорка.
4. Есть блок первопричины (5 Почему) и блок саморефлексии (хансей).
5. Соответствие ISO 25010 (характеристики) и 38500 (6 принципов) — не нарушено.

## Статус реализации (2026-07-04) — ✅ ВНЕДРЕНО

Конвейер реализован в `backend/app/modules/llm/reasoning.py` (BL-005), подключён к
`GET /api/v1/assessments/{period_id}/judgment-conclusion` (ответ: заключение + аудируемая трасса
`reasoning` + `confidence`).

**Проверка критериев приёмки (часть VII):**
1. ✅ Заключение только после Э0–Э6 — трасса всех 8 этапов в каждом ответе (аудит).
2. ✅ Немаваси ≥ 3 линз — применяются 4: CIO, Менеджер качества, Риск-офицер, ИБ (меньше 3 — ValueError).
3. ✅ Дзидока/grounding — три фильтра на каждый LLM-проход: числа только из входа, отбраковка
   эхо-плейсхолдеров скелета, детект вырожденных повторов; отбраковка → детерминированный fallback.
4. ✅ Блоки «Первопричина (5 Почему)» и «Уверенность и оговорки (Хансей)» обязательны в контракте ЛПР.
5. ✅ Честность отсутствия: непереданные источники (карточки мер и т.п.) явно помечаются
   «данные отсутствуют»; синтез мер без источников не запускается.

**Инженерные детали:** 3 LLM-прохода вместо 8 (CPU-экономия): Э1+Э2, Э3 (все линзы), Э5+Э7;
конвейер полностью работоспособен без модели (детерминированные fallback-этапы); результат кэшируется.
SFT-датасет (`export_llm_dataset`) расширен полем `reasoning` — трасса как обучающий сигнал (уровень C).

**Тесты:** `backend/tests/test_reasoning.py` — 14 юнит-тестов по критериям манифеста.
Живой прогон на стенде (Qwen2.5-0.5B, CPU): ~70–90 с, LLM-этапы E1/E2/E3/E7 приняты, E5 честно
детерминирован (в БД нет источников мер); заключение без выдуманных чисел.

**Сверка манифест ↔ реализация (аудит 2026-07-04) — осознанные отклонения v1:**

  `/reports/measures-analytics` (куда фронт шлёт сводку мер) пока работает через одноходовую
