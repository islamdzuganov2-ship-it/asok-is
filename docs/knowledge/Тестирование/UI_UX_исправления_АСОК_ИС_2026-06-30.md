# АСОК ИС — UI/UX исправления (changelog) · 2026-06-30

> Устранение UI/UX-замечаний: паритет дашбордов «Демо ↔ LLM», «Невозможно измерить» с обязательным
> комментарием, SoD по мерам. Все изменения применены в коде и проверены (юнит + живой API).

## 1. Паритет дашбордов и тепловых карт (DEF-09)

**Было:** в режиме LLM/реальная БД дашборды строились иначе, чем в демо (моках):
- имена характеристик из Excel-импорта двоились → теплокарта ≈14 «характеристик» вместо 8
  («Надежность» и «Надёжность», «Эффективность. Показатели…» вместо «Производительность», и т.п.);
- аналитическая теплокарта в live теряла % в ячейках, % в шапке и drill-down (бэкенд не отдавал
  `characteristics`/`systemDetails`);
- управленческая теплокарта показывала длинные имена вместо аббревиатур.

**Стало (как в моках):**
| Слой | Изменение |
|---|---|
| `backend/app/constants/quality_model.py` | `canonical_characteristic()` — нормализация имён к 8 каноническим (ё/е, регистр, префиксы, синонимы) + `ABBR` |
| `backend/app/api/v1/endpoints/assessments.py` `GET /dashboard` | каноническая агрегация: `xAxisLabels`=8, `characteristics`, `systemDetails`, баллы ячеек, серые «невозможно измерить», порядок ИС по числу низких метрик |
| `backend/app/api/v1/reports.py` `GET /executive-dashboard` | нормализация характеристик к 8 |
| `frontend/src/pages/dashboard/ExecutiveDashboard.tsx` | аббревиатуры в шапке теплокарты (паритет с моком) |

**Проверка:** оба эндпоинта в live возвращают ровно 8 характеристик в каноническом порядке;
`systemDetails`/`characteristics` присутствуют; теплокарта `LevelHeatmap` рендерит %/цвета/drill-down,
как в демо. Это также закрывает корневую причину **DEF-02** (расхождение номенклатуры).

## 2. «Невозможно измерить» с обязательным комментарием (DEF-10)

**Было:** в режиме реальной БД нигде нельзя было пометить «невозможно измерить»; в оценке не было
галочки, делающей комментарий обязательным (костыль — `val_b=0`).

**Стало:**
| Слой | Изменение |
|---|---|
| БД | `assessment_values.unmeasurable BOOL` (миграция `004_unmeasurable_flag`; в DEMO добавлено ALTER) |
| Схемы | `EditableMetricIn/Out`, `ValueAddIn` + поле `unmeasurable` |
| API | при `unmeasurable=true` комментарий ОБЯЗАТЕЛЕН (иначе 422 / запись отклонена), `X=NULL`, уровень «Невозможно измерить», `val_a/val_b` очищаются |
| Полнота/finalize | «невозможно измерить» с обоснованием засчитывается как закрытая подхарактеристика |
| `frontend/MetricsInputPage.tsx` | колонки «Невозм. изм.» (чекбокс) + «Комментарий» (обязателен, подсветка; val_a/val_b блокируются) |
| Дашборды | уровень «Невозможно измерить» — серым (как `UNMEASURABLE` в моках) |

**Проверка (живой API, 5/5 PASS):** без комментария → 422; с комментарием → 201, X=null,
уровень «Невозможно измерить»; флаг сохраняется; PUT-валидация; дашборд показывает уровень.

## Итерация 7 (2026-06-30) — эскалация, опц. борды, оценка, суждения, лимит мер, аналитика LLM

Проверено: pytest 31/31, все модули компилируются (Vite 200), новые эндпоинты работают.

### Эскалация (SoD, правильный поток) + визуал Ганта
- Эскалацию инициирует **только QM** (обязательна причина невыполнения/просрочки);
  решение принимает **только топ-менеджмент** — «указание игнорировать» / «запросить доп. меры»;
  после — QM «отрабатывает». `governanceSlice`: `escalateTask` / `decideEscalation` / `resolveEscalation`.
- Колокольчик: топ-менеджеру — «эскалация ожидает решения»; QM — «решение получено — отработать».
- Диаграмма переделана в читаемый таймлайн: линии месяцев + маркер «сегодня», зебра-строки,
  пилюли-бары с градиентом и стартовой точкой, чип «осталось дней»/просрочка, фильтр
  (Активные/Просрочено/Эскалация/Выполнено/Все) со счётчиками, легенда.

### Опциональные борды топ-менеджера (все, кроме «Управленческого»)
- Флаг `execAnalytics` (Аналитический дашборд) + карточка в «Настройка» с мини-превью.
  У топ-менеджера всегда только «Управленческий дашборд» и «Настройка»; Аналитический/Динамика/
  План задач — по галочке.

### Оценка ИС
- Кнопка **«Назад к оценке»** в табличном вводе; контекст ИС/периода сохраняется (localStorage) —
  возврат не «выкидывает» из оценки выбранной системы.
- **Всплывающие подсказки** в табличном вводе: описание подхарактеристики + рекомендуемые артефакты
  (по наведению на метрику), пояснения к колонкам A/B (что и куда вводится).

### Дашборд менеджера по качеству
- **Карточка «Заполненные профессиональные суждения»** внизу (эндпоинт `judgments-filled`),
  связка характеристика + подхарактеристика + система/период, поиск и раскрытие.
- **Лимит мер до 3 самых критичных** (наименьший балл) + «показать все» на карточках
  «Поставленные меры и намерения» и «Выработка мер».

### Углубление аналитики LLM (не перефразирование)
- Бэкенд считает **аналитические факты**: ранжирование зон по критичности, доля от всех мер,
  системные зоны, вывод-приоритеты. LLM оформляет их в связный управленческий вывод; при слабом/
  недостоверном ответе — честный аналитический каркас (уже проранжированный), а не перечисление.

## Итерация 8 (2026-07-05) — BL-001 E1: контур оценки СИИ по ГОСТ Р 59898-2021 (+BL-003)

Второй оценочный контур для систем ИИ, изолированный от ISO 25010. Все критерии приёмки E1
подтверждены живым E2E-прогоном.

| Слой | Реализация |
|---|---|
| Каталог (BL-003) | `modules/quality/ai_quality_model.py` — 4 группы/8 хар./37 субхар./7 ИИ-специфичных, каждой metric_kind + inputs_schema + подсказка |
| Движок | `modules/quality/ai_calculation.py` — A/B, ACCURACY/PRECISION/RECALL/SPECIFICITY/F1, EXPERT_SCALE; нормировка к baseline±ε → X+conformant; Q (равные веса) |
| БД | `systems.system_kind (CLASSIC\|AI)`, таблица `ai_assessment_values` (миграция 006) |
