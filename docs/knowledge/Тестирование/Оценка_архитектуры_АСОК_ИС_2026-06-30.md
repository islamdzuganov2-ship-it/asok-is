# АСОК ИС — Оценка архитектуры: микросервисность и независимость релизов

## Вердикт (кратко)
- **Микросервисность: НИЗКАЯ (~2/10).** Это **модульный монолит** с чистым разделением
  фронтенд / бэкенд / фоновый воркер, но БЕЗ признаков микросервисной архитектуры.
- **Независимость релизов: ЧАСТИЧНАЯ.** Фронтенд и бэкенд релизятся независимо (разные образы,
  контракт через `/api/v1`). Внутри бэкенда модули независимо НЕ релизятся (один процесс, один
  образ, одна БД, общие миграции).

## Фактура (из `docker-compose.yml` и структуры кода)
| Компонент | Деплой-единица | Данные | Вывод |
|---|---|---|---|
| `backend` (FastAPI) | 1 образ `./backend`, 1 процесс, все роутеры (`auth, systems, assessments, metrics, reports, excel, risks`) | общая PostgreSQL | **монолит** |
| `celery_worker` | тот же образ `./backend`, другая команда | та же PostgreSQL, Redis | фоновый воркер монолита, **не отдельный сервис** |
| `frontend` (React SPA) | отдельный образ `./frontend` | — | отдельная деплой-единица |
| `postgres` / `redis` | инфраструктура | единая схема | общее хранилище → **тесная связность** |
| LLM (llama.cpp) | **in-process** внутри backend/celery | — | не сервис; смена модели = редеплой бэкенда |

Признаки, которых НЕТ (микросервисы): API-gateway, service discovery, БД-на-сервис (database per
service), независимое версионирование модулей, межсервисные контракты, распределённые транзакции/саги.

## Насколько независимо можно релизить
- ✅ **Фронтенд ↔ бэкенд** — независимо (два образа, REST-контракт `/api/v1`, same-origin через прокси).
- ✅ **Воркер** — можно перезапустить отдельно, но он делит кодовую базу и БД с бэкендом (версии должны совпадать).
- ❌ **Модули бэкенда** (оценки, отчёты, риски, Excel, LLM) — НЕ независимы: один процесс, один образ,
  общие модели и Alembic-миграции. Изменение в одном модуле → редеплой всего бэкенда.
- ❌ **LLM** — встроена в процесс; обновление модели/логики = редеплой бэкенда (частично смягчено
  `docker-compose.override.yml` с внешним файлом модели, но код инференса — в бэкенде).
- ⚠️ **Схема БД** — единая, без bounded contexts → изменение таблицы затрагивает все модули.

## Оценка (честная)
Для MVP/внутреннего инструмента **модульный монолит — правильный выбор**: проще эксплуатация, одна
БД, простая согласованность данных, быстрая разработка. Микросервисы здесь были бы **преждевременны**
(оверинжиниринг: рост сложности деплоя, распределённые транзакции, сетевые отказы) без выигрыша при
текущем масштабе (десятки ИС, единичные пользователи).

Сильная сторона уже есть: **чистое разделение фронт/бэк/воркер** даёт главный практический бонус
независимых релизов (UI и API катятся отдельно). Модульность бэкенда (`app/api/v1/*`, `services/*`,
`constants/*`) — хорошая база для будущего вычленения сервисов «по команде».

## Рекомендации (по возрастанию зрелости, без преждевременной миграции)
1. **Оставить монолит**, но зафиксировать границы модулей (bounded contexts) и запретить перекрёстные
   импорты между доменами — чтобы будущее вычленение было дешёвым.
2. **Вынести LLM в отдельный сервис/сайдкар** (независимый цикл обновления модели, изоляция ресурсов
   CPU/RAM инференса от API). Наибольший ROI по независимости релизов.
3. **Контрактные тесты фронт↔бэк** (OpenAPI + schemathesis/pact) — чтобы независимые релизы двух
   тиров не ломали друг друга. Сейчас интеграционных автотестов нет (см. DEF-«тестируемость»).
4. **Версионирование API** (`/api/v1` уже есть) + политика обратной совместимости.
5. Если появится масштаб/разные SLA — кандидаты на вычленение: **Excel-импорт/отчёты** (тяжёлые,
   пакетные) и **База рисков** (иной цикл изменений). Не раньше, чем это оправдано нагрузкой.

## Связь с оценкой качества АСОК ИС
Это подтверждает результаты самооценки (Q3-2026): **Сопровождаемость 56%** (модульность есть, но
тестируемость 30% — нет интеграционных тестов на стыках), **Переносимость 77%** (Docker — плюс к
независимости развёртывания). Микросервисность низкая — но осознанно и уместно для текущей стадии.
