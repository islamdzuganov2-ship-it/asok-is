## DEF-01 🔴 Critical — LLM-инференс не работает (несовместимость модели и рантайма)

**Где:** `models/llm/asok-model.gguf`, `backend/app/services/llm_service.py`, `backend/requirements.txt`.

**Симптом:** `GET /api/v1/reports/llm-status` → `available=false`. В логах backend:
```
llama_model_load: error loading model: error loading model architecture:
unknown model architecture: 'qwen35'
ValueError: Failed to load model from file: models/llm/asok-model.gguf
```

**Корневая причина:** развёрнутый файл модели — «Qwen3.5 9B» с метаданными GGUF
`general.architecture = qwen35`, `general.name = Qwen_Qwen3.5 9B` (5.3 ГБ).
Архитектура `qwen35` **нестандартна** (в llama.cpp есть `qwen2`/`qwen3`, но не `qwen35`) и не
поддерживается ни установленным `llama-cpp-python==0.2.90`, ни любой текущей стабильной сборкой.
Дополнительно — трёхстороннее расхождение документации о модели:
- `requirements.txt` (коммент) — «Qwen2.5-1.5B-Instruct Q4_K_M (~1 ГБ)»;
- `docs/LLM_SETUP.md` — «Qwen 9B Q4_K_M ~5.5 ГБ»;
- фактически развёрнута «Qwen3.5 9B» (`qwen35`).

**Влияние:** ключевая фича «AI-резюме встроенной LLM» не выполняет реальный инференс. Система
корректно деградирует на честный grounded-fallback (это правильное поведение, без падений), но
заявленная LLM-аналитика не работает.

**Исправление (выполнено):**
1. Документация и конфиг приведены к реальности и согласованы: `requirements.txt`,
   `docs/LLM_SETUP.md`, `backend/app/core/config.py`, `backend/app/services/llm_service.py`
   — указана поддерживаемая модель **Qwen2.5-1.5B-Instruct Q4_K_M** (arch `qwen2`) и явное
   предупреждение про `qwen35`.
2. Для рабочего инференса развёрнута стандартная модель Qwen2.5-1.5B-Instruct Q4_K_M —
   **загружается и отвечает** (демонстрация: [[Демонстрация_LLM_АСОК_ИС_2026-06-30]]).

**Рекомендация эксплуатации:** заменить `asok-model.gguf` на Qwen2.5-1.5B-Instruct Q4_K_M
(стандартный `qwen2`, помещается в лимит памяти контейнера ≈5.8 ГБ). Если нужен именно 9B/Qwen3 —
обновить `llama-cpp-python` до ≥0.3.x с поддержкой `qwen3` и пересобрать образ (компиляция),
но arch `qwen35` всё равно непереносима — требуется корректная конвертация модели.

## DEF-02 🟠 High — Демо-данные не финализируемы; теплокарта замусорена

**Где:** `backend/app/services/excel_importer.py` (`import_quality_timeline`, `get_or_create_metric`), демо-данные в БД.

**Симптом:**
- `GET /assessments/periods/summary` → у всех периодов `filled=0/31`, `complete=false`, при этом
  статус `CALCULATED` (значения есть). `POST /finalize` для демо-периодов всегда 409.
- Управленческая теплокарта строится по ~14 «характеристикам» вместо канонических 8.

**Корневая причина:** Excel-импорт сохраняет имена характеристик «как есть», без приведения к
эталонной модели. В БД сосуществуют варианты, не совпадающие с `QUALITY_PAIR_KEYS`:
`Надежность` (е) и `Надёжность` (ё); `Безопасность` vs `Защищённость`;
`Эффективность. Показатели временных Характеристик` (вместо `Производительность`);
`Удобство использования. Показатели полноты описания`; `Пригодность для обслуживания`
(вместо `Сопровождаемость`); подхарактеристика `Тестируемость` использована как характеристика.
Так как `finalize`/summary считают только пары из эталона, импортированные данные «осиротевшие».

**Влияние:** governance-цикл (полнота → finalize) для демо-данных недостижим; KPI на дашбордах
считается по «размазанной» номенклатуре; дубликаты характеристик искажают картину для руководства.

**Рекомендация:** ввести нормализацию имён к канонической модели при импорте (словарь синонимов
характеристик/подхарактеристик + унификация `ё`→`е` при сравнении) в `get_or_create_metric`;
для уже загруженных данных — разовая миграция-сопоставление. Подтверждено эмпирически: при
**чистых канонических именах** `finalize` достигает 31/31 и переводит период в `COMPLETE`
(TC-FIN-02 PASS).

## DEF-03 🟡 Medium — celery_worker постоянно unhealthy ✅ ИСПРАВЛЕНО

**Где:** `backend/dockerfile` (`HEALTHCHECK curl :8000`), `docker-compose.yml` (`celery_worker`).

**Корневая причина:** воркер использует образ backend, наследуя его `HEALTHCHECK`
(`curl http://localhost:8000/health`). У воркера нет HTTP-порта → проверка падает всегда
(`FailingStreak=43`, `Failed to connect to localhost port 8000`). Сам воркер исправен.

**Исправление:** в `docker-compose.yml` для `celery_worker` добавлен корректный healthcheck:
```yaml
healthcheck:
  test: ["CMD-SHELL", "celery -A app.workers.tasks.celery_app inspect ping -t 10 | grep -q pong || exit 1"]
```
**Ретест:** после `docker compose up -d celery_worker` → `asok_celery: Up (healthy)`. **PASS.**

## DEF-04 🟡 Medium — Асинхронный импорт Excel не сохраняет данные

**Где:** `backend/app/workers/tasks.py::parse_excel_task`, `backend/app/api/v1/excel_upload.py::upload_excel`.

**Корневая причина:** `POST /excel/upload` ставит задачу `parse_excel_task.delay(...)`, но сама
задача только парсит и возвращает счётчики (`return {"status":"COMPLETED","imported":N}`) —
**в БД ничего не пишет**. Реально сохраняет данные только синхронный `/excel/import-assessment`.
Жёсткие заголовки задачи (`metric_id|val_a|val_b`) расходятся с гибким маппингом синхронного пути.

**Влияние:** пользователь видит «задача COMPLETED, импортировано N», но значения не появляются.

**Рекомендация:** реализовать запись в БД внутри `parse_excel_task` (через sync-сессию) либо
убрать асинхронный путь до его реализации, оставив синхронный `/import-assessment`.

## DEF-05 🟢 Low — Несогласованные единицы globalHealthScore

**Где:** `reports.py::get_executive_dashboard` (0–100, напр. `59.76`) vs

## DEF-06 🟢 Low — seed_iso25010 не обновлял data_source ✅ ИСПРАВЛЕНО

**Где:** `backend/app/scripts/seed_iso25010.py` (ветка обновления существующей пары).

**Корневая причина:** при обновлении уже существующей канонической пары seed выставлял
`formula_type`/`is_active`, но **не** `data_source`. Если пара ранее заведена из Excel/UI
(напр. «Надёжность/Доступность (uptime)», `data_source=ASSESSMENT_UI`), она «терялась» из
фильтра `data_source='ISO25010'` → в каталоге числилось 30 из 31 канонической пары.

**Исправление:** в ветке обновления добавлено `metric.data_source = "ISO25010"`.
**Ретест:** повторный seed → `SELECT count(*) WHERE data_source='ISO25010'` = **31** (было 30). **PASS.**

## DEF-08 🟢 Low — Семантика «0% качества» vs «нет данных»

**Где:** `backend/app/services/calculation_engine.py::map_to_level`.

**Суть:** `map_to_level(0.0)` возвращает «Невозможно измерить». Но честно измеренный 0%
(напр. DIRECT `a=0, b=100` → X=0.0) тоже попадает в «Невозможно измерить», смешиваясь с «нет
данных». Сейчас это соответствует текущему ТЗ и юнит-тесту `test_map_to_level`.
**Рекомендация (уточнение ТЗ):** развести «нет измерения» (значения не введены) и «измерено 0%»
(«Низкий уровень»), если бизнес-смысл этого требует.
