# АСОК ИС — Ролевая модель (детальное ТЗ)

> Канонический источник по ролям и правам. Синхронизирован с кодом
> (`backend/app/api/deps.py`, `backend/app/models/user.py`, фронтовые роуты/меню/governance)
> и руководством пользователя ([[АОК ИС/Руководство пользователя/00_Индекс]]).

---

## 1. Назначение и принципы

АСОК ИС реализует **контур управления качеством информационных систем (ИС)**: данные о
качестве собираются, превращаются в управленческие меры и доводятся до исполнения под
контролем руководства. Ролевая модель обеспечивает, чтобы каждый участник видел и делал
ровно то, что относится к его зоне ответственности.

Принципы:
1. **Минимум привилегий** — роль получает только необходимый доступ.
2. **Разделение обязанностей (SoD)** — кто фиксирует данные, не принимает решение по мере;
   кто решает, не отчитывается о выполнении. Это исключает конфликт интересов.
3. **Нейминг по уровню, а не по титулу** — верхний уровень не привязан к конкретной должности
   (CIO/CTO/CEO/директор), чтобы корректно охватывать любого ЛПР.
4. **Стабильность кодов** — внутренние коды ролей не меняются (токены/БД), меняются только подписи.

## 2. Три канонические роли

| Код роли (внутр.) | Подпись в интерфейсе | Уровень | Кратко |
|---|---|---|---|
| `ADMIN` | **Топ-менеджмент** | Стратегический | Видит картину качества, принимает решения по мерам, задаёт приоритеты и ресурсы, администрирует систему. |
| `QUALITY_MANAGER` | **Менеджер по качеству** | Тактический | Формирует профессиональные суждения, ставит меры, контролирует их выполнение, ведёт базу рисков. |
| `TEST_ANALYST` | **Аналитик** | Операционный | Собирает и вводит исходные данные качества (val_a/val_b), грузит Excel, готовит расчёты. |

### 2.1 Маппинг легаси-ролей
Ранее в коде встречались `CTO`, `CEO`, `CIO`, `EXECUTIVE`. Все они — **верхний уровень** и по
доступу приравниваются к роли **Топ-менеджмент** (`ADMIN`-tier). Новые учётные записи создаются
только в трёх канонических ролях; легаси-коды принимаются как алиасы для обратной совместимости.

## 3. Детальное описание ролей

### 3.1 Топ-менеджмент (`ADMIN`)
**Кто:** лицо, принимающее решения верхнего уровня (руководство ИТ/качества). Нейминг намеренно
обобщённый — «Топ-менеджмент» — чтобы не привязываться к титулу.

**Зачем нужен:** превращает картину качества в управленческие решения — что приоритизировать,
кому поручить, в какой срок; контролирует динамику технического долга.

**Что видит и делает:**
- **Управленческий дашборд** (полный доступ): общий индекс качества ИТ-ландшафта, топ проблемных
  ИС по критичности, тепловая карта характеристик, статус технического долга, реестр мер.
- **Решения по мерам качества:** одобряет/отклоняет меры менеджера по качеству с обязательной
  возможностью оставить комментарий; до решения может **изменить ответственного и срок**.
- **Контроль выполнения:** видит результат («Выполнено»/«Не выполнено» + комментарий менеджера),
  но **сам не отмечает выполнение** (это зона менеджера по качеству).
- **Аналитический дашборд** (чтение), **Настройки/администрирование** (фиче-флаги, пользователи,
  сервисные операции).

**Чего НЕ делает:** не вводит первичные метрики (это аналитик), не формирует профессиональные
суждения и не ставит меры (это менеджер по качеству), не отмечает факт выполнения.

### 3.2 Менеджер по качеству (`QUALITY_MANAGER`)
**Кто:** ответственный за методику и качество ИС.

**Зачем нужен:** связующее звено между данными и решениями — интерпретирует метрики, фиксирует
профессиональное суждение, ставит меры и контролирует их фактическое выполнение.

**Что видит и делает:**
- **Дашборд менеджера по качеству:** выбор ИС из списка, разбор по характеристикам и метрикам.
- **Профессиональное суждение:** по метрике/подхарактеристике фиксирует обоснование, при
  необходимости вручную корректирует уровень и **ставит меру** (карточка риска: формулировка,
  ответственный ФИО + должность, срок). Мера уходит топ-менеджменту со статусом «ожидает решения».
- **Контроль выполнения:** по одобренной мере отмечает **«Выполнено»/«Не выполнено» с обязательным
  комментарием** (как выполнено или почему нет). Только эта роль закрывает выполнение.
- **База рисков:** создание/редактирование/архивация записей (накопительная база знаний для LLM).
- **Оценка ИС, отчёты, аналитический дашборд** — доступны.

**Чего НЕ делает:** не принимает решение по собственным мерам (исключение «сам себе одобрил»);
не меняет ответственного/срок после постановки (это право топ-менеджмента до решения).

### 3.3 Аналитик (`TEST_ANALYST`)
**Кто:** тест-аналитик / специалист, собирающий первичные данные.

**Зачем нужен:** обеспечивает достоверные исходные данные, на которых строится вся оценка.

**Что видит и делает:**
- **Оценка ИС (рабочее место):** добавление ИС и метрик, создание оценочного периода.
- **Ручной ввод метрик:** значения `val_a` (факт) и `val_b` (план/база) по каждой метрике;
  система рассчитывает коэффициент X и уровень качества.
- **Загрузка Excel:** массовый импорт значений; **экспорт отчётов** (CSV).
- **Аналитический дашборд** (чтение), **база рисков** (чтение).

**Чего НЕ делает:** не формирует суждений и мер, не принимает решений, не отмечает выполнение,
не видит управленческий и менеджерский дашборды.

## 4. Матрица прав (resource × role)

**C** — создание · **R** — чтение · **U** — изменение · **D/Arch** — удаление/архив · «—» — нет доступа.

| Ресурс / действие | Топ-менеджмент | Менеджер по качеству | Аналитик |
|---|:--:|:--:|:--:|
| Управленческий дашборд | R | — | — |
| Дашборд менеджера по качеству | R | R | — |
| Аналитический дашборд | R | R | R |
| Настройки / фиче-флаги | R·U | — | — |
| Пользователи (администрирование) | C·R·U·D | — | — |
| ИС (системы) | C·R·U·D | C·R | C·R |
| Метрики каталога | C·R·U | C·R | C·R |
| Оценочный период | C·R | C·R | C·R |
| Ввод val_a / val_b (ручной) | R | R·U | **C·R·U** |
| Импорт Excel | R | C | C |
| Экспорт отчётов (CSV/реестры) | R | R | R |
| Профессиональное суждение | R | **C·R** | — |
| Мера качества (постановка) | R | **C·R** | — |
| Решение по мере (одобрить/отклонить + коммент.) | **C·U** | — | — |
| Смена ответственного/срока (до решения) | **U** | — | — |
| Контроль выполнения (выполнено/не выполнено + коммент.) | R | **C·U** | — |
| База рисков | R·C·U·Arch | **C·R·U·Arch** | R |
| Реестр мер качества | R (+решение) | R | — |

## 5. Жизненный цикл меры качества (state machine)

```
[Аналитик] вводит данные
        │
        ▼
[Менеджер по качеству] профессиональное суждение + постановка меры
        │  (status = PENDING_APPROVAL — «ожидает решения»)
        ▼
[Топ-менеджмент] решение (может скорректировать ответственного/срок)
   ├─ одобрить → status = APPROVED  (+ комментарий ЛПР)
   └─ отклонить → status = REJECTED (+ комментарий ЛПР)
        │
        ▼ (только для APPROVED)
[Менеджер по качеству] отчёт о выполнении
   ├─ Выполнено    → execution = DONE     (+ обязательный комментарий)
   └─ Не выполнено → execution = NOT_DONE (+ обязательный комментарий «почему»)
        │
        ▼
[Топ-менеджмент] видит статус техдолга: ожидают решения / одобрено-ждут выполнения /
                 выполнено / просрочено-не выполнено; burndown и выбор периода (год/квартал)
```

**SoD-инварианты (зашиты в логику):**
1. Меру создаёт менеджер по качеству, решение принимает топ-менеджмент — нельзя одобрить свою меру.
2. Отчёт о выполнении даёт только менеджер по качеству; топ-менеджмент видит результат, но не отмечает.
3. Менять ответственного и срок до решения может только топ-менеджмент.

## 6. Где enforced (точки контроля)

**Backend** (`app/api/deps.py::require_role`):
- `risk_base` создание/изменение/архив — `QUALITY_MANAGER`, `ADMIN`;
- импорт Excel (`/excel/*`) — `TEST_ANALYST`, `QUALITY_MANAGER`, `ADMIN`;
- сидинг проектных файлов — `ADMIN`.
- `models/user.py` хранит коды ролей; в DEMO_MODE при отсутствии токена пользователь трактуется
  как ADMIN (только для демо; в проде отключается — см. ИБ-бэклог).

**Frontend** (`App.tsx`):
- `RequireRole` на роутах: управленческий — топ-менеджмент; менеджерский — менеджер по качеству;
  оценка ИС — аналитик/менеджер/топ; настройки — топ-менеджмент;
- ролевой `DashboardRouter` ведёт каждого на «свой» дашборд;
- governance-логика: решение по мере — топ-менеджмент; контроль выполнения — менеджер по качеству.

## 7. Нейминг (правила)
- Внутренние коды: `ADMIN`, `QUALITY_MANAGER`, `TEST_ANALYST` — не менять.
- Подписи: **Топ-менеджмент / Менеджер по качеству / Аналитик** — единый источник
  `frontend/src/constants/roles.ts` (без разнобоя в строках).
- В интерфейсе показываем подпись, а не код.

## 9. Предложения по развитию (по команде)
1. **Разделить `ADMIN`** на «Топ-менеджмент» (бизнес-решения) и «Системный администратор»
   (пользователи, фиче-флаги, сидинг) — чистый SoD при появлении выделенного админа.
2. **Роль «Ответственный исполнитель»** — чтение мер и отметка факта по своим задачам, если
   исполнение делегируется вне менеджера по качеству.
3. **Журнал ИБ-событий по ролям** — кто и какое действие совершил (аудит, безопасность).
4. **LDAP/SSO-маппинг** групп каталога на три роли.
