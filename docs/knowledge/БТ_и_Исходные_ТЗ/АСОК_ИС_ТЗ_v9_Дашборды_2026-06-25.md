# АСОК ИС — ТЗ v9: Управленческий дашборд (C-Level) и Менеджер по качеству

> Обогащение методики МК_8.1 требованиями к двум ролевым интерфейсам + решения по
> оптимизации кода из ревью. Связь: [[АСОК_ИС_три_дашборда_рефакторинг]],
> [[АСОК_ИС_Code_Review_v7_2026-05-25]], [[АСОК_ИС/00_Главный_Индекс]].

## Проблемные зоны исходного ТЗ
- **P1** один дашборд на все роли → C-Level видит сырьё аналитика.
- **P2** нет петли «суждение менеджера → одобрение топ-менеджментом».
- **P3** суждение не привязано к под-характеристике, не порождает задачу/риск.
- **P4** нет «нативной» подачи проблемы + рекомендации к действию.
- **P5** кричащая палитра против требования «спокойные тона».
- **P6** рассинхрон ключа токена (`token` vs `asok_access_token`) — дашборд не грузился.
- **P7** отсутствуют эндпоинты `/dashboard/{role}`, `/metrics/{id}/judgment`.

## Управленческий дашборд (R1)
Gauge общего индекса (спокойная шкала) · ТОП-3 проблемных ИС (AI-резюме + 1 рекомендация) ·
тепловая карта RAG · Risks Burndown. По клику — модал: **кто виноват / с кого спрашивать /
рекомендуемые действия + меры менеджера на одобрении**. Минимум текста и цвета.

## Менеджер по качеству (R2)
Выбор ИС/характеристики · Gauge характеристики · таблица метрик (расчётный % / уровень) ·
модал **«Профессиональное суждение»** (обоснование + чекбокс «Создать карточку риска» →
риск/ответственный/срок). Меры уходят топ-менеджменту со статусом **«ожидает одобрения»**
с явной формулировкой «что ожидается и почему».

## Governance-петля
`governanceSlice` (Redux + localStorage). Менеджер создаёт меру `PENDING_APPROVAL` →
Executive `APPROVED/REJECTED`. Интерфейс совместим с будущим
`POST /metrics/{id}/judgment` + `PATCH /governance/proposals/{id}`.

## Решения по оптимизации (из ревью)
- O1 lazy-загрузка ролевых дашбордов; O2 `echarts-for-react` вместо ручного `echarts.init`;
- O3 единая спокойная RAG-палитра `theme/ragPalette.ts`; O4 governance-persist без бэкенда;
- O5 cache-invalidation одобрения; O6 ролевая навигация в `AppLayout`.
