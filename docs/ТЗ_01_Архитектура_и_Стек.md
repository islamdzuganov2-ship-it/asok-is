## 1. Назначение системы

### 1.1. Общее описание

АСОК ИС (Автоматизированная Система Оценки Качества Информационных Систем) — программный комплекс, предназначенный для автоматизации процессов оценки, мониторинга и управления качеством информационных систем в банковской среде. Система реализует методологию оценки качества на основе международного стандарта **ISO/IEC 25010:2023** (модель качества продукта) и национального стандарта **ГОСТ Р 59898-2021** (качество автоматизированных информационных систем).

Система заменяет ручной процесс оценки качества ИС, который традиционно включает:

- сбор метрик из разрозненных источников (Excel-таблицы, отчёты служб эксплуатации, данные мониторинга);
- ручной расчёт интегральных показателей качества по формулам стандарта;
- подготовку аналитических отчётов для руководства;
- формирование мер по повышению качества на основании экспертных суждений.

АСОК ИС автоматизирует весь цикл: от загрузки исходных данных до генерации рекомендаций с использованием локальной LLM (Large Language Model), при этом обеспечивая прозрачность расчётов и аудируемость результатов.

### 1.2. Целевые пользователи

Система реализует **три канонические роли** (подробно — в [ТЗ-02](./ТЗ_02_Ролевая_Модель_и_Безопасность.md)):

| Роль (код) | Подпись в UI | Описание | Ключевые сценарии |
|------------|--------------|----------|-------------------|
| **`ADMIN`** | Топ-менеджмент | Руководитель ИТ-подразделения / CIO / CTO / CEO | Просмотр исполнительных дашбордов с LLM-аналитикой, утверждение и отклонение мер, эскалация решений, администрирование |
| **`QUALITY_MANAGER`** | Менеджер по качеству | Специалист по качеству ИС | Создание оценок, внесение метрик, предложение корректирующих мер, профессиональные суждения |
| **`TEST_ANALYST`** | Аналитик | Тестировщик / аналитик данных | Загрузка данных (Excel/CSV), просмотр дашбордов, работа с реестром инцидентов |

> **Legacy-коды.** Коды `CTO`, `CEO`, `CIO`, `EXECUTIVE` исторически присутствуют в БД и токенах; все они приравнены к уровню `ADMIN` (см. `frontend/src/constants/roles.ts`, `backend/app/modules/iam/models.py`). Новые учётные записи создаются только с каноническими кодами.

Целевые организации — **банки, финансовые институты и кредитные организации**, для которых критически важно:

- соответствие требованиям регулятора (ЦБ РФ);
- управление качеством и рисками ИТ-ландшафта;
- обеспечение непрерывности бизнес-процессов, зависящих от ИС.

### 1.3. Ключевая бизнес-ценность

1. **Автоматизация расчётов.** Интегральные показатели качества (по характеристикам и подхарактеристикам ISO 25010) рассчитываются автоматически по формулам стандарта, исключая человеческий фактор.

2. **LLM-аналитика.** Локально развёрнутая языковая модель (on-premise, без передачи данных вовне) формирует:
   - объяснения причин отклонений метрик;
   - рекомендации по мерам повышения качества;
   - анализ рисков и прогнозы деградации;
   - профессиональные суждения (reasoning) по многоаспектной методологии.

3. **Управление рисками.** База рисков с триггерами, привязанными к пороговым значениям метрик, обеспечивает проактивное выявление угроз качеству.

4. **Прозрачность для регулятора.** Все расчёты, суждения и решения сохраняются с аудиторским следом (audit trail), что обеспечивает воспроизводимость и проверяемость результатов.

5. **Управление мерами и разделение ответственности (SoD).** Система governance обеспечивает полный цикл: предложение мер -> согласование -> утверждение -> контроль исполнения, с разделением полномочий между ролями.

6. **Аналитика технических сбоев.** Модуль инцидентов позволяет отслеживать технические сбои ИС, анализировать их влияние на показатели качества и формировать отчёты для руководства.

- **Полностью асинхронный стек**: FastAPI + SQLAlchemy async + asyncpg. Все эндпоинты — `async def`, сессии БД — `AsyncSession`. Это обеспечивает высокую пропускную способность при I/O-bound нагрузке (обращения к БД, LLM-инференс).

- **JWT-аутентификация**: stateless-токены, роль пользователя закодирована в payload.
- **Celery для тяжёлых задач**: импорт Excel-матриц (до нескольких тысяч строк), LLM-reasoning (генерация суждений по каждой подхарактеристике) — выполняются в фоновом воркере, не блокируя API.

### 2.4. LLM-инференс

Система использует **модель-агностичный** подход к LLM:

```
models/
├── llm/           # Каталог GGUF-моделей (read-only в контейнере)
│   └── *.gguf     # Любая совместимая модель (Qwen3, LLaMA, Gemma2, Phi3, Mistral...)
└── llm_brain/     # «Резервный мозг» — память, корпус, фидбэк (writable, переносимо)
```

**Ключевые свойства:**

- **Рантайм `llama-cpp-python` 0.3.x** — поддерживает современные архитектуры: Qwen2/Qwen3, LLaMA 3.x, Gemma 2, Phi-3, Mistral, StableLM и др.
- **Переключение модели** — замена GGUF-файла в `models/llm/` + перезапуск контейнера. Никаких изменений в коде.
- **CPU-инференс по умолчанию** — готовое wheel без компиляции llama.cpp. GPU/CUDA — отдельный Docker-образ (`dockerfile.cuda` + `docker-compose.gpu.yml`).
- **On-premise** — модель работает локально, данные не покидают контур банка.
- **«Резервный мозг» (`llm_brain/`)** — хранилище обучающих примеров, корпуса знаний и фидбэка. Переносимо между моделями (при смене GGUF brain не теряется).

## 3. Архитектура — модульный монолит

### 3.1. Обоснование выбора (ADR-001)

Для АСОК ИС выбрана архитектура **модульного монолита** (Modular Monolith). Это осознанное архитектурное решение, зафиксированное в ADR-001, основанное на следующих факторах:

**Почему НЕ микросервисы:**

| Фактор | Микросервисы | Модульный монолит |
|--------|-------------|-------------------|
| Команда | Требует 3+ команд | 1-2 разработчика — оптимально |
| Инфраструктура | Kubernetes, service mesh, API gateway | Docker Compose — достаточно |
| Транзакции | Saga, eventual consistency | ACID-транзакции в одной БД |
| Развёртывание | CI/CD для каждого сервиса | Единый образ, единый deploy |
| Отладка | Distributed tracing (Jaeger) | Обычный стек-трейс |
| On-premise | Сложная инсталляция у клиента | `docker compose up` — готово |

**Почему модульный монолит, а не классический монолит:**

- **Изоляция доменов**: каждый модуль — отдельный пакет Python со своей моделью данных, бизнес-логикой и API.
- **Контролируемые зависимости**: явные правила импорта между модулями (проверяются architecture-тестами).
- **Путь к микросервисам**: если потребуется масштабирование отдельных модулей (например, `llm`), модуль можно извлечь в отдельный сервис без рефакторинга остальной системы.
- **ISO 25010 maintainability**: модульность системы — это применение стандарта качества к самой себе.

### 3.2. Структура модулей

Система состоит из **10 доменных модулей** + инфраструктурного ядра:

```
backend/app/
├── main.py                  # Точка входа FastAPI
├── config.py                # Конфигурация (Pydantic Settings)
├── database.py              # Async engine + session factory
├── dependencies.py          # Общие зависимости (get_db, get_current_user)
├── seed.py                  # Инициализация демо-данных
└── modules/
    ├── __init__.py
    ├── iam/                 # Идентификация и управление доступом
    │   ├── models.py        # User (SQLAlchemy)
    │   ├── schemas.py       # Pydantic-схемы
    │   ├── service.py       # Бизнес-логика
    │   ├── router.py        # FastAPI-эндпоинты
    │   └── auth.py          # JWT, хэширование паролей
    ├── systems/             # Реестр информационных систем
    ├── quality/             # Модель качества (ISO 25010)
    ├── assessment/          # Оценка (периоды, метрики, расчёты)
    ├── governance/          # Меры, решения, SoD, эскалация
    ├── risk/                # База рисков и триггеры
    ├── reporting/           # Отчёты и дашборды
    ├── dataio/              # Импорт/экспорт Excel/CSV
    ├── llm/                 # LLM-сервис, мозг, шлюз правил
    └── incidents/           # Аналитика технических сбоев
```

### 3.3. Описание модулей

#### 3.3.1. `iam` — Идентификация и управление доступом

**Ответственность:** управление пользователями, ролями, аутентификация, авторизация.

- Модель `User`: UUID PK, username, email, password_hash, role, is_active, soft-delete.
- JWT-аутентификация: access-токен с payload `{sub: user_id, role: role}`.
- Ролевая модель: 5 ролей (`admin`, `manager`, `analyst`, `auditor`, `viewer`), проверка через FastAPI-зависимости.
- Хэширование паролей: bcrypt через passlib.
- CRUD: создание/редактирование/деактивация пользователей (только admin).

**API:** `POST /api/auth/login`, `GET /api/users/me`, `GET /api/users`, `POST /api/users`, `PUT /api/users/{id}`.

#### 3.3.2. `systems` — Реестр информационных систем

**Ответственность:** ведение реестра ИС банка — карточки систем с атрибутами.

- Модель `InformationSystem` (таблица `systems`): name, code (уникальный), status_lc (стадия жизненного цикла: ОЭ, ПЭ, Создание и тестирование), criticality_class (MISSION CRITICAL, BUSINESS CRITICAL, BUSINESS OPERATIONAL), owner.
- CRUD с soft-delete.
- Фильтрация по статусу и классу критичности.

**API:** `GET /api/systems`, `POST /api/systems`, `PUT /api/systems/{id}`, `DELETE /api/systems/{id}`.

#### 3.3.3. `quality` — Модель качества

**Ответственность:** справочник характеристик, подхарактеристик и метрик качества по ISO 25010 и ГОСТ Р 59898-2021.

- Модель `MetricCatalog` (таблица `metric_catalog`): characteristic, subcharacteristic, formula_type (DIRECT/INVERSE), description, data_source.
- Дерево качества: 8 характеристик ISO 25010 (Функциональная пригодность, Эффективность производительности, Совместимость, Удобство использования, Надёжность, Безопасность, Сопровождаемость, Переносимость), каждая с подхарактеристиками.
- Поддержка ГОСТ Р 59898 — дополнительные характеристики, специфичные для АИС.
- Формула расчёта: DIRECT (чем больше, тем лучше) и INVERSE (чем меньше, тем лучше) — нормализация в шкалу [0, 1].

**API:** `GET /api/quality/metrics`, `GET /api/quality/tree`.

#### 3.3.4. `assessment` — Оценка

**Ответственность:** периоды оценки, значения метрик, расчёт интегральных показателей.

- Модель `Period`: привязка к системе + временной диапазон (квартал/год). Поле `period_sort_key` для определения «последнего периода».
- Модель `MetricValue`: значение метрики в конкретном периоде для конкретной ИС. Поддержка флага `is_unmeasurable` (невозможно измерить).
- Расчёт интегральных показателей:
  - Уровень подхарактеристики: среднее арифметическое нормализованных значений метрик.
  - Уровень характеристики: среднее взвешенное подхарактеристик (веса E2 — настраиваемые, миграция 007).
  - Интегральное качество Q: среднее взвешенное характеристик.
- Сравнение с предыдущими периодами (дельта, деградация).

**API:** `GET /api/assessment/periods`, `POST /api/assessment/calculate`, `GET /api/assessment/results/{system_id}/{period_id}`.

#### 3.3.5. `governance` — Управление мерами

**Ответственность:** полный цикл управления мерами по повышению качества, разделение ответственности (Separation of Duties).

- Модель `Measure` (таблица `proposals`, миграция 008): текст меры, статус (draft, proposed, approved, rejected, in_progress, completed), привязка к характеристике/подхарактеристике, автор, утверждающий.
- Модель `Decision`: решение по мере (approve/reject), обоснование, ссылка на утверждающего.
- **SoD (Separation of Duties)**: автор меры НЕ может быть её утверждающим. Аналитик предлагает — руководитель утверждает.
- **Эскалация**: нерассмотренные меры эскалируются при превышении SLA.
- Frontend: Redux async thunks, `useAppDispatch`.

**API:** `POST /api/governance/measures`, `PUT /api/governance/measures/{id}/approve`, `PUT /api/governance/measures/{id}/reject`.

#### 3.3.6. `risk` — База рисков

**Ответственность:** управление рисками, привязанными к качеству ИС.

- Модель `RiskEntry` (миграция 003): описание риска, категория, привязка к характеристике, пороговые значения (trigger_threshold), уровень критичности, статус (active, mitigated, accepted).
- Триггеры: автоматическая активация рисков при выходе метрик за пороговые значения.
- Связь с мерами (`governance`): каждая мера может быть привязана к одному или нескольким рискам.

**API:** `GET /api/risks`, `POST /api/risks`, `PUT /api/risks/{id}`.

#### 3.3.7. `reporting` — Отчёты и дашборды

**Ответственность:** формирование аналитических отчётов и визуализаций.

Виды отчётов:

| Отчёт | Аудитория | Содержание |
|-------|-----------|------------|
| **Руководительский** | CIO/CTO | Общая картина по всем ИС, светофорные индикаторы, ключевые риски |
| **Менеджерский** | Руководитель направления | Детализация по конкретной ИС, характеристики и метрики |
| **Динамика** | Аналитик | Сравнение периодов, тренды, метки мер на графиках |
| **Сбои** | Аналитик / Руководитель | Аналитика технических инцидентов |

- Экспорт в Excel (через `dataio`).
- Графики: радарные диаграммы характеристик, столбчатые графики динамики, тепловые карты рисков.

**API:** `GET /api/reports/executive`, `GET /api/reports/manager/{system_id}`, `GET /api/reports/dynamics/{system_id}`.

#### 3.3.8. `dataio` — Импорт/Экспорт данных

**Ответственность:** загрузка данных из Excel/CSV и выгрузка результатов.

- **Синхронный импорт**: небольшие файлы (до 100 строк) — обработка в контексте HTTP-запроса.
- **Асинхронный импорт**: крупные матрицы (Excel) — через Celery-задачу, статус отслеживается через polling.
- Поддержка Excel-матриц оценки (миграция 002): предзаполненные шаблоны с метриками.
- Экспорт: генерация Excel-файлов с результатами оценки.
- Автоматический сид демо-данных: `seed_project_excel_files()` — загружает Excel из volume (если файлы присутствуют).

**API:** `POST /api/dataio/import/excel`, `GET /api/dataio/export/{system_id}/{period_id}`, `GET /api/dataio/tasks/{task_id}`.

#### 3.3.9. `llm` — LLM-сервис

**Ответственность:** инференс языковой модели, шлюз правил, reasoning, база знаний.

Структура модуля:

| Файл | Назначение |
|------|------------|
| `service.py` | Инициализация модели, inference API |
| `gate.py` | Детерминированный шлюз правил (Rule Engine) |
| `reasoning.py` | Multi-aspect reasoning (BL-005) |
| `brain.py` | «Резервный мозг» — память, корпус, фидбэк |
| `knowledge.py` | База знаний (RAG-подобная) |
| `prompts.py` | Шаблоны промптов |
| `dataset.py` | Управление обучающим датасетом |
| `tasks.py` | Celery-задачи (фоновый reasoning) |

**Архитектура «Gate → LLM → Explanation»:**

```
Данные оценки (метрики, дельты, anomalies)
        │
        ▼
   Gate (Python) — детерминированные правила:
   • Q < порог критического уровня → Severity: HIGH
   • Измерено < 70% подхарактеристик → Coverage: LOW
   • Деградация к пред. периоду → Regression: FAILED
        │
        ▼
   LLM — ОБЪЯСНЯЕТ вердикт Gate:
   • Причины отклонений
   • Анализ рисков
   • Рекомендации по мерам
   • НЕ МОЖЕТ отменить вердикт Gate
        │
        ▼
   Суждение (ProfessionalJudgment) — сохраняется в БД
```

**Ключевой инвариант:** решение (сработало ли правило, какова серьёзность) принимает детерминированный Python-код, а не модель. LLM получает список сработавших правил как контекст для разбора и обязана объяснить их, но не может отменить или «передумать». Это обеспечивает:

- воспроизводимость результатов;
- аудируемость (детерминированная часть логирует входные данные и вердикт);
- безопасность (модель не принимает бизнес-решений).

#### 3.3.10. `incidents` — Аналитика технических сбоев

**Ответственность:** учёт и анализ технических инцидентов (сбоев) информационных систем.

- Модель `Incident` (миграция 009, 010): дата, тип сбоя, длительность, влияние, статус, привязка к ИС.
- Аналитика: распределение по типам, динамика по периодам, влияние на показатели качества.
- Связь с характеристикой «Надёжность» (reliability) в модели ISO 25010.
- Уведомления об аномалиях (`AnomalyNotification`).

**API:** `GET /api/incidents`, `POST /api/incidents`, `GET /api/incidents/analytics/{system_id}`.

### 3.4. Правила зависимостей между модулями

Модули организованы в **слои зависимостей** (dependency layers). Нижележащие слои не зависят от вышележащих:

```
Слой 3 (верхний):  reporting, dataio, llm, incidents
                        │        │       │       │
Слой 2 (средний):  assessment, governance, risk
                        │           │        │
Слой 1 (нижний):   iam, systems, quality
```

**Правила:**

1. Модули одного слоя НЕ импортируют друг друга напрямую — только через общие интерфейсы (зависимости FastAPI).
2. Модуль верхнего слоя может импортировать модели и сервисы нижних слоёв.
3. Циклические зависимости ЗАПРЕЩЕНЫ — проверяются architecture-тестами.
4. Общие утилиты (config, database, dependencies) — инфраструктурный слой, доступный всем модулям.

### 3.5. Миграция Strangler Fig

Система изначально была написана как классический монолит (плоская структура `app/models.py`, `app/routes.py`). Миграция к модульному монолиту выполнена по паттерну **Strangler Fig**:

1. Созданы целевые модули с пустыми `__init__.py`.
2. Модели перенесены в соответствующие модули.
3. Введены ШИМЫ (shims) — переэкспорт из старого расположения в новое.
4. Маршруты перенесены в модульные `router.py`.
5. Шимы удалены после полного перехода.
6. Добавлены architecture-тесты для предотвращения регрессии.

Миграция **завершена**, шимы удалены. Все модули работают автономно.

## 5. Принципы разработки

### 5.1. Соответствие стандартам

#### ISO/IEC 25010:2023 — Модель качества продукта

Стандарт ISO 25010 определяет **8 характеристик** качества программного обеспечения. АСОК ИС использует этот стандарт двояко:

1. **Как предмет оценки** — система оценивает качество ИС банка по всем 8 характеристикам и их подхарактеристикам.
2. **Как требование к себе** — архитектура и реализация АСОК ИС спроектированы с учётом тех же характеристик:

| Характеристика ISO 25010 | Реализация в АСОК ИС |
|--------------------------|---------------------|
| Функциональная пригодность | Полное покрытие бизнес-требований ТЗ |
| Эффективность производительности | Async-стек, кэширование Redis, фоновые задачи Celery |
| Совместимость | REST API (OpenAPI 3.0), Excel import/export |
| Удобство использования | Премиум UI (Ant Design 5 + кастомная тема), responsive |
| Надёжность | Healthcheck-и Docker, soft-delete, транзакции ACID |
| Безопасность | JWT, bcrypt, ролевая модель, SoD, on-premise |
| Сопровождаемость | Модульный монолит, архитектурные тесты, TypeScript |
| Переносимость | Docker-контейнеризация, модель-агностичный LLM |

#### ISO/IEC 38500 — IT Governance

Модуль `governance` реализует принципы IT-управления ISO 38500:

- **Direct**: руководитель задаёт меры и контролирует их исполнение.
- **Evaluate**: аналитические отчёты и дашборды для оценки состояния.
- **Monitor**: динамика показателей качества, метки мер на графиках, аномалии.

#### ГОСТ Р 57580.1 — Безопасность финансовых операций

Требования к защите информации, реализованные в системе:

- Аутентификация по логину/паролю с хэшированием bcrypt.
- Авторизация на уровне API (проверка роли в JWT).
- Soft-delete — данные не удаляются физически.
- Аудиторский след всех решений и суждений.
- On-premise развёртывание — данные не покидают контур банка.
- HTTPS (Caddy с автоматическим TLS).

#### 152-ФЗ «О персональных данных»

- Персональные данные (ФИО, email) хранятся в БД с шифрованием на уровне СУБД (transparent encryption).
- Soft-delete с возможностью полной очистки по запросу субъекта.
- Логирование доступа к ПД.
- On-premise — данные остаются в периметре организации.

### 5.2. On-premise развёртывание

Архитектурное решение: АСОК ИС развёртывается **исключительно on-premise** в контуре безопасности банка. Это обусловлено:

1. **Регуляторными требованиями** — ЦБ РФ ограничивает передачу данных о критичности и уязвимостях ИС за периметр.
2. **LLM on-premise** — языковая модель (GGUF) работает локально, данные не отправляются внешним API (OpenAI, Anthropic и др.).
3. **Требованиями ИБ** — банковские стандарты запрещают SaaS-решения для критичных внутренних процессов.

Развёртывание:

```bash
# Минимальный запуск (CPU LLM)
docker compose up -d

# С GPU-ускорением для LLM
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d

# С удалённым доступом через Cloudflare Tunnel
docker compose --profile tunnel up -d

# С HTTPS на собственном домене (Let's Encrypt через Caddy)
docker compose --profile direct up -d
```

### 5.3. Модель-агностичный LLM

Принцип «модель — расходный материал»:

1. Любой GGUF-файл, совместимый с `llama-cpp-python` 0.3.x, работает без изменений кода.
2. Система опрашивает метаданные модели при загрузке и адаптируется (контекстное окно, формат чата).
3. Переключение модели = замена файла в `models/llm/` + `docker compose restart backend`.
4. «Резервный мозг» (`models/llm_brain/`) не зависит от модели — обучающие примеры и фидбэк переносимы.
5. Протестированные архитектуры: Qwen3, LLaMA 3, Gemma 2, Phi-3, Mistral, StableLM.

| `asok_backend` | Custom (Python 3.11) | 8000 | FastAPI + Uvicorn |
| `asok_celery` | Custom (Python 3.11) | — | Celery worker (фоновые задачи) |
| `asok_frontend` | Custom (Node 20) | 3000 | Vite dev-server |

**Опциональные сервисы** — активируются флагом `--profile`:

| Сервис | Образ | Профиль | Назначение |
|--------|-------|---------|------------|
| `webserver` | `caddy:2-alpine` | `direct` | Reverse proxy + TLS Let's Encrypt (порты 80, 443) |
| `tunnel` | `cloudflare/cloudflared` | `tunnel` / `named` | Cloudflare Tunnel |
| `ngrok` | `ngrok/ngrok` | `ngrok` | Альтернативный туннель |
| `ddns` | `favonia/cloudflare-ddns` | `ddns` | Обновление DNS при смене IP |

> **Отдельного контейнера для LLM нет.** Модель загружается внутри процесса бэкенда через `llama-cpp-python` — это исключает сетевое взаимодействие с моделью и связанные с ним отказы. Контейнер `celery beat` также не используется: периодических задач по расписанию в текущей конфигурации нет.

### 7.2. Сеть и volumes

- Единая bridge-сеть `asok_net` — все контейнеры видят друг друга по имени сервиса.
- Volumes:
  - `pgdata` — данные PostgreSQL (персистентные).
  - `redisdata` — данные Redis.
  - `caddy_data`, `caddy_config` — TLS-сертификаты Caddy.
  - `./models/llm` — GGUF-модели (bind mount, read-only).
  - `./models/llm_brain` — резервный мозг (bind mount, writable).

### 7.4. GPU-вариант

Для ускорения LLM-инференса доступен GPU-вариант:

```bash
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d
```

- Используется `dockerfile.cuda` с CUDA 12.4.
- `llama-cpp-python` собирается с поддержкой cuBLAS.
- Контейнер получает доступ к GPU через `nvidia-container-toolkit`.

### 8.1. Глоссарий

| Термин | Определение |
|--------|------------|
| **АСОК ИС** | Автоматизированная система оценки качества информационных систем |

| **Reasoning** | Многоаспектное рассуждение LLM по результатам оценки |
| **Brain** | «Резервный мозг» — хранилище памяти/корпуса/фидбэка LLM |
| **Strangler Fig** | Паттерн миграции: постепенная замена старого кода новым |
