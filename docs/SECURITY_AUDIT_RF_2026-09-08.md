# АСОК ИС — аудит информационной безопасности по требованиям РФ

Прогон системы статическими анализаторами + ручной разбор кода, конфигурации и периметра
с отображением на нормативные требования РФ и на практику ИБ финтеха/бигтеха.

**Объект:** backend (FastAPI 0.109 / SQLAlchemy 2.0 / Celery / JWT / локальная LLM),
frontend (React 18 / Vite 5 / Redux), развёртывание (Docker Compose, Cloudflare/ngrok/Caddy),
CI (`.gitlab-ci.yml`).

**Объём кода:** 21 431 строка Python (231 файл), 171 HTTP-эндпоинт, 563 файла под git.

## 0. Резюме для руководства

| Вопрос | Ответ |
|--------|-------|
| Можно ли эксплуатировать систему в контуре банка сегодня? | **Нет.** Есть 3 критические находки, любая из которых даёт полный захват системы удалённо. |
| Можно ли пройти оценку по ГОСТ Р 57580.2 сегодня? | **Нет.** Не выполнены базовые меры: регистрация событий ЗИ, МФА, антивирус, резервирование, сертифицированные СКЗИ. Оценочная готовность к «стандартному» уровню — **~30 %**. |
| Можно ли выпустить систему в контур кредитной организации (683-П, ОУД4)? | **Нет.** Не начата ни оценка по ОУД4 (ГОСТ Р ИСО/МЭК 15408-3), ни SSDLC по ГОСТ Р 56939. |
| Что хорошего | Архитектура защиты **правильная**: RBAC на 104 эндпоинтах, bcrypt(12), параметризованный ORM, защита загрузок (сигнатура + zip-бомба + лимиты), тесты-стражи доступа (`test_route_guards`, `test_auth_bypass`), fail-fast на дефолтных секретах. Классических инъекций (SQL/XSS/eval/path traversal) анализаторы **не нашли**. |
| Что плохого | Отсутствуют не «фичи безопасности», а **контур управления**: журнал ИБ-событий не пишется вовсе, секрет подписи токенов лежит в репозитории, зависимости не обновляются и не проверяются, CI-пайплайн физически не запускается. |

Главный вывод: **проблема не в коде приложения, а в эксплуатационном контуре и в цепочке
поставки.** Код писался аккуратно; конфигурация, секреты, зависимости и процессы — нет.

## 3. Реестр находок

Критичность: **К** — критическая, **В** — высокая, **С** — средняя, **Н** — низкая.
Столбец «Норма» — на что именно ложится нарушение.

### 3.1. Критические

| ID | Находка | Где | Норма |
|----|---------|-----|-------|
| **SEC-01** | **Секрет подписи JWT лежит в репозитории и равен кодовому дефолту.** `backend/.env` отслеживается git и содержит `JWT_SECRET_KEY=dev_secret_key_change_in_production_minimum_32_chars` — ровно то значение, что и `Settings.JWT_SECRET_KEY`. Кто угодно, получив репозиторий, подписывает валидный токен `{"sub":…,"role":"SUPER_ADMIN","type":"access"}` и получает полный доступ **без пароля**. Там же `POSTGRES_PASSWORD=asok_pass123` и `DEMO_MODE=true`, а значит активны встроенные пароли `superadmin/Super123!`, `admin/Admin123!`, `analyst/…`, `manager/…` (`iam/router.py:20-50`). Контейнер бэкенда читает именно этот файл (`WORKDIR /app` + bind-mount `./backend:/app` + `env_file=".env"`). В `docker-compose.yml` есть 4 профиля публикации наружу (cloudflared ×2, ngrok, Caddy) — при любом из них это **удалённый захват системы неаутентифицированным нарушителем**. | `backend/.env`, `iam/router.py`, `config.py`, `docker-compose.yml` | ГОСТ Р 57580.1 (УЗП, РД); ФСТЭК №21 ИАФ.1–ИАФ.5, УПД.1; 152-ФЗ ст.19 |
| **SEC-02** | **Уязвимая криптобиблиотека в цепочке аутентификации.** `python-jose 3.3.0` — CVE-2024-33663 (CRITICAL, algorithm confusion) и CVE-2024-33664 (DoS). Обе закрыты в 3.4.0. | `requirements.txt`, `iam/security.py` | ГОСТ Р 57580.1 (ЦЗИ); ГОСТ Р 56939 (управление уязвимостями); приказ ФСТЭК №239 |
| **SEC-03** | **Журнал событий защиты информации не ведётся вообще.** Таблица `audit_log` создана миграцией 013 и описана в `iam/models.py:48`, но в коде **ноль записей** в неё (`grep AuditLog` → только определение модели и архитектурный тест). Не фиксируются: входы и неудачные входы, выходы, изменения матрицы прав, создание и блокировка учётных записей, сброс паролей, решения по мерам, экспорт отчётов, доступ к ПДн. Логирование приложения тоже не сконфигурировано (`logging.basicConfig`/`dictConfig` отсутствуют; `LOG_LEVEL` из `.env.example` нигде не читается) — есть только stdout контейнера без централизации, ротации и защиты целостности. **Следствие:** расследование инцидента невозможно; в ГосСОПКА передавать нечего. | `iam/models.py`, вся кодовая база | ГОСТ Р 57580.1 (регистрация событий ЗИ, РИ); ФСТЭК №21 РСБ.1–РСБ.7; 187-ФЗ; 152-ФЗ ст.19 |

### 3.2. Высокие

| ID | Находка | Где | Норма |
|----|---------|-----|-------|
| **SEC-04** | **Нет защиты от подбора пароля.** На `/api/v1/auth/login` нет rate-limit, нет блокировки учётной записи после N неудач, нет задержки, нет CAPTCHA, нет уведомления владельца. Парольная политика — `min_length=6` без требований к сложности, без истории, без срока действия, без принудительной смены при первом входе и после административного сброса. | `iam/router.py:65`, `iam/schemas.py` | ГОСТ Р 57580.1 (УЗП, РД); ФСТЭК №21 ИАФ.1, УПД.10 |
| **SEC-05** | **Токены нельзя отозвать.** JWT без `jti`, без списка отзыва, без привязки к устройству или IP; серверного выхода из системы нет. | **SEC-08** | **Цепочка поставки не контролируется.** Нет lock-файла Python (транзитивные зависимости не зафиксированы), нет SBOM, нет сверки с БДУ ФСТЭК, нет подписи и сканирования образов, нет политики обновлений. `--extra-index-url` в `backend/dockerfile` открывает dependency confusion. Итог по актуальным базам: **26 уязвимостей Python + 15 JavaScript**. | `requirements.txt`, `backend/dockerfile`, `package.json` | ГОСТ Р 56939 (управление конфигурацией и сторонними компонентами); приказ ФСТЭК №239; требования к доверенному ПО |

Проверено: `GET /api/v1/governance/proposals` (`governance/router.py:59`) отдаёт **все** меры любому вошедшему, включая роль `EXECUTOR`, — фильтрации по владельцу или исполнителю нет; ограничение области видимости по ИС (задача P8 из ТЗ-02) не реализовано. Разграничение «свои/чужие» держится на клиентском фильтре. | `governance/router.py` и ещё 67 мест | ГОСТ Р 57580.1 (РД); ФСТЭК №21 УПД.2, УПД.4; 152-ФЗ ст.5 (минимизация) |

### 4.1. 152-ФЗ «О персональных данных» + ПП РФ №1119 + приказ ФСТЭК №21

## 5. Ограничения системы

Ограничения архитектурного и организационного характера — их **нельзя закрыть правкой кода**,
они требуют решений заказчика.

| # | Ограничение | Следствие | Направление решения |
|---|-------------|-----------|---------------------|
| **ОГР-1** | Симметричная подпись токенов (HS256): один секрет и подписывает, и проверяет | компрометация одного файла = подделка любых токенов; невозможна смена ключа без разлогина всех | переход на RS256/ES256 (далее — ГОСТ Р 34.10-2012), ключи в HSM/КриптоПро |
| **ОГР-2** | Аутентификация только локальная | нет единого входа, нет централизованного отключения при увольнении, нет корпоративных парольных политик | интеграция с корпоративным IdP (LDAP/Kerberos/SAML/OIDC), SCIM |
| **ОГР-3** | Нет сертифицированных СКЗИ | формально невозможно закрыть требования ФСБ к защите ПДн и требования Банка России | КриптоПро CSP/NGate, ГОСТ-TLS на периметре, аттестация |
| **ОГР-4** | LLM накапливает рабочие данные (`memory.jsonl`, `corpus.jsonl`) вне БД | неконтролируемое накопление сведений, включая ПДн; нет удаления, резервирования и учёта | перенести «мозг» в БД под общие политики хранения либо запретить запись ПДн в него |
| **ОГР-5** | Публикация наружу через иностранные туннели заложена в штатную схему развёртывания | несовместимо с контуром банка и с Указом №250 | развёртывание только внутри контура; профили `tunnel`/`ngrok`/`ddns` вынести из прод-манифеста |
| **ОГР-6** | Однопользовательский стенд: один Postgres, один Redis, один бэкенд, `--beat` внутри воркера | нет отказоустойчивости; RTO/RPO недостижимы; при масштабировании расписание сработает N раз | HA-топология, вынос beat, кластер БД, реплики |
| **ОГР-7** | Демо-режим встроен в продуктивный код (`DEMO_MODE`, `DEMO_USERS`, `DEMO_AUTH_BYPASS`, сиды) | риск активации в проде одной строкой конфигурации; недекларированная функциональность для оценки по ОУД4 | отдельный прод-профиль сборки без демо-кода |
| **ОГР-8** | Границы ИС и состав обрабатываемых данных не зафиксированы документально | невозможно определить уровень защищённости, категорию КИИ и применимые положения Банка России | описание ИС, классификация данных, модель угроз, акт категорирования |

## 7. Что уже сделано правильно (не ломать)

- **RBAC как данные, а не как `if`**: каталог прав в коде, матрица `role_permissions` в БД,
  `require_permission` на 104 эндпоинтах, `SUPER_ADMIN` вне матрицы.
- **Тесты-стражи**: `test_route_guards.py` (у каждого маршрута есть гейт, у каждого изменяющего —
  право), `test_auth_bypass.py`, `test_config_security.py`, `test_security.py`, `test_permissions.py`.
- **Хеширование паролей**: bcrypt, cost 12, соль; хранится только хеш.
- **Отсутствие инъекций**: везде ORM с параметрами; единственный `text()` — в сиде справочника.
- **Загрузка файлов**: потоковое чтение с обрывом по лимиту, проверка сигнатуры OOXML, защита
  от zip-бомбы, `uuid4` + `os.path.basename` в имени, запись вне event loop.
- **Разделение `DEMO_MODE` и `DEMO_AUTH_BYPASS`** после ДЕФ-02 — правильный разбор инцидента:
  невалидный токен теперь всегда даёт 401.
- **Fail-fast на небезопасной конфигурации** (`config.security_issues()` + `main.py`) — механизм
  верный, его лишь обходит `.env` из репозитория (ИБ-01 и ИБ-02 это чинят).
- **Разделение обязанностей заложено в модель данных** (роли `RISK_MANAGER` и `AUDITOR`,
  статусная модель мер) — остаётся довести до технической проверки (ИБ-19).
- **LLM работает on-prem** — данные не покидают контур организации; это сильная сторона
  архитектуры, её нужно сохранить при доработке по ИБ-26.

## 8. Приложение. Предлагаемые джобы ИБ для CI

```yaml
security:sast:
  script:
    - bandit -r backend/app -ll -f json -o bandit.json
    - semgrep scan --config=p/security-audit --config=p/python --config=p/react --error

security:sca:
  script:
    - pip-audit -r backend/requirements.lock --strict
    - cd frontend && npm audit --audit-level=high

security:secrets:
  script:
    - gitleaks detect --no-git -v
    - test -z "$(git ls-files | grep -E '(^|/)\.env$')"   # .env не должен отслеживаться

security:containers:
  script:
    - trivy image --severity HIGH,CRITICAL --exit-code 1 $BACKEND_IMAGE:$CI_COMMIT_SHA
    - trivy config --severity HIGH,CRITICAL --exit-code 1 .
```
