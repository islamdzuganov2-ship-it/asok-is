## 0. Резюме: постановка и принятые развилки

### 0.1 Постановка

Презентация фиксирует контур из четырёх работающих подсистем: оценка по ISO/IEC 25010 и
ГОСТ Р 59898, риски с триггерами, управленческая петля мер и локальная LLM. Проверка кода
подтверждает: **подсистемы действительно есть и считают** — 166 HTTP-эндпоинтов, модуль
`econ` на 2631 строку, ALE/ROSI/вето/матрица акцепта реализованы на сервере.

Проблема не в возможностях, а в **доступе к ним**. Наиболее ценные для руководителя цифры
лежат на третьем-четвёртом шаге навигации, за названиями разделов, которые описывают
артефакт («База рисков», «Риск-экономика»), а не вопрос («что нам стоит текущее качество»).
Часть возможностей не выведена в интерфейс вообще.

**Цель ТЗ.** Руководитель получает ответ на свой вопрос **на первом экране, без обучения и
без навигации**, и при этом сохраняет возможность спуститься до первичной записи — не теряя
выбранного разреза.

Метрика цели, по которой ТЗ проверяется: **количество кликов от входа до ответа** и
**сохранность разреза при углублении**. Обе величины измеримы, обе вынесены в §14.

### 0.3 Ключевое проектное решение

Вместо ещё одного дашборда вводится **один объект — «разрез» (Slice)** — и **три горизонта
его показа**. Разрез живёт в адресной строке, поэтому:

- любой экран системы читает его одинаково, а не своими параметрами;
- переход вглубь не сбрасывает контекст;
- любое состояние экрана — это ссылка, которую можно переслать в переписке правления.

Кокпит — это первый горизонт над этим объектом, а не отдельная подсистема.

**Обобщение.** Из одиннадцати проверенных обещаний восемь реализованы на сервере и **не

не требует новых расчётов — требуется **другая подача**.

Сопутствующее наблюдение о навигации: восемь страниц уже читают параметры из адресной строки

`AssessmentWorkspacePage`), но каждая — **своим набором ключей** (`characteristic`, `system`,
`category`, `owner`, `status`). Общего словаря нет, поэтому переход между разделами теряет
контекст. Это техническая причина, по которой «разрезы» сегодня не складываются.

## 2. Принцип решения: закон трёх горизонтов

Единственное правило подачи, из которого выводится всё остальное в этом ТЗ.

| Горизонт | Бюджет внимания | Что показывается | Механика |
| :--- | :--- | :--- | :--- |
| **L1 — «десять секунд»** | один взгляд, без прокрутки | 5–6 плиток. Плитка = **вопрос обычным языком** + **одна цифра** + изменение к прошлому периоду + одна строка «почему это важно» | посадочная страница роли |
| **L2 — «одна минута»** | один клик, контекст не теряется | разложение этой цифры на 5–7 строк в выбранном разрезе: топ вкладов, переключатель группировки, действие по строке | **боковая шторка** поверх кокпита |
| **L3 — «десять минут»** | глубина по потребности | существующие страницы системы как есть, с уже применённым разрезом | переход по ссылке, возврат восстанавливает L2 |

Три следствия, обязательные к соблюдению:

1. **L1 не содержит таблиц, вкладок и графиков сложнее спарклайна.** Всё, что требует
   чтения дольше пяти секунд, живёт на L2.
2. **L2 не является новой страницей.** Шторка открывается поверх кокпита, кокпит остаётся
   под ней. Уход со страницы допустим только на L3 и только по явному действию пользователя.
3. **L3 не переписывается.** Существующие девять дашбордов и семь разделов остаются
   глубоким слоем. Это принципиально: объём ТЗ — надстройка доступа, а не переделка системы.

Схема перехода:

```
ВХОД (роль → своя посадочная)
  │
  ├─ L1  Кокпит: 5–6 плиток-ответов ────────────── разрез в адресной строке
  │        │ клик по плитке
  │        ▼
  ├─ L2  Шторка: разложение цифры ─────────────── тот же разрез, уточняется
  │        │ клик по строке
  │        ▼
  └─ L3  Глубокая страница (существующая) ─────── тот же разрез, применён фильтрами
           │ «← к кокпиту»
           ▼
         возврат на L2 в ту же точку
```

## 3. Сквозной разрез (Slice) — несущая конструкция

### 3.1 Определение

Разрез — это ответ на вопрос «о чём именно мы сейчас говорим». Один объект, общий для всех
экранов системы.

```ts
// frontend/src/store/slices/sliceSlice.ts  (новый файл)
export interface Slice {
  period: string | 'latest';            // код периода оценки; 'latest' — последний доступный
  systems: string[];                    // id ИС; [] — весь портфель
  criticality: Criticality[];           // [] — все классы
  characteristic: string | null;        // одна из 8 характеристик ISO 25010
  subcharacteristic: string | null;     // уточнение внутри характеристики
  owner: string | null;                 // владелец ИС / ответственный за меру
  lens: 'score' | 'ale' | 'delta' | 'coverage';  // денежная линза
}
```

Поле `lens` не изобретается: оно уже существует в `ExecutiveDashboard.tsx` как `MoneyMode`
с четырьмя значениями «Балл качества / ALE под риском / ΔALE снимаемый мерами / Покрытие
мерами». ТЗ поднимает его из локального состояния одной карточки в общий разрез.

### 3.2 Адресная строка — источник истины

```
/dashboard/ceo?p=2026-Q2&sys=a1b2,c3d4&crit=MC&char=Надёжность&sub=Отказоустойчивость&owner=Иванов&lens=ale
```

| Ключ | Значение | Пропуск означает |
| :-- | :--- | :--- |
| `p` | код периода или `latest` | `latest` |
| `sys` | id ИС через запятую | весь портфель |
| `crit` | `MC` / `BC` / `BO` через запятую | все классы |
| `char` | название характеристики | все характеристики |
| `sub` | название подхарактеристики | все подхарактеристики |
| `owner` | ФИО или id ответственного | все ответственные |
| `lens` | `score` / `ale` / `delta` / `coverage` | `score` для CTO, `ale` для CEO |

**Правило источника истины:** адресная строка первична, Redux — производное зеркало для
виджетов. Обратный порядок запрещён: иначе ссылка перестаёт воспроизводить экран, и главное
свойство разреза («переслал в переписке — открылось то же самое») теряется.

**Контракт сериализации** — один модуль, используемый всеми страницами:

```ts
// frontend/src/store/slice/sliceUrl.ts
export function sliceToParams(s: Slice): URLSearchParams;
export function paramsToSlice(p: URLSearchParams): Slice;   // с валидацией и дефолтами
export function useSlice(): [Slice, (patch: Partial<Slice>) => void];
```

`useSlice` — единственный разрешённый способ читать и менять разрез в компонентах. Прямое
обращение к `useSearchParams` за ключами разреза запрещается регресс-тестом (§14, КП-ПР-3).

### 3.3 Обратная совместимость с текущими ссылками

Существующие переходы уже используют собственные ключи. Их не ломаем: `paramsToSlice`
понимает старые имена как синонимы и при первом чтении переписывает адрес в новый формат
(`replace`, без записи в историю браузера).

| Старый ключ | Где используется | Новый ключ |
| :-- | :--- | :--- |
| `characteristic` | `ExecutiveDashboard.tsx:183`, `TaskPlanDashboard.tsx:112` | `char` |
| `owner` | `TaskPlanDashboard.tsx:113` | `owner` (без изменений) |
| `system` | `IncidentsAnalyticsPage.tsx:96` | `sys` (с преобразованием имени в id) |
| `status` | `TaskPlanDashboard.tsx:114` | остаётся локальным параметром страницы |
| `category` | `IncidentsAnalyticsPage.tsx:97` | остаётся локальным параметром страницы |

Граница проведена так: **в разрез входит только то, что имеет смысл на всех экранах**.
Статус меры и категория сбоя осмысленны на одной странице — они остаются её собственными
параметрами и в разрез не поднимаются.

### 3.4 Панель разреза (SliceBar)

Один компонент, отрисовываемый под шапкой приложения на всех страницах, где разрез применим.

Состав слева направо: период · ИС (мультивыбор с поиском) · класс критичности · характеристика ·
владелец · линза · **«Сбросить»** · **«Скопировать ссылку на разрез»**.

Требования:

- **Свёрнутое состояние по умолчанию.** Показывается строка-резюме: `Весь портфель · 2026-Q2 ·
  все классы`. Разворачивается кликом. Руководитель, которому разрез не нужен, не видит шести
  контролов.
- **Активные фильтры всегда видны** компактными чипами даже в свёрнутом состоянии — чтобы
  цифра на экране никогда не читалась как «по всему портфелю», когда это не так. Это
  требование корректности решений, а не украшение.
- **Панель не рендерится там, где разрез не применим** (администрирование, настройка).
- На узком экране (< 768 px) сворачивается в одну кнопку «Разрез (3)».

### 3.5 Наследование разреза при переходах

| Переход | Что происходит с разрезом |
| :--- | :--- |
| L1 → L2 (клик по плитке) | сохраняется целиком |
| L2 → L2 (переключение группировки) | сохраняется, меняется только способ показа |
| L2 → L3 (клик по строке) | сохраняется **и уточняется** значением строки (кликнули по ИС — она добавляется в разрез) |
| L3 → L2 (кнопка «← к кокпиту») | восстанавливается разрез, с которым уходили, **и позиция шторки** |
| Смена раздела через меню | сохраняется всё, что применимо к новому разделу; неприменимые поля молча игнорируются, но **не стираются** (вернулись — снова действуют) |
| «Сбросить» | всё в дефолт, адрес очищается |

Предпоследняя строка — самая частая причина ощущения «система меня теряет»: сегодня переход
в другой раздел обнуляет контекст полностью.

## 4. Командная строка (Ctrl+K)

Единая точка «я знаю, что ищу». Открывается по `Ctrl+K` / `⌘K` и кнопкой-лупой в шапке.

| Что ищем | Эндпоинт (существующий) | Действие по выбору |
| :--- | :--- | :--- |
| Информационная система | `GET /systems?is_active=true` | разрез сужается до этой ИС, остаёмся на текущем экране |
| Характеристика / подхарактеристика | `QUALITY_MODEL` (константа фронта) | разрез сужается до неё |
| Риск | `GET /risks/search?q=` и **`GET /risks/semantic-search?q=`** | открывается карточка риска |
| Мера | `GET /governance/proposals` | открывается карточка меры с решением |
| Раздел системы | `NAV_SECTIONS` | переход с сохранением разреза |
| Ответ на вопрос | реестр плиток кокпита | открывается L2 этой плитки |

Отдельно отмечается: **семантический поиск по рискам уже реализован** (`/risks/semantic-search`,
pgvector) и сегодня доступен только внутри страницы «База рисков». Командная строка делает его
общесистемным без единой строки нового бэкенда — характерный пример «возможность есть, доступа
нет».

Требования: результаты сгруппированы по типу, максимум 5 в группе; навигация стрелками; `Esc`
закрывает без изменений; при пустом запросе показываются вопросы кокпита как быстрые команды.

## 7. Механика раскрытия L1 → L2 → L3

### 7.1 Контракт плитки

Плитка — единица кокпита. Оба кокпита строятся одной оболочкой и различаются только реестром
плиток; это прямое следствие Р-3 (разные по содержанию, одинаковые по механике).

```ts
// frontend/src/dashboards/cockpit/types.ts
export interface CockpitTile {
  id: string;
  question: string;              // «Сколько нам стоит текущее качество?»
  perm?: string;                 // право; без него плитка не строится и не запрашивает данные
  defaultEnabled: boolean;       // для персонализации через DashboardShell
  useValue(slice: Slice): TileValue;
  Detail: React.FC<{ slice: Slice }>;            // содержимое шторки L2
  drillTo(row: unknown, slice: Slice): string;   // ссылка L3 с уточнённым разрезом
}

export interface TileValue {
  value: number | string | null;   // null — данных нет; ноль не подменяет отсутствие
  unit: '₽/год' | '%' | 'шт.' | 'п.п.' | null;
  delta?: { value: number; unit: string; direction: 'up' | 'down' };
  trend?: number[];                // для спарклайна
  tone: 'critical' | 'low' | 'medium' | 'high' | 'neutral';
  subtitle: string;                // одна строка «почему это важно»
  empty?: { reason: string; fixHref?: string; fixLabel?: string };  // §7.3
}
```

### 7.2 Оболочка

`ExecCockpit` строится **поверх существующего `DashboardShell`**: механика «Настроить →
галочки + перетаскивание, раскладка хранится per-user через `PUT /iam/me/preferences`» уже
работает у владельца риска и переиспользуется без изменений. Это закрывает требование
«погружаться дальше по необходимости своей натуры» на уровне состава экрана: набор плиток
руководитель настраивает под себя, дефолт задаёт реестр роли.

Отличие от текущего `DashboardShell`: плитки укладываются **сеткой** (2–3 в ряд), а не
вертикальной лентой, поскольку требование L1 — «без прокрутки».

### 7.3 Правило честной пустоты

Ни одна плитка не имеет права показать `0`, `0 ₽` или `—` без объяснения. Если данных нет,
`TileValue.empty` обязателен и содержит причину и, где возможно, ссылку на её устранение.

Это не новое правило, а перенос действующего методологического инварианта системы на уровень
кокпита: слайд 5 фиксирует «неизмеримая метрика исключается из расчёта, а не считается нулём».
Денежные плитки — самое опасное место для его нарушения: «0 ₽ под риском» читается как «всё
хорошо», хотя означает «справочник стоимости пуст».

| Причина | Формулировка на плитке | Ссылка |
| :--- | :--- | :--- |
| Нет ставок сопровождения / стоимости минуты БП | «Стоимость не рассчитана: не заполнены справочники стоимости» | Риск-экономика → Справочники |
| Не задан порог катастрофичности | «Вето катастрофичности не применяется: порог не задан» | Риск-экономика → Финпараметры |
| Нет предыдущего периода | «Изменение не показано: это первый период оценки» | — |
| Разрез пуст | «В выбранном разрезе нет данных» | «Сбросить разрез» |
| Нет права | плитка не рендерится вовсе | — |

### 7.4 Шторка L2

- Ширина 720 px, на узком экране — во весь экран.
- Заголовок = вопрос плитки, подзаголовок = действующий разрез словами.
- Внутри: переключатель группировки (по ИС / по характеристике / по владельцу / по классу),
  таблица 5–7 строк с «показать все», одно рекомендованное действие внизу.
- Закрывается `Esc` и кликом вне; **разрез при закрытии не откатывается** — если в шторке
  уточнили ИС, кокпит перестраивается под неё.
- Состояние шторки хранится в адресе: `&tile=ceo-cost&by=system` — чтобы возврат с L3
  восстанавливал точку выхода.

### 7.5 Возврат с L3

На каждой глубокой странице, открытой из кокпита, в левом верхнем углу появляется
`← К кокпиту`. Признак «пришли из кокпита» — параметр `&from=cockpit`. Кнопка возвращает на
посадочную роли с восстановлением `tile` и `by`.

| **Работа с данными** | Внесение данных · База рисков · Риск-экономика · Отчёты · Мои задачи | по правам |
| **Администрирование** | без изменений | по правам |

Персонализация (`hiddenSections`, `navOrder`) и механика обязательных разделов
(`mandatorySections`) работают как сейчас — меняются только группировка и подписи.

### 8.3 Что это даёт численно

Сегодня путь CEO к главной цифре: вход → «Сбор и анализ данных» → «Риск-экономика» → вкладка
«Дашборд стоимости» → найти показатель среди прочих = **3 клика и одно сканирование
страницы**, при условии что человек знает, где искать.

После: вход → цифра на первом экране = **0 кликов**.

## 9. Гигиена экрана руководителя

Четыре точечных изменения, каждое — устранение конкретного риска.

### 9.1 Переключатель «Демо ↔ LLM»

Сегодня тумблер стоит в шапке приложения (`AppLayout.tsx`) и молча меняет источник данных для
всех дашбордов. На кокпите CEO рядом с ним будет стоять сумма в рублях.

**Решение:** на кокпитах CEO и CTO тумблер из шапки убирается. Вместо него — заметная плашка
над плитками: «Демонстрационные данные» (в демо-режиме) или ничего (в живом). Переключение
остаётся доступным из раздела «Настройка» и в шапке для административных ролей.

**Причина:** случайное переключение во время демонстрации правлению меняет цифру в рублях без
предупреждения. Это репутационный риск, несоразмерный удобству тумблера.

### 9.2 AI-резюме

Сегодня на управленческом дашборде это карточка-простыня с абзацем текста, а на карточках
топ-3 ИС — кнопки «Собрать AI-резюме», которые руководитель должен нажать сам.

**Решение:**

- На L1 — **одна строка** под заголовком кокпита: управленческий вывод до 25 слов, с маркером
  происхождения. Полный текст — по «развернуть».
- Кнопки ручной генерации на кокпите убираются: вывод запрашивается фоново при открытии, до
  готовности показывается детерминированная формулировка. Механика подмены уже существует
  (слайд 13, п. 3 — «система работает без модели»).
- Маркер «✓ вывод ИИ» против «сводка по метрикам» **сохраняется обязательно** — он уже
  реализован в `ExecutiveDashboard.tsx` и является частью контура доверия.

### 9.3 Единица измерения на первом экране

На L1 денежные величины округляются до значащего порядка («12,4 млн ₽», не «12 437 118 ₽»).
Точное значение — на L2 и в подсказке. Существующий помощник `utils/money.ts` расширяется
функцией компактного формата.

### 9.4 Ссылка на разрез

Кнопка «Скопировать ссылку» в панели разреза кладёт в буфер полный адрес текущего состояния
(разрез + открытая шторка). Это заменяет скриншоты в переписке и даёт руководителю способ
передать не картинку, а **воспроизводимый вопрос**.

## 10. Бэкенд: чего не хватает и что добавляется

Изменения минимальны: три новых эндпоинта, параметры разреза на три существующих и один
опциональный агрегатор. Формулы расчёта не трогаются.

### 10.1 `GET /econ/acceptance-queue` — очередь по матрице акцепта (новый)

Закрывает плитку CEO 5.2 и выводит `acceptance_matrix` в интерфейс впервые.

```
GET /econ/acceptance-queue?signer=&period=&system_id=&criticality=
→ AcceptanceQueueOut {
    items: [{
      kind: 'NONCONFORMITY' | 'RISK_ACCEPTANCE' | 'MEASURE',
      id, title, systemName, criticality,
      ale: float,
      signer: str,              # вычислен по acceptance_matrix
      waitingDays: int,
      slaDays: int,             # nc_sla_days | nc_sla_days_critical
      overdue: bool,
      vetoes: [str],            # регуляторное / катастрофичности / класса ИС
    }],
    bySigner: { signer: {count, totalAle, overdue} },
    matrixApplied: [{maxAle, signer}],   # какие пороги применены — для прозрачности
  }
```

Право: `view.risk_economics` (у CEO и CTO есть по умолчанию — проверено в
`DEFAULT_ROLE_PERMISSIONS`). Логика подписанта переиспользует `nonconformity/service.py:65`,
вынесенную в общий помощник, — новой бизнес-логики не появляется.

### 10.2 `GET /econ/portfolio-trend` — динамика портфельных величин (новый)

Закрывает изменения на плитках CEO 5.1 и CTO 6.2. Сегодня дельт на портфельном уровне нет
нигде — ни на сервере, ни в интерфейсе, поэтому плитки не могут показать «стало лучше или
хуже», а это первое, что спрашивает руководитель.

```
GET /econ/portfolio-trend?metric=ale|score|closure|availability&periods=6&<разрез>
→ { points: [{period, value}], delta: {absolute, relative}, anomaly: bool }
```

`anomaly` = изменение ≥ 12 п.п. для `metric=score` — порог зафиксирован (слайд 11) и уже
реализован для отдельных ИС; здесь поднимается на портфель.

### 10.3 `GET /governance/proposals/overdue-summary` — просрочка и Ц_ОМ портфельно (новый)

Закрывает плитку CEO 5.5. Сегодня цена неисполнения считается только для одной меры
(`/proposals/{pid}/price-of-inaction`); портфельной суммы нет.

```
GET /governance/proposals/overdue-summary?<разрез>
→ { overdueCount, ownersAffected, totalPriceCurrent, totalPriceSnapshot,
    byOwner: [{owner, count, price}],
    items: [{proposalId, title, systemName, owner, overdueDays, priceCurrent, escalatedAt}] }
```

Считается суммированием существующего расчёта Ц_ОМ по просроченным мерам — формула не
меняется, различие ELIMINATING / COMPENSATING сохраняется (ТЗ-19 §17.4).

### 10.4 Параметры разреза на существующие эндпоинты

| Эндпоинт | Сейчас | Добавляется |
| :--- | :--- | :--- |
| `GET /econ/dashboard` | без параметров | `period`, `system_id` (мн.), `criticality`, `characteristic` |
| `GET /risk-events/portfolio-summary` | без параметров | те же |
| `GET /governance/proposals/effect-curve` | без параметров | те же |

Требование обратной совместимости: **вызов без параметров возвращает то же, что сегодня**.
Существующая страница «Риск-экономика» продолжает работать без правок.

### 10.5 Агрегатор кокпита (рекомендуется)

```
GET /reports/cockpit?role=CEO|CTO&<разрез>
→ { tiles: { <tileId>: TileValue }, generatedAt, dataMode, periodsUsed }
```

**Рекомендация — делать агрегатор**, по двум причинам:

1. Шесть параллельных запросов дают шесть независимых спиннеров: экран «прыгает» несколько
   секунд. Для роли, которая смотрит на него десять секунд, это половина бюджета внимания.
2. Дельты на всех плитках обязаны считаться **от одного и того же предыдущего периода**. При
   независимых запросах согласованность периода не гарантируется — и две плитки могут
   сравнивать с разными базами, чего пользователь не увидит.

Агрегатор не содержит расчётов: он вызывает существующие сервисы (`cost_dashboard`,
`portfolio_risk_summary`, `incident_analytics`, `manager_metrics`, `triggered_risks`) и
складывает результат. Права проверяются по каждой плитке отдельно: плитка, на которую нет
права, в ответе отсутствует.

Альтернатива (шесть прямых запросов с фронта) допустима как временное решение фазы 3, но в
критерий КП-ПР-8 (время до первого кадра) она, вероятно, не уложится на живых данных.

## 11. Маршруты, права и совместимость

### 11.1 Маршруты

| Маршрут | Было | Становится |
| :--- | :--- | :--- |
| `/dashboard/ceo` | заглушка → `ExecutiveDashboard` | **кокпит CEO** |
| `/dashboard/cto` | заглушка → `ExecutiveDashboard` | **кокпит CTO** |
| `/dashboard/executive` | общий управленческий дашборд | **без изменений** — остаётся «полной лентой» уровня L3 |

Решение сознательное: кокпиты занимают уже существующие маршруты ролей, поэтому
`HOME_BY_ROLE`, гейтинг `RequirePermission`, состав меню, персонализация и обязательные
разделы **не требуют изменений вообще**. Текущий `ExecutiveDashboard` не выбрасывается: он
становится глубоким слоем для тех, кому нужна лента целиком, и доступен из кокпита ссылкой
«Полная картина».

### 11.2 Права

**Новых прав не вводится.** Проверено по `DEFAULT_ROLE_PERMISSIONS`
(`modules/iam/permissions.py:131`): у ролей `CEO` и `CTO` уже есть `view.risk_economics`,
`governance.decide`, `nonconformity.decide`, `view.dashboard.incidents`,
`view.dashboard.risk_radar`, `view.dashboard.dynamics` и `view.dashboard.taskplan` — то есть
все источники данных кокпита им уже разрешены.

Право на плитку берётся от права на её источник:

| Плитка | Требуемое право |
| :--- | :--- |
| CEO 5.1, 5.3, 5.4, 5.6; CTO 6.5 | `view.risk_economics` |
| CEO 5.2, 5.5; CTO 6.1 | `view.risk_economics` (просмотр) + `governance.decide` (действие) |
| CTO 6.2 | `view.dashboard.dynamics` |
| CTO 6.3 | `view.dashboard.incidents` |
| CTO 6.4 | `view.dashboard.risk_radar` |

Следствие: суперадминистратор, сняв право матрицей, автоматически убирает плитку — без
отдельной настройки кокпита. Это соответствует действующему принципу «персонализация поверх
RBAC, право — верхняя граница» (`AppLayout.tsx`, ДЕФ-12).

| Что | Гарантия |

## 12. Требования к подаче и дизайну

1. **Одна цифра — один смысл.** На плитке ровно одна крупная величина. Всё остальное —
   вспомогательное и мельче как минимум вдвое.
2. **Премиум-слой обязателен.** Используются `theme/premium.ts` (`premiumCard`, `TYPE`,
   `SPACE`, `GOLD`) и `theme/ragPalette.ts`. Самодельная вёрстка плиток не допускается —
   плитки строятся на существующем `KpiCard`, как уже сделано для «Владельца риска» и
   «Моих задач».
3. **Инвариант RAG соблюдается:** `color` — для графики, `strong` — для текста и плашек
   (T-57). Проверяется `npm run check:contrast`, допустимо 0 нарушений.
4. **Темы.** Обе рантайм-темы. Цвета графиков берутся через `useChartTokens()`, а не из
   `BRAND.*` — CSS-переменные не работают на canvas ECharts (зафиксировано в ТЗ-17).
5. **Адаптивность.** 1280×800 — кокпит без прокрутки и без горизонтального скролла; 768 px —
   две плитки в ряд; 375 px — одна, панель разреза сворачивается в кнопку.
6. **Отсутствие «прыжков».** Плитки резервируют высоту до загрузки (скелетон фиксированного
   размера), чтобы экран не переставлялся под курсором.
7. **Язык.** Формулировки на плитках проходят действующий фильтр делового языка
   (`style_guide.py`): без терминов реализации — «grounding», «fallback», «движок», кодов
   этапов конвейера. На стороне LLM это уже охраняется тестом; для статических подписей
   вводится такая же проверка в тестах фронта.

## 14. Критерии приёмки

Приёмка численная. Формулировки построены так, чтобы проверялись без интерпретации.

| Код | Критерий | Как проверяется |
| :-- | :--- | :--- |
| КП-ПР-1 | CEO видит сумму под риском **на первом экране без прокрутки** при 1440×900 и 1280×800 | ручная проверка + скриншот в UI-аудите |
| КП-ПР-2 | До любого из шести ответов — **0 кликов**; до причины (L2) — **1 клик**; до первичной записи (L3) — **2 клика** | сценарный чек-лист |
| КП-ПР-3 | Разрез сохраняется на **всех** переходах L1→L2→L3→назад; ни один компонент не читает ключи разреза мимо `useSlice` | новый набор `cockpitSlice.test.ts` |
| КП-ПР-4 | Скопированная ссылка, открытая в новой вкладке, воспроизводит экран целиком, включая открытую шторку | тест сериализации + ручная проверка |
| КП-ПР-5 | Ни одна плитка не показывает `0` / `0 ₽` при отсутствии данных — только причина и, где возможно, ссылка на устранение | юнит-тест на `TileValue.empty` для каждой плитки реестра |
| КП-ПР-6 | Старые ссылки (`?characteristic=`, `?system=`, `?owner=`) открывают то же, что раньше | тест обратной совместимости `sliceUrl` |
| КП-ПР-7 | Вызовы изменённых эндпоинтов **без параметров** возвращают прежний результат | pytest на каждый из трёх |
| КП-ПР-8 | Первый осмысленный кадр кокпита: ≤ 1,5 с на демо-данных, ≤ 3 с на живых | замер в UI-аудите |
| КП-ПР-9 | `npm run typecheck` — 0 ошибок; `npm test` — все зелёные; `npm run check:contrast` — 0 нарушений; `npm run build` — проходит | обязательные проверки перед PR (CLAUDE.md) |
| КП-ПР-10 | `pytest` в backend — все зелёные, включая новые тесты Ф2 | Docker-стек |
| КП-ПР-11 | Кокпит корректен в обеих темах и на 375 px | UI-аудит + `npm run check:ui` |
| КП-ПР-12 | Ни один текст на плитках не содержит терминов реализации | тест по словарю `style_guide` на стороне фронта |

**Отдельный критерий готовности к демонстрации (КП-ПР-14).** Сценарий на живом стенде: вход
под CEO → назвать сумму под риском → открыть её разложение → перейти к конкретной ИС →
вернуться к кокпиту → скопировать ссылку → открыть её в новой вкладке. Сценарий проходится
**без единого объяснения со стороны показывающего**. Если требуется комментарий «а теперь
нажмите вот сюда» — критерий не выполнен.

## 15. Открытые вопросы к заказчику

Первые четыре — блокирующие для денежных плиток: в конфигурации стоят заглушки, и без ответов
плитки будут корректно, но постоянно показывать «не рассчитано».

| Код | Вопрос | Текущее состояние в коде | Почему важно |
| :-- | :--- | :--- | :--- |
| **В-КП-1** | Пороги матрицы акцепта: подтвердить 1 млн ₽ (владелец ИС) / 10 млн ₽ (CIO) / свыше (правление) | `acceptance_matrix`, описание — *«пороги — предложение»* | Плитка CEO 5.2 целиком строится на этих порогах |
| **В-КП-2** | Порог вето катастрофичности (MaxSLE), например 1 % годовой EBITDA | `catastrophe_threshold: value = None`, описание — *«ЗАДАТЬ»* | Одно из трёх вето слайда 7 **не применяется ни разу** |
| **В-КП-3** | Риск-аппетит по классам ИС: подтвердить 500 тыс. / 2 млн / 5 млн ₽ в год | `risk_appetite_by_class`, описание — *«ЗАГЛУШКА — сверить с заказчиком»* | Задаёт тон (цвет) плитки 5.1 и порог эскалации мер |
| **В-КП-4** | Коэффициент накладных к ФОТ (сейчас 1,6) | `k_overhead`, описание — *«ЗАГЛУШКА — уточнить»* | Входит в стоимость сбоя, то есть во все суммы ALE |
| В-КП-5 | Кто в системе подписант уровня «правление/комитет» — роль `CEO` или отдельная сущность | в матрице это строка текста, не роль | Определяет, чья очередь наполняется в плитке 5.2 |
| В-КП-6 | Нужен ли разрез по **бизнес-процессам** (`business_processes` в `econ` уже есть) наряду с разрезом по ИС | БП существуют, в разрез не включены | Влияет на состав `Slice` и панель разреза |
| В-КП-7 | Дефолтный период кокпита — последний закрытый или текущий незакрытый | периоды разных ИС расходятся (`periodsUsed` это уже фиксирует) | Определяет, что показывать, когда ИС на разных периодах |
| В-КП-8 | Нужна ли CEO плитка «Что мы покажем регулятору» (5.6) или это вопрос комплаенса, а не правления | — | Шесть плиток или пять |

Оговорка по В-КП-1…В-КП-4: **разработка ими не блокируется**. Механика строится на
конфигурируемых параметрах, значения правятся через `PUT /econ/config/{key}` без деплоя.
Блокируется только осмысленность цифр на демонстрации.

## 16. Риски решения

| Риск | Оценка | Что делаем |
| :--- | :--- | :--- |
| **Кокпит станет десятым дашбордом**, а не входом — руководитель по привычке пойдёт в старые разделы | высокий | Кокпит занимает **существующие** маршруты ролей (`/dashboard/ceo`, `/dashboard/cto`), а не добавляет пункт меню. Обойти его можно только сознательно |
| **Цифры на плитках разойдутся** с цифрами на глубоких страницах | высокий | Плитки не считают ничего сами: `TileValue` собирается из ответов тех же сервисов, что питают глубокие страницы. Любой пересчёт на фронте запрещён |
| Разрез окажется слишком мелким инструментом, и его никто не тронет | средний | Панель свёрнута по умолчанию; разрез уточняется **сам** при углублении (клик по строке = сужение). Ручная настройка — не обязательный шаг, а возможность |
| Шесть параллельных запросов сделают кокпит медленным | средний | Агрегатор `/reports/cockpit` (§10.5); порог зафиксирован критерием КП-ПР-8 |
| Заглушки в финпараметрах (В-КП-2…4) превратят денежные плитки в «не рассчитано» на демонстрации | средний | Правило честной пустоты (§7.3) делает это **объяснимым**, а не сломанным; параметры правятся конфигом без деплоя |
| Вопросы во второй строке меню перегрузят сайдбар | низкий | `TYPE.micro`, приглушённый тон, в свёрнутом сайдбаре — только подсказка; проверяется контрастом и UI-аудитом |
| Рост объёма `ExecutiveDashboard` (887 строк) повторится в кокпите | низкий | Реестр плиток: каждая плитка — отдельный модуль со своим `useValue` и `Detail`; оболочка не знает об их содержимом |

## 17. Границы: что этим ТЗ не делается

Чтобы объём не расползался, фиксируется явно.

- **Не меняются расчётные формулы**: Score, веса ГОСТ, ALE, ROSI, Ц_ОМ, вето, матрица акцепта.
  ТЗ поднимает существующие расчёты в интерфейс, не корректируя ни один.
- **Не переписываются существующие страницы.** Девять дашбордов и семь разделов получают
  только чтение разреза и кнопку возврата.
- **Не меняется ролевая модель и RBAC.** Новых ролей и новых прав нет (§11.2).
- **Не добавляется редактирование данных на кокпите**, кроме решения по мере — и оно
  выполняется существующим `MeasureDecisionModal` с серверной проверкой SoD.
- **Не трогается контур LLM**: конвейер E0–E7, самопроверка и журнал доверия остаются как есть.
  Меняется только подача вывода на экране руководителя (§9.2).
- **Не выполняется интеграция с ITSM** и внешними менеджерами задач — остаётся в границах
  ТЗ-19 (Р-8).
- **Не создаётся мобильное приложение.** Адаптивность — в пределах веб-интерфейса (§12.5).
