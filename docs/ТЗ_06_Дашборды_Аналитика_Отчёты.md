## 1. Принципы построения аналитики

### 1.1. Разделение расчёта и интерпретации

Любой числовой показатель на дашборде рассчитан детерминированно по формулам стандарта. Текстовая интерпретация формируется отдельно и визуально отделена. Пользователь всегда может понять, где данные, а где вывод из них.

### 1.2. Ролевая специализация

Каждый дашборд отвечает на вопросы конкретной роли:

| Роль | Главный вопрос | Дашборд |
|------|----------------|---------|
| Топ-менеджмент | Что требует моего решения? | Исполнительный |
| Менеджер качества | Где просело и что предложить? | Менеджерский, динамика |
| Аналитик | Какие данные внести и проверить? | Аналитический, сбои |

Один и тот же набор данных подаётся по-разному, а не показывается всем одинаково с разграничением по кнопкам.

### 1.3. От общего к частному

Информация раскрывается каскадно: сводка → информационная система → характеристика → подхарактеристика → метрика. Пользователь не тонет в 55 метриках сразу, а спускается по уровням только там, где увидел проблему.

### 1.4. Единая цветовая семантика

Уровни качества окрашиваются по RAG-палитре (`theme/ragPalette.ts`) во всех представлениях одинаково. Палитра акцентов оформления (`AccentKey`) намеренно отделена от палитры данных — цвет карточки не конкурирует с цветом показателя.

## 2. Модель качества как основа расчётов

### 2.1. Две модели

| Модель | Стандарт | Область |
|--------|----------|---------|
| Базовая | ISO/IEC 25010:2023 | Качество программного продукта: 8 характеристик, **31 подхарактеристика** |
| Расширенная | ГОСТ Р 59898-2021 | Качество систем ИИ: 4-уровневая иерархия, 37 подхарактеристик, из них 7 специфичных для ИИ |

### 2.2. Расчёт показателя метрики

```
X = val_a / val_b × 100 %
```

где `val_a` — числитель (например, число успешных операций), `val_b` — знаменатель (общее число операций). Валидация `val_b > 0` выполняется на уровне формы и на бэкенде.

### 2.3. Уровни качества

| Уровень | Диапазон X | Цвет RAG |
|---------|-----------|----------|
| Критический | < 25 % | Красный |
| Низкий | 25 – 50 % | Оранжевый |
| Средний | 50 – 75 % | Жёлтый |
| Высокий | 75 – 100 % | Зелёный |

### 2.4. Интегральный показатель

Интегральный показатель качества (ИПК) агрегирует значения метрик до уровня подхарактеристик, характеристик и системы в целом. Для модели ГОСТ 59898 применяются настраиваемые веса подхарактеристик (миграция 007, этап E2) — вклад подхарактеристики в итог задаётся явно.

### 2.5. Неизмеримые метрики

Метрика может быть помечена флагом «неизмеримо» (миграция 004). Такая метрика **исключается из расчёта**, а не считается нулём.

> **Обоснование.** Отсутствие данных — это не плохое качество. Если метрику невозможно измерить в текущем периоде, засчитывать её как 0 % означало бы штрафовать систему за пробел в измерениях и искажать интегральный показатель. Правила закреплены в блоке D ТЗ v16 (задача T-55).

В интерфейсе такие метрики отображаются отдельной пометкой, а не пустым значением — чтобы не возникало впечатления утерянных данных.

### 2.6. Тепловая карта (`LevelHeatmap`)

Матрица «информационные системы × характеристики» с окраской ячеек по уровню качества. Даёт мгновенное представление о том, где сосредоточены проблемы. Корректность отображения (согласованность цветов и значений между представлениями) доработана в блоке E ТЗ v16, задача T-56.

## 3. Исполнительный дашборд

**Маршрут:** `dashboard/executive`
**Роли:** `ADMIN` + legacy (`CTO`, `CEO`, `CIO`, `EXECUTIVE`)
**Источник данных:** `GET /api/v1/reports/executive-dashboard`

### 3.1. Назначение

Дашборд построен вокруг **очереди решений**, а не вокруг данных. Руководитель не вносит метрики и не считает показатели — он утверждает меры, реагирует на аномалии и оценивает риски.

### 3.2. Состав

**1. Карточка аналитики (акцент `gold`).**
Управленческое резюме, сформированное локальной LLM: состояние в 2–3 предложениях, конкретная рекомендация, наиболее просевшая характеристика. Все числа в тексте прошли grounding-проверку — выдуманных значений быть не может (см. [ТЗ-05](./ТЗ_05_LLM_Интеграция_и_Обучение.md), раздел 7).

**2. Интегральный показатель качества** по всем ИС с индикатором изменения относительно предыдущего периода.

**3. Тренды качества** — график ECharts по периодам.

**4. Очередь мер на утверждение.** Предложения со статусом «предложена». Просроченные выделяются отдельно. Переход в `MeasureDecisionModal`: утвердить / отклонить / вернуть на доработку с обязательным обоснованием.

**5. Сработавшие триггеры рисков** — интеграция с радаром рисков (`GET /api/v1/risks/triggered`).

**6. Уведомления об аномалиях** — `NotificationBell` в шапке.

### 3.3. Решение для роли

Кнопка «Предложить меру» на этом дашборде отсутствует: предложение — зона ответственности менеджера качества. Это прямое следствие инварианта SoD (см. [ТЗ-02](./ТЗ_02_Ролевая_Модель_и_Безопасность.md)).

## 4. Дашборд менеджера качества

**Маршрут:** `dashboard/manager`
**Роли:** `QUALITY_MANAGER`, `ADMIN`

### 4.1. Назначение

Операционная работа с качеством: найти просадку, разобраться в причине, предложить меру.

### 4.2. Каскадное раскрытие (задачи T-26…T-30)

```
Сводка по всем ИС
    └── Информационная система
            └── Характеристика
                    └── Подхарактеристика
                            └── Метрики
```

Каждый уровень — `CollapsibleCard` с premium-оформлением, акцентной полосой и анимированным раскрытием. Состояние раскрытия сохраняется при навигации.

### 4.3. Состав

| Блок | Содержание |
|------|-----------|
| Метрики качества по ИС | Значения с окраской по RAG-палитре |
| `MeasureDevelopmentPanel` | Формирование предложения: описание, обоснование, срок, привязка к характеристике |
| `ProfessionalJudgmentsPanel` | Профессиональные суждения по характеристикам |
| `TechDebtCard` | Накопленный технический долг качества |
| `MeasuresAiAnalyticsCard` | LLM-анализ эффективности ранее внедрённых мер |

### 4.4. Решение для роли

Кнопка «Утвердить» отсутствует принципиально — не скрыта по условию, а не предусмотрена. Менеджер качества предлагает; решение принимает другой человек. Попытка обойти это через прямой запрос к API блокируется проверкой в `governance/service.py`.

## 5. Динамика качества

**Маршрут:** `dashboard/manager/dynamics`
**Роли:** `QUALITY_MANAGER`, `ADMIN` + legacy
**Источник данных:** `GET /api/v1/reports/system-dynamics?system_id=...`
**Состояние:** `dynamicsSlice`

### 5.1. Назначение

Анализ изменения качества во времени (ТЗ v14; доработки v15 — задачи T-21, T-22).

### 5.2. Интегральный показатель по кварталам

Все информационные системы отображаются **на одной диаграмме** ECharts. Это осознанное решение: сравнение систем между собой важнее детализации каждой в отдельности — оно показывает, отстаёт ли конкретная система от общего тренда или снижение носит общий характер.

### 5.3. Обнаружение аномалий

**Алгоритм:** если модуль изменения интегрального показателя между соседними периодами составляет **12 процентных пунктов и более**, отклонение помечается как аномальное.

**Обоснование порога.** Меньшие колебания объясняются естественной вариативностью измерений и сменой состава измеримых метрик. Больший разрыв означает либо реальное изменение качества, либо ошибку в данных — в обоих случаях требуется объяснение человека.

**Реакция системы:**
1. Точка на графике выделяется.
2. Создаётся уведомление.
3. Пользователю предлагается зафиксировать причину отклонения.

Причина сохраняется и в дальнейшем передаётся в контекст LLM как часть истории (`history_block`), обеспечивая преемственность выводов между периодами.

### 5.4. Метки эффективности мер (задача T-15, R2)

На временной шкале отмечаются моменты внедрения утверждённых мер. Это позволяет визуально сопоставить меру и последующее изменение показателя — то есть ответить на вопрос **«сработала ли мера»**.

> **Контекст.** Отсутствие отслеживания эффективности мер было зафиксировано как пробел в код-ревью 2026-07-06: система умела предлагать и утверждать меры, но не показывала результат. Метки на шкале закрывают этот разрыв, замыкая цикл управления.

### 5.5. Детализация

**`DynamicsModal`** — тренд по отдельной характеристике, отдельно от интегрального показателя. Позволяет увидеть, что за стабильным общим показателем скрывается разнонаправленное движение характеристик.

**`Sparkline`** — компактные встроенные графики трендов в таблицах и карточках.

## 6. Аналитика технических сбоев

**Маршрут:** `dashboard/incidents`
**Роли:** `QUALITY_MANAGER`, `ADMIN` + legacy
**Источники:** `GET /api/v1/incidents/analytics`, `GET /api/v1/incidents`
**Основание:** ТЗ v16, блок A (задачи T-36…T-43)

### 6.1. Назначение

Учёт и анализ технических отказов информационных систем.

### 6.2. Ключевые показатели

| Показатель | Расчёт | Смысл |
|-----------|--------|-------|
| Общее число сбоев | Количество записей за период | Объём проблем |
| Среднее время устранения | Среднее по `resolved_at − occurred_at` | Скорость реакции |
| MTBF | Средняя наработка на отказ | Устойчивость системы |
| Доступность, % | Доля времени работоспособного состояния | Итоговое качество услуги |

### 6.3. Представления

- **Фильтры:** информационная система, период, критичность, категория (`GET /incidents/categories`).
- **Распределение по категориям** — структура проблем.
- **Тренд числа сбоев по времени** — динамика.
- **Распределение времени устранения** — выявление «долгих хвостов».
- **Реестр инцидентов** с отметкой об устранении (`POST /incidents/{iid}/resolve`).

### 6.4. Внесение данных

- Массовый импорт из таблицы (`POST /incidents/import`), вкладка «Загрузка сбоев» рабочего места.
- Ручное создание (`POST /incidents`).
- Изменение записи (`PATCH /incidents/{iid}`).

### 6.5. Связь с моделью качества

Модуль сбоев — не изолированная статистика. Показатели надёжности и доступности служат **объективным источником значений метрик** модели качества, в отличие от экспертных оценок. Это повышает достоверность интегрального показателя: часть метрик подтверждается фактами эксплуатации, а не суждениями.

## 7. Радар рисков

**Маршрут:** `dashboard/risk-radar`
**Роли:** `QUALITY_MANAGER`, `ADMIN` + legacy
**Основание:** ТЗ v11, раздел R3; задача T-16

### 7.1. Назначение

Перевод работы с рисками из реактивного режима в проактивный.

### 7.2. База рисков

Накопительный реестр: описание риска, привязка к ИС и характеристике, критичность, условие срабатывания триггера. Реестр пополняется по мере эксплуатации и не обнуляется между периодами — это организационная память о том, что уже случалось.

### 7.3. Триггеры

Триггер — условие на значения метрик. При его выполнении риск считается сработавшим и попадает в радар (`GET /api/v1/risks/triggered`, фильтры по системе и характеристикам).

> **Смысл механизма.** Сбой фиксируется постфактум. Триггер срабатывает, когда метрика приблизилась к опасной границе, но отказа ещё не произошло. Это даёт время на предупреждающую меру.

### 7.4. Заземление LLM

Записи базы рисков передаются модели как `risks_block` в контексте рассуждения. Линза `RISK` конвейера прямо отвечает на вопрос: *какие риски из переданной базы активируются, каковы последствия и меры минимизации*. Благодаря этому рекомендации опираются на накопленный опыт организации, а не на общие соображения.

### 7.5. Операции

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/api/v1/risks` | Реестр |
| POST | `/api/v1/risks` | Создание записи |
| PATCH | `/api/v1/risks/{risk_id}` | Изменение |
| POST | `/api/v1/risks/{risk_id}/archive` | Архивация |
| GET | `/api/v1/risks/triggered` | Сработавшие триггеры |
| GET | `/api/v1/risks/search` | Поиск |

## 8. План задач

**Маршрут:** `dashboard/taskplan`
**Роли:** `QUALITY_MANAGER`, `ADMIN` + legacy
**Состояние:** `governanceSlice`
**Основание:** задачи T-23, T-24

### 8.1. Пузырьковая шкала (`TaskBubbleTimeline`)

Меры представлены пузырьками на оси времени: положение — срок, размер — значимость, цвет — статус.

### 8.2. Жизненный цикл меры

```
предложена ──► утверждена ──► в работе ──► выполнена
     │              │
     ├──► отклонена │
     │              ↓
     └──► возвращена на доработку
                    │
              [просрочка]
                    ↓
              эскалация ──► решение по эскалации
```

### 8.3. Контроль сроков и эскалация

Просроченные меры выделяются визуально и подлежат эскалации на уровень выше. Эскалация — отдельный поток с собственными эндпоинтами (`escalate`, `escalation-decision`, `resolve-escalation`).

### 8.4. Техническая заметка

Все операции governance реализованы как асинхронные thunk-функции в `governanceSlice`; вызов только через типизированный `useAppDispatch`. Состояние мер хранится в БД (задача T-10, миграция 008), а не во фронтенде — это обеспечивает согласованность между пользователями и аудируемость.

## 9. Профессиональные суждения

**Маршруты:** `assessments/:id/review`, вкладка «Профессиональное суждение» рабочего места

### 9.1. Назначение

Не всё качество измеримо числом. Профессиональное суждение фиксирует экспертную оценку характеристики с обоснованием — это признанная практика оценки качества, а не обходной путь вокруг метрик.

### 9.2. Процесс

```
Система формирует перечень характеристик, требующих суждения
        ↓  GET /assessments/judgments-pending
Эксперт заполняет суждения (ProfessionalJudgmentModal)
        ↓  PUT /assessments/{period_id}/judgments
Формируется итоговое заключение с участием LLM
        ↓  GET /assessments/{period_id}/judgment-conclusion
Пользователь оценивает качество заключения (ConclusionFeedback)
        ↓  POST /assessments/conclusion-feedback
Обратная связь попадает в feedback.jsonl «резервного мозга»
```

### 9.3. Роль в обучении системы

Суждения — основной источник доменных знаний:
- передаются в конвейер рассуждения как `judgments_block`;
- сохраняются в память «мозга» для припоминания в будущих периодах;
- исправленные пользователем заключения (`human_edits()`) служат наиболее ценным материалом для возможного дообучения модели.

### 9.4. Аудит

`FilledJudgmentsCard` показывает историю: кто, когда и что зафиксировал. Суждения не перезаписываются анонимно — сохраняется авторство.

## 10. Аномалии и уведомления

### 10.1. Типы уведомлений

| Тип | Источник | Действие пользователя |
|-----|----------|----------------------|
| Обнаружена аномалия | Отклонение ≥ 12 п.п. между периодами | Указать причину |
| Мера просрочена | Наступил срок, статус не «выполнена» | Эскалировать или обновить срок |
| Мера утверждена | Решение по предложению | Приступить к исполнению |

### 10.2. Компонент `NotificationBell`

Расположен в шапке приложения. Поддерживает статусы «прочитано / не прочитано» и переход из уведомления непосредственно на страницу, где требуется действие.

### 10.3. Принцип

Уведомление всегда ведёт к действию. Информационных уведомлений без адресата действия система не формирует — иначе колокольчик быстро перестают замечать.

## 11. Отчётность

### 11.1. Страница отчётов

**Маршрут:** `reports`, доступ — все авторизованные роли.

| Возможность | Эндпоинт |
|-------------|----------|
| Данные отчётности | `GET /api/v1/reports/excel-data` |
| Матрицы по периоду | `GET /api/v1/reports/assessment-period/{period_id}/matrices` |
| Выгрузка XLSX | `GET /api/v1/reports/export/{period_id}/xlsx` |
| Загрузка отчёта | `POST` (загрузка файла) |

### 11.2. Фильтры (задача T-11, R3)

Поиск по тексту и фильтрация по характеристике — позволяют быстро найти нужный фрагмент в объёмном отчёте.

### 11.3. Отчёт о соответствии стандарту

`GET /api/v1/ai-assessments/{period_id}/conformance-report` — отчёт о соответствии требованиям ГОСТ Р 59898-2021 для систем ИИ.

Вкладка «Отчёты CSV» рабочего места — выгрузка данных оценки в машиночитаемом виде для дальнейшей обработки.

## 12. Демо-данные

### 12.1. Сценарий (версия 2, ТЗ v14)

| Параметр | Значение |
|----------|----------|
| Информационные системы | 4 |
| Периоды | 6 кварталов |
| Метрики | 55 на систему и период |

Сценарии подобраны так, чтобы демонстрировать разные типы поведения: устойчивое улучшение, деградация, стабильность, волатильность. Это позволяет показать работу детектора аномалий и меток эффективности мер на реалистичных данных.

### 12.2. Согласованность фронтенда и бэкенда

Моки фронтенда (`data/mockDashboards.ts`, `mockIncidents.ts`, `mockScaleData.ts`) согласованы с сидами БД: одни и те же системы, периоды и порядки величин. Переключение между демо-режимом и работой с реальным бэкендом не даёт визуальных расхождений (дефекты DEF-12…DEF-15 закрыты в ТЗ v14).

### 12.3. Ключ сортировки периодов

`period_sort_key` обеспечивает корректное определение «последнего периода» независимо от способа сортировки. Это устраняет класс ошибок, при которых «Q1 2025» оказывался позже «Q4 2025» из-за лексикографического сравнения меток.

### 12.4. Ролевая видимость

Состав демо-данных зависит от роли вошедшего пользователя: каждая роль видит сценарий, релевантный её задачам. Состояние демо-режима сохраняется в `localStorage` под ключами версии v2.
