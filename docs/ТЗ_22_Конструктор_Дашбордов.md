## 1. Постановка задачи

До конструктора состав каждого дашборда был **зашит в его компонент**. Практические следствия:

* «Взять карточку сбоев на дашборд менеджера» означало правку кода и релиз.
* Роли видели фиксированный набор: то, что руководителю не нужно, убрать было нельзя, а то,
  что нужно, — добавить.
* Персонализация существовала точечно и по-разному: у владельца риска (BL-008) — свой выбор
  состава виджетов, у остальных дашбордов — никакого.

Требование заказчика (2026-08-08): **«настроить дашборды под себя, перетаскивать по странице»**.

## 2. Принятое решение: дашборд как список id из каталога

Введены три сущности (`frontend/src/dashboards/types.ts`):

| Сущность | Смысл |
| :--- | :--- |
| `CardDef` | Карточка в общесистемном каталоге: глобальный id, заголовок, дашборд-происхождение (`source`), право (`perm`), нужный скоуп (`scope`), размеры по умолчанию и минимумы, подсказка, миниатюра, компонент |
| `DashboardDef` | Штатный дашборд: ключ, право, заголовок и **дефолтная раскладка** — пока пользователь ничего не трогал, дашборд выглядит ровно как до конструктора |
| `CardLayout` | Позиция и размер карточки в 12-колоночной сетке (формат `react-grid-layout`) |

**Инвариант обратной совместимости:** дефолтная раскладка каждого штатного дашборда повторяет
его исходную вёрстку один в один. Пользователь, не открывавший «Настроить», не замечает,
что дашборд стал сборным.

**Инвариант стабильности id:** id карточки формата `<источник>.<имя>` лежит в сохранённых
prefs пользователей. Переименование id = молчаливая потеря карточки у всех, кто её поставил
(она отсеется при `sanitize` в `useDashboardLayout`). Id не переименовываются.

## 4. Скоупы: карточка вне родного дашборда

Карточка, унесённая на чужой дашборд, обязана тащить за собой состояние и данные своего
происхождения: карточки менеджера живут вокруг выбранной ИС → характеристики → подхарактеристики,
карточки риск-экономики — вокруг четырёх общих запросов контура.

Решение — **скоупы** (`dashboards/scopes/`). На 2026-08-31 их **девять**: `manager`, `exec`,
`incidents`, `taskplan`, `dynamics`, `analytics`, `mytasks`, `econ`, `cockpit`.

`ScopeHost` смотрит, карточки каких скоупов **реально присутствуют в раскладке**, и оборачивает
сетку только нужными провайдерами. Положил на «Мой дашборд» одну плитку сбоев — поднимется скоуп
сбоев, а менеджерский запрос к `/assessments/dashboard` не уйдёт вовсе.

Порядок вложения провайдеров зафиксирован порядком в `SCOPES`: иначе React пересоздавал бы
поддерево при добавлении карточки нового скоупа и сбрасывал состояние соседей.

Карточки со `scope: 'none'` самодостаточны — сами тянут данные и держат своё состояние.

## 5. Сетка, режим редактирования и хранение раскладки

| Параметр | Решение |
| :--- | :--- |
| Сетка | `react-grid-layout`, **12 колонок** (как antd `Row/Col` — дефолтные раскладки переносились из старой вёрстки один в один), высота строки 30px, отступы 16px |
| Перетаскивание | только **за шапку карточки** (`draggableHandle: .dash-card__handle`). Внутри карточек живые элементы — сортируемые таблицы, селекторы, кликабельные ячейки теплокарты; при перетаскивании за любую точку обычный клик превращался бы в микро-перетаскивание |
| Изменение размера | за правый нижний угол, правую и нижнюю грань; минимумы `minW`/`minH` из `CardDef` |
| Узкий экран (< 992px) | сетка схлопывается в одну колонку в порядке раскладки, редактирование выключено: тащить карточки пальцем по 12-колоночной сетке в 375px — лотерея |
| Заполнение ячейки | карточка обязана занимать 100% высоты ячейки и скроллить содержимое внутри себя. Для карточек с собственной `<Card>` — обёртка `FillCard` + CSS-класс `.dash-fill-card` (иначе под карточкой в ячейке остаётся пустота, тем большая, чем сильнее её растянули) |
| Хранение | серверные prefs `PUT /iam/me/preferences`, ключ `dashboards[<key>] = { layout, v }` (JSONB) — раскладка едет за пользователем между устройствами |
| Управление | «Настроить» → правка; «Готово» — сохранить, «Отмена» — откатить черновик, «Сбросить» — вернуть штатный вид |

## 6. RBAC: персонализация поверх прав

**Каталог — предпочтение поверх прав, а не право.** Карточку, чей `perm` не выдан пользователю,
нельзя ни увидеть в каталоге, ни отрисовать из сохранённой раскладки.

Второе важно практически: администратор может забрать право уже после того, как пользователь
собрал дашборд. Проверка `cardAllowed(def, permissions)` применяется и при показе каталога,
и при рендере сохранённой раскладки — RBAC остаётся верхней границей персонализации.

Право карточки совпадает с правом дашборда-источника. Управленческие карточки несут **список**
прав (`['view.dashboard.cto', 'view.dashboard.ceo']`) — один дашборд открыт двум ролям.

## 7. Каталог в интерфейсе: поиск, группировка, миниатюры

`CardPicker.tsx` — шторка «Каталог карточек»:

* **Группировка по дашборду-происхождению.** Пользователь ищет не «карточку `exec.heatmap`»,
  а «ту теплокарту с управленческого». Карточки текущего дашборда идут первой группой с меткой
  «этот дашборд» — чаще всего возвращают убранную свою.
* **Поиск** по заголовку, подсказке и названию дашборда, нечувствительный к регистру и «ё».
* **Уже добавленные показываются отмеченными** («на дашборде», кнопка неактивна), а не прячутся:
  увидеть, что карточка уже взята, полезнее, чем гадать, куда она делась.
* **Миниатюра формы карточки** (`thumbnail`) — маленькое SVG рядом с названием: рамка тоном,
  жирная полоса-«крупная цифра», опционально ломаная тренда и стрелка дельты. Показывает **форму**
  того, что добавляешь, а не живые данные. Поле необязательное; на 2026-08-31 миниатюры несут
  15 карточек кокпита (`TileThumbnail.tsx`).

## 8. Производительность: ленивая загрузка карточек

Каталог по построению ссылается на все карточки системы, и бандлер видит в этом один общий граф —
при статических импортах общий чанк вырастал до **~440 КБ gzip**, и открытие ЛЮБОГО дашборда
тянуло весь каталог разом.

Решение: карточка грузится лениво (`lazyCard`), своим чанком на модуль-источник; у каждой ячейки
свой `Suspense` (общий на всю сетку не годится — одна медленная карточка гасила бы весь дашборд).
Сам `CardPicker` тоже грузится только при первом открытии.

Исключение — `RISK_CARDS` и `COCKPIT_CARDS`: они самодостаточны, лежат в небольших модулях,
дробить их нечего.

## 10. Критерии приёмки

1. **Обратная совместимость.** Пользователь, не открывавший «Настроить», видит каждый штатный
   дашборд ровно таким, каким он был до конструктора.
2. **Сборка.** С любого дашборда можно добавить любую доступную по правам карточку системы,
   переставить её и изменить размер; «Готово» сохраняет раскладку на сервер, она переживает
   перезаход и смену устройства.
3. **Сброс.** «Сбросить» возвращает штатную раскладку дашборда.
4. **RBAC.** Карточка без права не видна в каталоге и не рендерится из сохранённой раскладки —
   в том числе если право забрали после сборки.
5. **Автономность карточки.** Карточка, унесённая на «Мой дашборд», работает: поднимается её
   скоуп, чужие скоупы запросов не делают.
6. **Геометрия.** Карточка занимает всю высоту ячейки и скроллит содержимое внутри себя;
   при растягивании под ней не возникает пустоты.
7. **Узкий экран.** < 992px — одна колонка, кнопка «Настроить» неактивна с пояснением.
8. **Каталог.** Поиск находит карточку по названию, подсказке и дашборду; уже добавленные
   отмечены; у карточек с миниатюрой видна форма.
9. **Проверки.** `npm run typecheck`, `npm test`, `npm run check:contrast`, `npm run build` —
   зелёные.

## 11. Границы: что этим ТЗ не делается

* **Не вводится редактор самих карточек** — состав каталога задаётся кодом; пользователь
  выбирает из готового, но не конструирует новые карточки.
* **Не вводится обмен раскладками между пользователями** (шаблоны, «поделиться дашбордом»).
* **Не меняются данные и расчёты карточек** — конструктор занимается только составом
  и геометрией; логика каждой карточки остаётся за её собственным ТЗ.
* **Не переносятся на конструктор административные экраны** (Пользователи, Права, Веса,
  Качество LLM) — это формы, а не аналитические полотна.
* **Не правятся ссылки `БТ-500` в комментариях кода** — отдельная задача, поведения не касается
  (см. врезку о нумерации и ТЗ-00, Р-10).
