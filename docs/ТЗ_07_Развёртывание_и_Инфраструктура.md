## 2. Базовые сервисы

### 2.1. `postgres`

PostgreSQL 14 (Alpine). Хранит все доменные данные. Проверка готовности (`healthcheck`) — обязательное условие запуска `backend` и `celery_worker`: они стартуют только после `condition: service_healthy`.

Данные сохраняются в именованном томе `pgdata` и переживают пересоздание контейнера.

### 2.2. `redis`

Redis 7 (Alpine). Две функции: брокер очереди Celery и кэш. Том `redisdata`.

### 2.3. `backend`

**Команда запуска:**

```
uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

**Подключения:**
- `DATABASE_URL=postgresql+asyncpg://asok_user:***@postgres:5432/asok_is`
- `REDIS_URL=redis://redis:6379/0`

**Тома:**

| Том | Режим | Назначение |
|-----|-------|------------|
| `./backend:/app` | rw | Исходный код (горячая перезагрузка в разработке) |
| `./models/llm:/app/models/llm` | **ro** | Каталог GGUF-моделей — только чтение |
| `./models/llm_brain:/app/models/llm_brain` | **rw** | «Резервный мозг» — требует записи |
| `/app/__pycache__` | anonymous | Изоляция кеша Python от хоста |

> **Почему каталоги моделей и «мозга» разделены.** Файлы моделей неизменны и монтируются только на чтение — это защищает их от случайной порчи. «Мозг» же постоянно пополняется памятью, обратной связью и корпусом, поэтому вынесен в отдельный том с правом записи. Такое разделение и делает знания переносимыми между моделями (см. [ТЗ-05](./ТЗ_05_LLM_Интеграция_и_Обучение.md), раздел 6).

### 2.4. `celery_worker`

**Команда запуска:**

```
celery -A app.workers.tasks.celery_app worker --loglevel=info --concurrency=2
```

Собирается из того же образа, что и бэкенд, и монтирует те же тома — включая «мозг» на запись, поскольку воркер тоже сохраняет память рассуждений.

**Проверка готовности.** У воркера нет HTTP-порта, поэтому стандартная проверка из Dockerfile (`curl :8000`) всегда завершалась неуспешно и контейнер числился нездоровым. Проверка переопределена на опрос брокера:

```yaml
healthcheck:
  test: ["CMD-SHELL", "celery -A app.workers.tasks.celery_app inspect ping -t 10 | grep -q pong || exit 1"]
  interval: 30s
  timeout: 15s
  retries: 3
  start_period: 30s
```

### 2.5. `frontend`

**Команда запуска:**

```
npm run dev -- --host 0.0.0.0 --port 3000
```

**Переменные:**
- `VITE_API_BASE_URL=/api/v1` — относительный путь;
- `VITE_PROXY_TARGET=http://backend:8000` — цель проксирования Vite.

> **Решение об относительном пути.** Запросы идут на тот же хост, откуда загружена страница, и проксируются Vite на бэкенд. Благодаря этому одна и та же сборка работает и на `localhost`, и по публичной ссылке туннеля — единый источник, без настройки CORS под каждый адрес.

Том `/app/node_modules` анонимный — зависимости контейнера не перетираются каталогом хоста.

## 3. Профили развёртывания

Опциональные сервисы активируются флагом `--profile`.

### 3.1. Локальная разработка

```bash
docker compose up -d
```

Доступ: интерфейс — `http://localhost:3000`, API и Swagger — `http://localhost:8000/docs`.

### 3.2. Быстрый туннель (случайная ссылка)

```bash
docker compose --profile tunnel up -d
```

Cloudflared со случайным адресом `trycloudflare.com`. Протокол http2 вместо quic — обходит проблемы QUIC/UDP и ошибку Cloudflare 1033.

### 3.3. Именованный туннель

```bash
docker compose --profile named up -d
```

Туннель на постоянный домен. Требует токен именованного туннеля Cloudflare.

### 3.4. Туннель ngrok

```bash
docker compose --profile ngrok up -d
```

### 3.5. Прямой доступ с TLS

```bash
docker compose --profile direct up -d
```

Поднимает Caddy на портах 80 и 443. Конфигурация `infra/Caddyfile`:

```
asokis.ai, www.asokis.ai {
    encode zstd gzip
    reverse_proxy frontend:3000
}
```

Caddy самостоятельно получает сертификат Let's Encrypt по протоколу HTTP-01. Обязательные условия: реальный доступ из интернета к портам 80 и 443, A-запись домена на публичный IP в режиме DNS-only (серое облако в Cloudflare).

### 3.6. Динамический DNS

```bash
docker compose --profile ddns up -d
```

Обновляет DNS-запись Cloudflare при смене публичного IP — актуально для развёртывания на канале без статического адреса.

## 6. Переменные окружения

Значения задаются в файле `.env` в корне проекта (подключается через `env_file`).

### 6.1. База данных и кэш

| Переменная | Назначение |
|-----------|-----------|
| `POSTGRES_PASSWORD` | Пароль пользователя `asok_user` |
| `DATABASE_URL` | Строка подключения (формируется в compose) |
| `REDIS_URL` | Адрес Redis |

### 6.2. Безопасность

| Переменная | Назначение |
|-----------|-----------|
| `JWT_SECRET_KEY` | Ключ подписи JWT (не короче 32 символов) |
| `DEMO_MODE` | `true` — доступны демонстрационные учётные записи; в продуктивной среде **обязательно `false`** |

**Контроль конфигурации (fail-fast).** Метод `Settings.security_issues()` (`backend/app/infrastructure/config.py`) при старте проверяет три условия:

1. `JWT_SECRET_KEY` не равен небезопасному значению по умолчанию;
2. длина `JWT_SECRET_KEY` не меньше 32 символов;
3. `DATABASE_URL` не содержит пароль по умолчанию (`asok_pass123`).

Реакция зависит от режима (`app/main.py:28-37`):

| Режим | Поведение при найденных проблемах |
|-------|-----------------------------------|
| `DEMO_MODE=true` | Предупреждение в журнал, старт разрешён |
| `DEMO_MODE=false` | `RuntimeError` — **приложение не стартует** |

> Молчаливый запуск в продуктивной среде со значениями по умолчанию опаснее отказа в запуске: скомпрометированный ключ подписи JWT позволяет выпустить токен любой роли. Требование соответствует ГОСТ Р 57580 и 152-ФЗ в части управления секретами.

### 6.3. LLM

| Переменная | Значение по умолчанию | Назначение |
|-----------|----------------------|-----------|
| `LLM_ENABLED` | `True` | Включение подсистемы |
| `LOCAL_LLM_MODEL_DIR` | `models/llm` | Каталог GGUF-моделей |
| `LOCAL_LLM_MODEL_FILE` | `auto` | Автоподбор новейшего файла либо явное имя |

| `LLM_BRAIN_DIR` | `models/llm_brain` | Каталог «резервного мозга» |

## 7. Инициализация базы данных

### 7.1. Порядок

```
Запуск postgres → healthcheck пройден
        ↓
Запуск backend → применение миграций Alembic (001…010)
        ↓
init_db.py — базовая инициализация
        ↓
Сиды справочников:
  seed_iso25010.py     — модель качества ISO 25010
  seed_korp_quality.py — корпоративная модель качества
  seed_scale.py        — шкалы и уровни
  seed_metrics.py      — определения метрик
        ↓
Сиды демо-данных:
  seed_demo.py         — комплексный демо-сценарий
  seed_governance.py   — меры и решения
  seed_risk_base.py    — база рисков
  seed_incidents.py    — реестр сбоев
```

### 7.2. Миграции

Применяются автоматически при старте бэкенда. Прямое изменение схемы БД запрещено — каждое изменение оформляется отдельной миграцией Alembic с реализованным откатом.

### 7.3. Автосид Excel-файлов

Автоматический сид из проектных Excel-файлов **опционален**: функция `seed_project_excel_files` проверяет наличие файлов и молча пропускает шаг, если их нет. Файлы намеренно отвязаны от сборки образа — загрузка Excel пользователем реализована как отдельная функциональность.

### 7.4. Выгрузка датасета

`export_llm_dataset.py` — формирование обучающего набора из накопленных суждений, мер и правок пользователей.

## 8. Работа с GPU

### 8.1. Требования

NVIDIA GPU, актуальный драйвер, `nvidia-container-toolkit`. На Windows — через WSL2.

### 8.2. Запуск

```bash
docker compose -f docker-compose.yml -f docker-compose.gpu.yml up -d --build
```

Оверрайд собирает `backend` и `celery_worker` по `dockerfile.cuda` (сборка `llama.cpp` с поддержкой CUDA), устанавливает `LLM_N_GPU_LAYERS=-1` и резервирует все доступные устройства:

```yaml
deploy:
  resources:
    reservations:
      devices:
        - driver: nvidia
          count: all
          capabilities: [gpu]
```

### 8.3. Возврат на CPU

Поднять стек без GPU-файла:

```bash
docker compose up -d
```

### 8.4. Когда применять

GPU оправдан для моделей 7B–14B при интерактивных сценариях. Для моделей до 1B и фоновой генерации достаточно CPU.

### 9.1. Выбор варианта

| Вариант | Когда подходит | Ограничения |
|---------|----------------|-------------|
| Быстрый туннель | Демонстрация, временный показ | Ссылка меняется при перезапуске |
| Именованный туннель | Постоянный внешний доступ | Требует домен в Cloudflare |
| ngrok | Альтернатива при недоступности Cloudflare | Ограничения бесплатного тарифа |
| Прямой доступ (Caddy) | Продуктивное развёртывание | Нужны открытые порты 80/443 и белый IP |

> **Замечание по безопасности.** Все варианты внешнего доступа публикуют систему в интернет. Для банковского контура штатным является развёртывание **без внешнего доступа**, внутри защищённого периметра. Туннели предназначены для демонстраций и разработки.

| Симптом | Причина | Решение |
|---------|---------|---------|
| Бэкенд не стартует, ошибка о секретах | `DEMO_MODE=false` без заданных секретов | Задать `JWT_SECRET_KEY` в `.env` |
| Бэкенд перезапускается | PostgreSQL не прошёл healthcheck | Проверить журнал `postgres`, доступность тома `pgdata` |
| `celery_worker` числится нездоровым | Брокер недоступен | Проверить `redis`, выполнить `celery inspect ping` |
| Выводы всегда детерминированные | Модель не загрузилась | Проверить `llm-status`, наличие `.gguf`, объём ОЗУ |
| Ошибка Cloudflare 1033 | Проблема QUIC/UDP | Профиль `tunnel` уже использует http2 — проверить сеть |
| Фронтенд не видит API | Неверный `VITE_PROXY_TARGET` | Проверить, что бэкенд доступен по имени `backend` |

### 10.4. Требования к ресурсам

| Конфигурация | ОЗУ | Комментарий |
|--------------|-----|-------------|
| Без LLM (`LLM_ENABLED=False`) | 4 ГБ | Полная функциональность кроме текстовых выводов |
| Модель 0.5B | 6 ГБ | Отладка, слабое оборудование |
| Модель 9B | 12 ГБ | Сбалансированный вариант |
| Модель 14B | 16 ГБ и более | Максимальное качество выводов |

Каталог `models/llm` занимает около 44 ГБ при полном наборе моделей. Для развёртывания достаточно одного файла.

## 11. Развёртывание на Linux

Платформа кросс-платформенна: тот же Docker-стек поднимается на Linux **без изменения кода** и теми же командами. Ниже — отличия от Windows/Docker Desktop, которые нужно учесть на нативном Linux.

### 11.1. Предварительные требования

- **Docker Engine 24+** и плагин **Docker Compose v2** (команда `docker compose`, не устаревший `docker-compose`). Установка на Debian/Ubuntu:
  ```bash
  curl -fsSL https://get.docker.com | sh
  sudo apt-get install -y docker-compose-plugin
  ```
- Добавить пользователя в группу `docker`, чтобы не требовался `sudo`: `sudo usermod -aG docker $USER` (нужно перелогиниться).
- Для GPU-варианта — драйвер NVIDIA и `nvidia-container-toolkit` **нативно, без WSL2**.

### 11.2. Регистрозависимая файловая система (обязательно)

Файловая система Linux различает регистр. Сборка использует **явное имя Dockerfile строчными буквами** во всех compose-файлах:

```yaml
build:
  context: ./backend
  dockerfile: dockerfile
```

Это критично: сокращённая форма `build: ./backend` искала бы `Dockerfile` (с заглавной) и падала бы с ошибкой «Dockerfile not found», поскольку файлы названы `backend/dockerfile`, `backend/dockerfile.cuda`, `frontend/dockerfile`. На Windows/macOS (регистронезависимая ФС) это скрыто, на Linux — фатально.

### 11.3. Права на записываемые тома

Бэкенд и Celery-воркер работают под пользователем `appuser` (**UID 1000**). Каталог «резервного мозга» монтируется на запись (`./models/llm_brain → /app/models/llm_brain`). Если на хосте владелец каталога не UID 1000, контейнер не сможет записывать память рассуждений и обратную связь. Перед первым запуском:

```bash
mkdir -p models/llm_brain models/llm
sudo chown -R 1000:1000 models/llm_brain
```

На Windows/Docker Desktop права проксирует VM, поэтому шаг не нужен — он специфичен для нативного Linux.

### 11.4. SELinux (RHEL, Fedora, CentOS Stream)

При включённом SELinux bind-mount по умолчанию недоступен контейнеру (ошибки «Permission denied» на смонтированных каталогах). Разрешение — пометить каталог проекта меткой контейнера:

```bash
sudo chcon -Rt container_file_t .
```

Альтернатива — суффикс `:z` у томов исходников/моделей или запуск с `--security-opt label=disable` (только для dev-стенда).

### 11.5. Окончания строк

Репозиторий фиксирует **LF** для файлов, исполняемых или читаемых в Linux-контейнерах (`.gitattributes`: `dockerfile`, `*.sh`, `*.mjs`, `*.yml`, `Caddyfile`). Это исключает сбои сборки из-за символов CR при клонировании на Windows и последующем переносе на Linux.

### 11.6. Хостовый `node_modules`

Файл `frontend/.dockerignore` исключает `node_modules` из контекста сборки. Иначе `COPY . .` затянул бы в образ нативные бинарники (`esbuild`/`rollup`), собранные под ОС хоста, — на Linux фронтенд упал бы на старте с ошибкой несовместимого бинарника. Файл удалять нельзя.

### 11.7. Запуск

Команды идентичны Windows:

```bash
git clone <repo> && cd asok-is
cp .env.example .env          # задать JWT_SECRET_KEY (≥32 симв.) и POSTGRES_PASSWORD
docker compose up -d --build
```

Интерфейс — `http://<host>:3000`, API и Swagger — `http://<host>:8000/docs`. Проверка готовности:

```bash
docker compose ps            # все сервисы в статусе healthy
docker compose exec -T backend python -m pytest -q
```
