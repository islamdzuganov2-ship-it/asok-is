## 3. Безопасность

### 3.1 Что сделано хорошо

- **Серверный RBAC (BL-008) реализован по-настоящему:** каталог из 37 прав (`iam/permissions.py`), матрица `role_permissions`, `require_permission` резолвит права из БД с кэшем. Фронт гейтит по тем же ключам (`RequirePermission`), то есть UI-гейт и серверный гейт согласованы.
- **Защита от самоблокировки:** `PROTECTED_SUPERADMIN_PERMISSIONS` — права управления доступом нельзя снять у `SUPER_ADMIN`, они не входят даже в `ADMIN_PERMISSIONS`. Дашборд качества LLM доступен исключительно суперадминистратору — как требует БТ-397.
- **Контроль конфигурации на старте:** `settings.security_issues()` + `main.py:30–39` — в проде (`DEMO_MODE=false`) дефолтный `JWT_SECRET_KEY`, ключ короче 32 символов или дефолтный пароль БД **не дают приложению стартовать**. Это правильная реализация требования ГОСТ Р 57580 / 152-ФЗ.
- **Валидация загрузки файлов** (`dataio/router.py:34–40`): расширение, лимит 10 МБ, магическая сигнатура ZIP; `os.path.basename` + UUID-префикс закрывают path traversal.
- `.env` в `.gitignore` и не в индексе. Секреты читаются только из окружения.

### 3.2 КР-06 · В демо-режиме API полностью открыт с правами ADMIN

**Тяжесть: критическая (по риску эксплуатации).**

`iam/deps.py:19–48` — `get_current_user`:

```python
if not credentials or not credentials.credentials:
    if settings.DEMO_MODE:
        return {"id": "...0001", "username": "demo", "roles": ["ADMIN"]}
```

…и то же самое в ветке `except JWTError`. То есть при `DEMO_MODE=true`:
- запрос **без токена** обслуживается как ADMIN;
- запрос с **истёкшим или подделанным** токеном обслуживается как ADMIN.

`DEMO_MODE` по умолчанию **`True`** (`config.py:86`). Стенд проброшен наружу через Cloudflare Tunnel (БТ-500…БТ-503), домен `asokis.ai` разрешён в CORS-регулярке. Итог: **любой, кто знает адрес туннеля, получает полный административный доступ к API без аутентификации.**

Отдельный аспект: тихая деградация невалидного токена до ADMIN маскирует ошибки — фронт не увидит 401 и не отправит на релогин.

**Рекомендация (минимальная, без слома демо):**
1. Разделить флаги: `DEMO_MODE` (демо-данные) и `DEMO_AUTH_BYPASS` (обход аутентификации), по умолчанию `false`.
2. Невалидный/просроченный токен — **всегда 401**, даже в демо-режиме; обход разрешить только для полностью отсутствующего заголовка.
3. При включённом обходе — предупреждение в лог на каждый запрос и баннер в UI.
4. Не поднимать туннель, пока обход включён (проверка в compose-профиле).

### 3.3 КР-07 · Чтение всего тела загрузки до проверки размера

**Тяжесть: значимая.** `dataio/router.py:112` и `:144`:

```python
content = await file.read()      # весь файл в память
_validate_xlsx(file.filename, content)   # ... и только потом проверка 10 МБ
```

Загрузка файла на 1 ГБ будет полностью буферизована в RAM до отказа. При лимите памяти контейнера (которого сейчас нет — см. КР-09) это гарантированный OOM. Дополнительно: `.xlsx` — это ZIP, а защиты от zip-бомбы (проверки распакованного объёма) нет.

**Рекомендация:** читать потоком чанками с обрывом по превышению лимита; после распаковки проверять суммарный размер листов.

### 3.4 КР-08 · Синхронная файловая запись в обработчике запроса

**Тяжесть: значимая.** `open(file_path, "wb")` в async-эндпоинтах (`dataio/router.py:118, 163, 280`) блокирует event loop на время записи. Для 10 МБ это десятки миллисекунд, но вместе с `load_workbook(...)` в том же обработчике (строка 166 — парсинг Excel синхронно!) блокировка становится секундной и останавливает обслуживание **всех** остальных запросов.

**Рекомендация:** `await asyncio.to_thread(...)` для записи и парсинга либо полностью через Celery (как уже сделано в `/upload`).

## 4. Производительность и утилизация ресурсов

Заказчик отдельно ставил задачу по утечкам памяти и CPU (БТ-520…БТ-524), ТЗ v17 описывает RES-01…RES-14. **В `main` не внедрено ничего из первой очереди.**

### 4.1 КР-09 · Нет лимитов памяти и CPU у контейнеров (RES-01)

**Тяжесть: критическая.** В `docker-compose.yml` нет ни `mem_limit`, ни `cpus`, ни `deploy.resources.limits` — ни для `backend`, ни для `celery_worker`. Резидентная GGUF-модель + `--reload` + неограниченный кэш работают без потолка: при исчерпании памяти хоста ядро убивает произвольный процесс.

### 4.2 КР-10 · `--reload` в профиле с резидентной моделью (RES-08)

**Тяжесть: критическая.** `docker-compose.yml:73`:

```
command: uvicorn app.main:app --host 0.0.0.0 --port 8000 --reload
```

`--reload` держит **два** процесса (reloader + worker) и перезапускает воркер при любом изменении файла — вместе с ним заново загружаются веса модели. Это прямая причина того, что заказчик наблюдал как «утечку памяти»: не утечка, а удвоение резидента и повторные загрузки. В базовом (не override) compose `--reload` быть не должно.

### 4.3 КР-11 · Неограниченный кэш ответов LLM (RES-04)

**Тяжесть: значимая.** `modules/llm/service.py:58` — `_cache: dict[int, str] = {}`, читается/пишется в трёх местах (строки 439, 463, 497 и 456, 484, 531), очищается только при `reload()`. Растёт неограниченно, каждый ответ — до `LLM_MAX_TOKENS` текста. Нужен `functools.lru_cache`-подобный контейнер с потолком.

### 4.4 КР-12 · Нет ограничения очереди на `_infer_lock` (RES-05)

**Тяжесть: значимая.** `service.py:57` — `_infer_lock = threading.Lock()`. Каждый параллельный запрос к LLM занимает поток из пула `asyncio.to_thread` и ждёт на блокировке неограниченно долго. При десятке одновременных запросов пул потоков исчерпывается и **блокируются обычные, не-LLM эндпоинты**. Нужен fail-fast (семафор с `try_acquire` → 503/«занято»).

### 4.5 КР-13 · Нет бюджета времени на инференс (RES-03/RES-06)

**Тяжесть: значимая.** `LLM_TIMEOUT_S` в конфиге отсутствует. Ни один вызов `complete()` не ограничен по времени; конвейер `reasoning.py` (53 КБ — крупнейший файл backend) делает несколько проходов подряд. Запрос может висеть минутами, честного fallback по таймауту нет.

### 4.6 КР-14 · `/llm-status` читает три файла с диска на каждый вызов (RES-07)

**Тяжесть: значимая.** `reporting/router.py:52` → `llm_service.model_info()` → `brain.stats()` (`brain.py:272`), который вызывает `_read_jsonl(_MEMORY)`, `_read_jsonl(_CORPUS)`, `_read_jsonl(_FEEDBACK)` и `_read_json(_META)` — **синхронно, в event loop**, без кэша. Эндпоинт опрашивается фронтом для переключателя «Моки ↔ LLM». По мере роста «резервного мозга» файлы растут, и каждый опрос статуса читает их целиком.

### 4.7 КР-15 · Не отключён LLM у Celery-воркеров (RES-02)

**Тяжесть: значимая.** `LLM_ENABLED` не переопределён для сервиса `celery_worker` в compose — воркер грузит **вторую копию весов** в память. Для 7-гигабайтной модели это +7 ГБ на пустом месте.

### 4.8 КР-16 · 20 неограниченных выборок в роутерах

**Тяжесть: значимая.** 20 вызовов `scalars().all()` в роутерах без `LIMIT`. На демо-объёмах (4 системы) незаметно; при заявленных заказчиком **100+ систем и 1000+ сбоев** (БТ-264) это выльется в многосекундные ответы и рост памяти.

## 5. Данные, миграции, развёртывание

### 5.1 КР-17 · Alembic не применяется при запуске стека

**Тяжесть: критическая.**

- `docker-compose.yml:73` — команда backend: только `uvicorn`, никакого `alembic upgrade head`.
- Схема создаётся в `main.py:startup_init` через `Base.metadata.create_all()` — **и только при `DEMO_MODE=true`** (строка 87–88: `if not settings.DEMO_MODE: return`).
- В репозитории 12 миграций (`001…012`), которые в рабочем стеке никогда не выполняются.

Следствия:
1. **В production (`DEMO_MODE=false`) схема не создаётся вообще** — приложение стартует на пустой БД и падает на первом запросе, если миграции не прогнали руками.
2. `create_all` создаёт только отсутствующие таблицы и **не применяет ALTER**. Любое изменение колонки, живущее в миграции, на демо-стенде не применится — БД будет расходиться с моделями.
3. Требование БТ-507 («production полагается исключительно на Alembic; не комбинировать `create_all` с `alembic upgrade head`») формально соблюдено разделением по режимам, но фактически создало худший вариант: в проде нет ни того, ни другого.

**Рекомендация:** `command: sh -c "alembic upgrade head && uvicorn ..."` для всех режимов; `create_all` оставить только в `scripts/init_db.py` для локальной разработки; добавить тест-страж «модели == head миграций» (`alembic check`).

### 5.2 КР-18 · Демо-пароли в исходниках

**Тяжесть: мелкая (в контексте демо) / значимая (при выходе наружу).** `scripts/seed_demo.py:194–202` — 8 учётных записей с паролями открытым текстом (`superadmin/Super123!`, `admin/Admin123!`, …). Для демо это осознанное решение; в связке с КР-06 и публичным туннелем — реальный вектор.

Требование от 2026-08-08 («через настройки менять состав дашбордов галочками — настроить дашборды под себя») подразумевает персонализацию для всех, а не только для топ-менеджмента.

Кроме того, флагов всего **четыре** (`execAnalytics`, `execDynamics`, `execTaskPlan`, `execIncidents`), тогда как требование — «абсолютно всех доступных» дашбордов. Дашборды CTO, CEO, «Основное», «Основное — риск», «Риск-радар» переключателей не имеют.

### 6.4 КР-21 · Drag & drop дашбордов (БТ-445) не реализован

**Тяжесть: значимая (функциональная дыра).** Требование «в режиме изменения дашборды должны быть перетаскиваемыми по странице» не реализовано нигде: ни библиотеки DnD в зависимостях, ни соответствующего состояния в `uiSlice`.

### 6.5 КР-22 · Мёртвое состояние темы

**Тяжесть: мелкая.** В `uiSlice` одновременно живут `theme: 'light' | 'dark'` с редьюсером `toggleTheme` и настоящий `themeName: ThemeName`. Первое ни на что не влияет (тему определяет `themeName`), но экспортируется и может быть случайно использовано.

### 6.6 КР-23 · Осиротевший `frontend/src/pages/package.json`

**Тяжесть: мелкая (гигиена).** В каталоге страниц лежит второй `package.json` со **старыми** версиями зависимостей (antd ^5.12.5 против ^5.17.0, TypeScript ^5.3.3 против ^5.4.5) и без `vitest`. Файл не используется сборкой, но сбивает с толку и может быть подхвачен инструментами, ищущими ближайший `package.json`. Аналог задачи T-03/T-04 (гигиена), не доведённой до конца.

## 7. LLM-подсистема

### 7.1 Что сделано хорошо

- **Модель-агностичность (БТ-362) реализована честно:** `LOCAL_LLM_MODEL_FILE="auto"` → автоподбор GGUF, чтение метаданных модели, `LLM_CHAT_FORMAT="auto"` → шаблон чата из файла модели, а при его отсутствии — откат на обычное завершение текста (`complete()`, `service.py:309–353`). Это действительно работает с любой GGUF, а не только с instruct-моделями.
- **«Резервный мозг» (БТ-363)** — `LLM_BRAIN_DIR` отдельно от каталога моделей, обучение переносится между моделями.
- **Grounding-контроль**: фильтры чисел, отбраковка эхо-ответов и вырожденных повторов, детерминированный fallback на каждом этапе — конвейер работает и без модели.
- **Тест-страж на терминологию** (`test_no_methodology_jargon_in_user_facing_output`) — БТ-378 не просто выполнен, а защищён от регресса.
- `LLM_TEMPERATURE = 0.1` — максимум детерминизма, как требовал заказчик.

### 7.2 Замечания

- См. КР-11…КР-15 — вся группа ресурсных ограничений отсутствует.
- `reasoning.py` (53 КБ) и `selfcheck.py` (48 КБ) — крупнейшие файлы проекта; конвейер и самооценка заслуживают декомпозиции по этапам.
