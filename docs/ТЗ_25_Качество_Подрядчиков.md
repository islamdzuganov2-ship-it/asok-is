# ТЗ-25. Модуль «Качество подрядчиков»

> **Версия:** 1.0 · **Дата:** 2026-09-26 · **Статус:** specced
> **Задача бэклога:** ДП-20 ([ТЗ-24](./ТЗ_24_Доработки_По_Сверке_Презентации.md), [BACKLOG.md → BL-010](./BACKLOG.md#bl-010)).
> **Коды требований:** `ДП-20.1…ДП-20.6` (фазы ниже).
> **Основание:** слайд 17 презентации «Качество — условие договора с подрядчиком»; риск-экон.
> ТЗ §2.4 («смешанная модель — усиление аргумента про вендоров»), §5 виджет 7 «Разрез по вендорам».

## 1. Зачем

Слайд 17 обещает три вещи: (1) целевые значения качества по подхарактеристикам в ТЗ и договоре
для каждой системы; (2) балл релиза и трассировку требований на приёмке каждого релиза;
(3) запрет перехода в эксплуатацию без решения комитета при баллах ниже порога и
ответственность подрядчика вплоть до отказа от оплаты. Там же — факт с реального портфеля:
функциональная пригодность 14 % из-за отсутствия трассировки требований в ТЗ.

Экономический смысл (риск-экон. §2.4): претензии и удержания по объективной метрике вместо
споров «по ощущениям»; бенчмарк вендорских линий против внутренних. В расчёт окупаемости
презентации (слайд 19) эффект сознательно не включён.

## 3. Границы

**Входит:** справочник подрядчиков; договоры и контрактный профиль качества; выгрузка
приложения «требования к качеству» для ТЗ и договора; реестр релизов; оценка релиза;
трассировка требований; гейт ввода в эксплуатацию с решением комитета; черновики претензий;
аналитика по подрядчикам.

**Не входит:** юридически значимая электронная подпись; ведение претензионной работы после
отправки претензии; интеграция с платёжными системами и ERP; оценка персонала подрядчика.

## 5. Функциональные требования

### ДП-20.1. Справочник подрядчиков и договоры

1. CRUD подрядчиков и договоров; привязка ИС к договору.
2. Контрактный профиль: для каждой пары «договор × ИС» — таблица подхарактеристик ГОСТ 25010
   (31 строка), в которой задаются целевое и минимально допустимое X и вес. Профиль по умолчанию
   предзаполняется текущим баллом ИС + 0,1 (не выше 1) — стартовая точка для переговоров.
3. Выгрузка «Приложение к ТЗ/договору: требования к качеству» — `GET /contracts/{id}/quality-appendix?format=xlsx|pdf`:
   по каждой ИС — подхарактеристика, метрика, формула (A/B, прямая/обратная), целевое и
   минимальное значение, способ измерения, тип доказательства (RE-21), последствия недостижения.

### ДП-20.2. Релизы и оценка релиза

1. Реестр релизов по ИС; релиз создаётся вручную или импортом CSV
   (ИС, версия, подрядчик, даты).
2. Оценка релиза — период оценки вида `RELEASE`, привязанный к релизу: те же метрики и формулы,
   что у квартальной оценки, но только по подхарактеристикам контрактного профиля.
3. **Балл релиза** = `weighted_system_score` по подхарактеристикам профиля с весами профиля
   (`quality/scoring.py`). Отдельно — список подхарактеристик ниже минимально допустимого X.

### ДП-20.3. Трассировка требований

1. Требования релиза загружаются CSV (id, название, источник) или вводятся вручную.
2. Результаты тестов — CSV (id требования, результат) или адаптер порта `TestManagementSource`
   по конфигурации (при заглушке — только CSV).
3. **Покрытие трассировки** = доля требований с результатом `PASS` среди всех требований релиза;
   отдельно — доля требований без тестов.
4. Покрытие трассировки подставляется как значение метрики подхарактеристики «Функциональная
   полнота» оценки релиза (A = требований с `PASS`, B = всего), с типом доказательства C.

### ДП-20.4. Гейт ввода в эксплуатацию

1. Статусы релиза: `PLANNED → IN_ACCEPTANCE → ACCEPTED | ACCEPTED_WITH_CONDITIONS | REJECTED → IN_PRODUCTION`.
2. Переход в `ACCEPTED` без решения комитета допускается, только если одновременно: балл релиза
   ≥ `release_gate_min_score` (по умолчанию 0,61), нет подхарактеристик ниже минимально
   допустимого X, покрытие трассировки ≥ `release_gate_min_trace` (по умолчанию 0,9).
3. Иначе нужен **решение комитета**: `ALLOW_WITH_CONDITIONS` (условия и срок; по каждому условию
   автоматически создаётся мера с ответственным подрядчиком) или `REJECT`. Решение принимает
   обладатель права `contracts.release.decide` (по умолчанию `CTO`) с номером протокола.
4. `IN_PRODUCTION` недоступен из `REJECTED`. Попытка — 409 с объяснением.
5. Параметры гейта — в экране финпараметров (ТЗ-24 ДП-09), изменения — в журнал аудита (ДП-24).

### ДП-20.5. Претензии и удержания

1. **Релизные сбои.** Ночная задача ищет сбои категории `RELEASE` с `release_id` в пределах
   гарантийного срока договора. Сумма = Σ стоимости сбоев (C_ТС, ТЗ-24 ДП-01) × доля по договору
   или фиксированный штраф за сбой — по условию договора.
2. **Недостижение целевых значений.** Для каждой подхарактеристики ниже минимально допустимого X
   в оценке релиза — штраф из договора.
3. Итог ограничивается максимальным удержанием договора. Формируется черновик претензии
   (`DRAFT`) с приложением: список сбоев со стоимостью, оценка релиза, выписка из профиля.
4. Смена статуса претензии — право `contracts.claims.edit`; отправка во внешний мир — вне системы.

### ДП-20.6. Аналитика по подрядчикам (виджет 7 риск-экон. §5)

Карточка каталога дашбордов «Подрядчики» и страница раздела:
- по каждому подрядчику: ALE систем договора; доля сбоев по вине подрядчика (`RELEASE` с его
  релизом или `vendor_involved`); MTTR вендорских линий против внутренних; стоимость трудозатрат
  L2/L3 вендора; средний балл релизов и его динамика; сумма претензий и удержаний;
- кассовая и некассовая экономия — строго по риск-экон. §2.4 (сверх пакета часов — кассовая;
  внутри пакета — отложенная до контрактного цикла).

## 7. Интерфейс

Раздел «Подрядчики» (группа «Разрезы»), вкладки: «Договоры и профили», «Релизы»,
«Претензии», «Аналитика». Карточка релиза: балл и отклонения по профилю, трассировка
(покрытие, список требований без тестов), блок гейта с кнопками по правам, связанные сбои.
Подсказки «как посчитано» — по образцу плиток кокпита.

## 8. Критерии приёмки

1. Для договора с двумя ИС выгружается приложение с целевыми значениями по 31 подхарактеристике.
2. Релиз с баллом 0,55 не переходит в `ACCEPTED` без решения комитета; с решением
   «с условиями» — переходит, условия стали мерами с ответственным подрядчиком.
3. Покрытие трассировки 12 из 20 требований даёт «Функциональную полноту» 0,6 в оценке релиза.
4. Два релизных сбоя в гарантийный срок формируют черновик претензии с суммой по условиям договора,
   не выше максимального удержания.
5. Аналитика по подрядчикам сходится с суммами по отдельным сбоям и релизам.
6. Роль без `view.risk_economics` не видит сумм претензий.
