## 1. Общая структура фронтенда

### 1.1. Технологический стек

| Компонент | Технология | Назначение |
|-----------|-----------|------------|
| Язык | TypeScript 5.x | Строгая типизация, контракты с API |
| Библиотека UI | React 18 | Компонентная модель, Suspense, lazy-загрузка |
| Сборщик | Vite | Быстрая пересборка в dev, оптимизированный prod-бандл |
| UI-фреймворк | Ant Design 5 | Базовые контролы, таблицы, модальные окна, формы |
| Состояние | Redux Toolkit | Глобальное состояние приложения |

| Графики | ECharts | Динамика качества, аналитика сбоев, радар рисков |
| Тесты | Vitest | Модульные тесты бизнес-логики |

### 1.2. Структура каталогов

```
frontend/src/
├── App.tsx                    # Корневой компонент, маршрутизация
├── main.tsx                   # Точка входа, провайдеры
├── pages/                     # Страницы верхнего уровня (10 файлов)
│   └── dashboard/             # Дашборды (6 файлов)
├── components/                # Переиспользуемые компоненты (20 файлов)
├── store/
│   ├── index.ts               # Конфигурация store
│   ├── hooks.ts               # useAppDispatch / useAppSelector
│   ├── api/apiSlice.ts        # RTK Query — 31 эндпоинт
│   └── slices/                # authSlice, dynamicsSlice, governanceSlice, uiSlice

├── data/                      # Демо-данные (моки)
└── utils/                     # Вспомогательные функции
```

### 1.3. Принципы построения интерфейса

1. **Ролевая адаптивность.** Интерфейс не показывает пользователю то, что ему недоступно: меню, маршруты и кнопки действий фильтруются по роли. Отказ в доступе обрабатывается и на уровне маршрута (`RequireRole`), и на уровне API (403).

2. **Каскадное раскрытие (cascading reveal).** Сложные дашборды не вываливают всю информацию сразу: пользователь идёт от общего к частному — сводка → ИС → характеристика → подхарактеристика. Реализовано через `CollapsibleCard`.

3. **Детерминизм перед интерпретацией.** Числовые показатели всегда рассчитаны на бэкенде по формулам стандарта; LLM-текст подаётся отдельным блоком и визуально отделён, чтобы пользователь не путал расчёт и интерпретацию.

4. **Ленивая загрузка.** Все страницы подключены через `React.lazy` + `Suspense` с `PageLoader`, что снижает объём первичного бандла.

5. **Единый визуальный язык.** Все карточки, отступы, тени и радиусы берутся из `theme/premium.ts`; произвольные inline-стили с «магическими» значениями не допускаются.

## 2. Маршрутизация и защита маршрутов

### 2.1. Карта маршрутов

Маршрутизация определена в `frontend/src/App.tsx`. Все маршруты, кроме `/login`, обёрнуты в `RequireAuth` и `AppLayout`.

| Маршрут | Компонент | Допустимые роли |
|---------|-----------|-----------------|
| `/login` | `LoginPage` | без авторизации |
| `dashboard` | `DashboardRouter` | все авторизованные |
| `dashboard/analytics` | `DashboardPage` | все авторизованные |
| `dashboard/executive` | `ExecutiveDashboard` | `ADMIN` + legacy (`CTO`, `CEO`, `CIO`, `EXECUTIVE`) |
| `dashboard/manager` | `ManagerDashboard` | `QUALITY_MANAGER`, `ADMIN` |
| `dashboard/manager/dynamics` | `QualityDynamicsPage` | `QUALITY_MANAGER`, `ADMIN` + legacy |
| `dashboard/taskplan` | `TaskPlanDashboard` | `QUALITY_MANAGER`, `ADMIN` + legacy |
| `dashboard/incidents` | `IncidentsAnalyticsPage` | `QUALITY_MANAGER`, `ADMIN` + legacy |
| `dashboard/risk-radar` | `RiskRadarPage` | `QUALITY_MANAGER`, `ADMIN` + legacy |
| `assessments/new` | `AssessmentWorkspacePage` | `TEST_ANALYST`, `QUALITY_MANAGER`, `ADMIN` |
| `assessments/:id/input` | `MetricsInputPage` | `TEST_ANALYST`, `QUALITY_MANAGER`, `ADMIN` |
| `assessments/:id/review` | `ExpertReviewPage` | `QUALITY_MANAGER`, `ADMIN` |
| `ai-assessments` | `AiAssessmentPage` | `TEST_ANALYST`, `QUALITY_MANAGER`, `ADMIN` |
| `reports` | `ExcelReportsPage` | все авторизованные |
| `risks` | `RiskBasePage` | все авторизованные |
| `admin/flags` | `AdminFlagsPage` | `ADMIN` + legacy |

### 2.2. Механизмы защиты

**`RequireAuth`** — проверяет наличие валидного токена в `authSlice`. При отсутствии перенаправляет на `/login` с сохранением исходного маршрута для возврата после входа.

**`RequireRole`** — принимает проп `allowedRoles: string[]`. Если роль текущего пользователя не входит в список, отображается экран отказа в доступе. Legacy-коды (`CTO`, `CEO`, `CIO`, `EXECUTIVE`) перечисляются явно наравне с `ADMIN`, что обеспечивает совместимость со старыми токенами.

**`DashboardRouter`** — не является защитой, а выполняет ролевую маршрутизацию по умолчанию: определяет, какой дашборд показать пользователю при переходе на `/dashboard`:
- `ADMIN` и legacy-роли → `ExecutiveDashboard`;
- `QUALITY_MANAGER` → `ManagerDashboard`;
- `TEST_ANALYST` → аналитический дашборд.

> **Важно.** Фронтенд-защита — это UX, а не безопасность. Реальное разграничение выполняется на бэкенде (см. [ТЗ-02](./ТЗ_02_Ролевая_Модель_и_Безопасность.md), раздел «Точки контроля»). Скрытая кнопка не мешает отправить запрос напрямую, поэтому каждый эндпоинт проверяет роль самостоятельно.

## 3. Страницы

### 3.1. LoginPage

**Назначение.** Точка входа в систему.

**Функционал:**
- форма ввода логина и пароля;
- отправка `POST /auth/login`, получение JWT-токена;
- сохранение токена под ключом `'token'` в `localStorage` (ключ согласован между `MetricsInputPage`, `authSlice` и `apiSlice` — рассогласование `asok_access_token` устранено, ретест QA 2026-06-30);
- декодирование роли из токена и запись в `authSlice`;
- ролевое перенаправление после успешного входа через `DashboardRouter`;
- отображение ошибок аутентификации (неверные учётные данные, недоступность сервера).

**Демо-учётные записи** (доступны только при `DEMO_MODE=true`): `admin`, `manager`, `analyst` — см. `DEMO_USERS` в `backend/app/modules/iam/router.py`.

---

### 3.2. DashboardPage (аналитический дашборд)

**Назначение.** Общий аналитический обзор, доступный всем авторизованным ролям.

**Функционал:**
- KPI-карточки верхнего уровня (внедрены задачами T-53, T-54): интегральный показатель качества, число ИС в оценке, количество открытых мер, количество сбоев за период;
- тепловая карта уровней качества по характеристикам (`LevelHeatmap`);
- карточка технического долга (`TechDebtCard`);
- переходы в специализированные дашборды.

**Ролевое поведение.** Состав карточек зависит от роли: `TEST_ANALYST` не видит блок мер и решений, поскольку не участвует в governance-цикле.

---

### 3.3. AssessmentWorkspacePage — «Внесение данных»

**Назначение.** Единое рабочее место для всех операций с данными оценки. Реализовано как страница с семью вкладками (`Tabs`). Переименование раздела «Оценка» → «Внесение данных» выполнено в рамках ТЗ v16 (блок B).

| # | Ключ вкладки | Название | Содержание |
|---|--------------|----------|------------|
| 1 | `new` | Новая оценка | Создание периода оценки: выбор ИС, год, квартал, метка периода |
| 2 | `edit` | Корректировка | `AssessmentCorrectionPanel` — правка завершённых оценок (T-47) |
| 3 | `judgment` | Профессиональное суждение | `JudgmentEntryPanel` — внесение недостающих суждений (T-48) |
| 4 | `reports` | Отчёты CSV | Выгрузка данных оценки в CSV |
| 5 | `upload-assessments` | Загрузка оценок | Импорт метрик из Excel (`DataUploadPanel`) |
| 6 | `upload-incidents` | Загрузка сбоев | Импорт реестра технических инцидентов |
| 7 | `measures` | Реестр мер | `MeasuresRegistryCard` — просмотр и управление мерами |

**Логика вкладок.** Вкладки 2–4 требуют выбранного периода оценки; при его отсутствии отображается `Alert` с подсказкой создать оценку на первой вкладке. Вкладка 7 доступна только ролям, участвующим в governance (`QUALITY_MANAGER`, `ADMIN`).

#### Вкладка «Корректировка» (`AssessmentCorrectionPanel`, задача T-47)

Показывает **завершённые** оценки — периоды, заполненные по всем 31 подхарактеристике. Порядок работы:

1. Завершённая оценка (`COMPLETE`) закрыта на правку. Сначала выполняется «Открыть на корректировку» (`POST /assessments/{id}/reopen`).
2. Значения правятся и сохраняются (`PUT /assessments/{id}/metrics`); X и уровень пересчитывает бэкенд.
3. Оценка завершается заново (`POST /assessments/{id}/finalize`).

> **Обоснование блокировки.** Без явной разблокировки цифры дашбордов менялись бы задним числом: показатель за закрытый квартал мог бы измениться без следа. Явный шаг переоткрытия делает правку осознанным действием.

RTK Query инвалидирует тег `Dashboard`, поэтому дашборды отражают правку без перезагрузки страницы.

#### Вкладка «Профессиональное суждение» (`JudgmentEntryPanel`, задача T-48)

Показывает **только** те метрики, по которым суждение ещё не внесено (`GET /assessments/judgments-pending`). Строка — пара «характеристика × подхарактеристика», у которой есть оценка (рассчитан X либо проставлено «невозможно измерить»), но нет записи в `professional_judgments`.

- Ввод использует ту же модель, что и `ProfessionalJudgmentsPanel`: `PUT /assessments/{period_id}/judgments` (upsert по паре). Связка «оценка ↔ суждение» сохраняется, а заполненная строка уходит из списка.
- **Сортировка — худший балл первым**, «невозможно измерить» в начале: менеджер по качеству начинает с проблемных зон.
- Флаг `all_periods` включает в выдачу архивные периоды; по умолчанию берётся последний.

#### Режимы источника данных

Обе новые вкладки поддерживают два режима (эталон — `IncidentsAnalyticsPage`):

| Режим | Источник | Поведение при сохранении |
|-------|----------|--------------------------|
| `live` | API | Запись в БД |
| `mock` | Демо-набор `mockAssessments.ts` | Правки живут в состоянии вкладки; в БД не пишутся |

В демо-режиме подпись и сообщение при сохранении честно указывают, что изменения не сохраняются в базу — пользователь не введён в заблуждение.

### 3.4. NewAssessmentPage

**Назначение.** Создание нового периода оценки (используется также как содержимое первой вкладки рабочего места).

**Функционал:**
- выбор информационной системы из реестра (`getSystems`);
- указание года и квартала;
- формирование метки периода (например, «Q3 2025»);
- расчёт `period_sort_key` для корректного определения «последнего периода» при сортировке;
- вызов `createAssessmentPeriod`;
- переход к вводу метрик после создания.

### 3.5. MetricsInputPage

**Назначение.** Ручной ввод значений метрик качества.

**Функционал:**
- таблица метрик с редактируемыми полями `val_a` (числитель) и `val_b` (знаменатель);
- валидация: `val_b > 0` — деление на ноль блокируется на уровне формы;
- автоматический расчёт `X = val_a / val_b × 100` и присвоение уровня качества;
- обработка неизмеримых метрик: метрика может быть помечена как «не применимо» и исключается из расчёта интегрального показателя (правила блока D ТЗ v16);
- сохранение через `saveAssessmentMetrics` (`PUT /assessments/{id}/metrics`), после чего бэкенд пересчитывает уровни;
- отображение рассчитанных значений через `getCalculatedMetrics`;
- финализация оценки (`finalizeAssessment`) и повторное открытие (`reopenAssessment`).

**Уровни качества** окрашиваются по RAG-палитре (`theme/ragPalette.ts`).

### 3.6. ExpertReviewPage

**Назначение.** Экспертная проверка результатов оценки и формирование профессиональных суждений.

**Функционал:**
- список характеристик, требующих экспертного суждения (`getPendingJudgments`);
- форма суждения по характеристике: оценка, обоснование, ссылки на подтверждающие данные (`ProfessionalJudgmentModal`);
- сохранение пакета суждений (`saveJudgments`);
- итоговое заключение по оценке (`getJudgmentConclusion`) — формируется с участием LLM;
- обратная связь по заключению (`ConclusionFeedback`) — оценка пользователем качества LLM-вывода, данные попадают в `feedback.jsonl` «резервного мозга»;
- карточка заполненных суждений (`FilledJudgmentsCard`) с историей.

### 3.7. ExcelReportsPage

**Назначение.** Формирование и выгрузка отчётов.

### 3.8. AiAssessmentPage

**Назначение.** Интерфейс LLM-аналитики.

**Функционал:**
- запуск генерации аналитического заключения по выбранной оценке;
- отображение многоаспектного рассуждения (BL-005): последовательность шагов методологии с промежуточными выводами;
- карточки рекомендаций;
- `MeasuresAiAnalyticsCard` — LLM-анализ эффективности предложенных мер;
- `ActionInsightModal` — детализация конкретной рекомендации с переходом к созданию меры.

**Гарантии.** Все числа в выводе LLM берутся из переданного контекста; вердикт об уровне качества формируется детерминированным движком правил (`gate`), а модель только объясняет его человеческим языком.

### 3.9. RiskBasePage

**Назначение.** Управление базой рисков (введена ТЗ v11, раздел R3).

**Функционал:**
- реестр записей о рисках: описание, привязка к ИС и характеристике, критичность;
- условия срабатывания триггеров (пороговые значения метрик);
- CRUD-операции над записями;
- накопительный характер: база рисков растёт со временем и служит источником заземления (grounding) для LLM.

---

### 3.10. AdminFlagsPage

**Назначение.** Административная настройка функциональных флагов.

**Функционал:**
- переключатели видимости разделов исполнительного дашборда (`ExecFeatureKey`);
- каждый переключатель сопровождается мини-превью раздела на SVG — видно, что именно включается;
- доступ только для `ADMIN` и legacy-ролей верхнего уровня.

> **Техническая заметка.** Флаги — **клиентские**: хранятся в `uiSlice` (действие `setExecFeature`) и не обращаются к бэкенду. Это настройка отображения для текущего пользователя, а не системная конфигурация. Серверных админ-эндпоинтов (`/api/v1/admin/...`) в системе нет; управление LLM вынесено в группу `/reports` (`llm-status`, `llm-models`, `llm-reload`).

## 4. Дашборды

### 4.1. ExecutiveDashboard — исполнительный дашборд

**Роль:** `ADMIN` и legacy-коды верхнего уровня.

**Назначение.** Управленческий взгляд на качество ИТ-ландшафта: что происходит, что требует решения.

**Состав:**

1. **Карточка LLM-аналитики.** Текстовое резюме состояния, сформированное локальной моделью: 2–3 предложения о состоянии, одна конкретная рекомендация, наиболее просевшая характеристика. Источник — `getExecutiveDashboard` (`/reports/executive-dashboard`).

2. **Интегральный показатель качества** по всем ИС с индикатором изменения относительно предыдущего периода.

3. **Тренды качества** — график ECharts по периодам.

4. **Очередь мер на утверждение** — меры со статусом «предложена», ожидающие решения. Количество просроченных выделяется отдельно. Переход к `MeasureDecisionModal` для принятия решения.

5. **Интеграция радара рисков** — сработавшие триггеры (`getTriggeredRisks`).

6. **Уведомления об аномалиях** — `NotificationBell` в шапке.

**Ключевое решение для роли.** Руководитель не вносит данные и не считает метрики — он принимает решения. Поэтому дашборд построен вокруг очереди действий: утвердить/отклонить меру, отреагировать на аномалию, оценить риск.

---

### 4.2. ManagerDashboard — дашборд менеджера качества

**Роль:** `QUALITY_MANAGER`, `ADMIN`.

**Назначение.** Операционная работа с качеством: где просело, почему, что предложить.

**Состав:**

1. **Каскадное раскрытие** (задачи T-26…T-30). Пользователь последовательно раскрывает уровни: сводка по всем ИС → детализация по конкретной ИС → характеристики → подхарактеристики. Каждый уровень — `CollapsibleCard` с premium-оформлением и акцентной полосой.

2. **Метрики качества по ИС** с окраской уровней по RAG-палитре.

3. **Панель разработки мер** (`MeasureDevelopmentPanel`) — формирование предложения по корректирующей мере с обоснованием.

4. **Панель профессиональных суждений** (`ProfessionalJudgmentsPanel`).

5. **Карточка технического долга** (`TechDebtCard`).

**Ключевое решение для роли.** Менеджер качества предлагает меры, но не утверждает их (инвариант SoD). Кнопка «Утвердить» на этом дашборде отсутствует принципиально, а не скрыта по условию — решение принимается на исполнительном дашборде другим пользователем.

### 4.3. QualityDynamicsPage — динамика качества

**Роли:** `QUALITY_MANAGER`, `ADMIN` + legacy.

**Назначение.** Анализ изменения качества во времени (ТЗ v14, доработки v15 — задачи T-21, T-22).

**Состав:**

1. **Интегральный показатель качества по кварталам.** Все информационные системы отображаются на одной диаграмме ECharts, что позволяет сравнивать их динамику между собой.

2. **Детектор аномалий.** Порог — **12 процентных пунктов** между соседними периодами. При превышении точка на графике выделяется, создаётся уведомление, пользователю предлагается указать причину отклонения.

3. **Метки эффективности мер** (задача T-15, R2). На временной шкале отмечаются моменты внедрения утверждённых мер, что позволяет визуально сопоставить меру и последующее изменение показателя — то есть оценить, сработала ли мера.

4. **`DynamicsModal`** — детализация по конкретной характеристике: её тренд отдельно от интегрального показателя.

5. **`Sparkline`** — компактные встроенные графики трендов в таблицах.

**Источник данных:** `getSystemDynamics` (`/reports/system-dynamics?system_id=...`), состояние — `dynamicsSlice`.

### 4.4. IncidentsAnalyticsPage — аналитика технических сбоев

**Роли:** `QUALITY_MANAGER`, `ADMIN` + legacy.

**Назначение.** Анализ технических отказов ИС (ТЗ v16, блок A, задачи T-36…T-43).

**Состав:**

1. **KPI-карточки:** общее число сбоев, среднее время устранения, MTBF (средняя наработка на отказ), процент доступности.

2. **Фильтры:** по информационной системе, периоду, критичности, категории (`getIncidentCategories`).

3. **Графики:** распределение сбоев по категориям, тренд числа сбоев по времени, распределение времени устранения.

4. **Реестр инцидентов** с возможностью отметить инцидент как устранённый (`resolveIncident`).

5. **Загрузка данных** из Excel (`importIncidents`) и ручное создание (`createIncident`).

**Источник данных:** `getIncidentAnalytics` (`/incidents/analytics`), `getIncidents` (`/incidents`).

**Связь с качеством.** Данные о сбоях используются для расчёта метрик надёжности и доступности в модели качества — это не изолированный модуль, а источник объективных показателей.

### 4.5. RiskRadarPage — радар рисков

**Роли:** `QUALITY_MANAGER`, `ADMIN` + legacy.

**Назначение.** Проактивное выявление угроз качеству (задача T-16).

**Состав:**

1. **Визуализация базы рисков** в виде матрицы «вероятность × влияние».

2. **Сработавшие триггеры** (`getTriggeredRisks`) — риски, условия которых выполнились по текущим значениям метрик. Фильтрация по системе и характеристикам.

3. **Накопительный реестр** знаний о рисках, пополняемый по мере эксплуатации.

4. **Источник заземления для LLM** — записи базы рисков передаются модели как контекст, что позволяет давать рекомендации, опирающиеся на накопленный организационный опыт, а не на общие соображения.

### 4.6. TaskPlanDashboard — план задач

**Роли:** `QUALITY_MANAGER`, `ADMIN` + legacy.

**Назначение.** Отслеживание жизненного цикла мер (задачи T-23, T-24).

**Состав:**

2. **Жизненный цикл меры:** предложена → утверждена → в работе → выполнена (или отклонена).

4. **Фильтры** по ИС, статусу, ответственному.

**Состояние:** `governanceSlice`. Все операции governance реализованы как асинхронные thunk-функции, вызов через `useAppDispatch`.

## 6. Дизайн-система Premium

### 6.1. Принципы

Визуальный язык системы ориентирован на ощущение **private banking**: сдержанность, воздух, отсутствие визуального шума, золото как единственный акцент. Интерфейс должен читаться как документ для руководителя, а не как техническая панель мониторинга.

### 6.2. Токены (`frontend/src/theme/premium.ts`)

**Золотой акцент:**

```ts
export const GOLD = {
  base: '#B99A55',
  soft: '#E9DCBE',
  line: 'rgba(185,154,85,0.35)',
  glow: 'rgba(185,154,85,0.18)',
};
```

**Радиусы и тени:**

| Токен | Значение | Применение |
|-------|----------|-----------|
| `radius` | 16 | Карточки, модальные окна |
| `radiusSm` | 12 | Вложенные элементы, кнопки |
| `shadow.card` | `0 1px 2px rgba(16,24,40,0.04), 0 10px 28px -14px rgba(16,24,40,0.14)` | Базовая тень карточки |
| `shadow.cardHover` | усиленная | Состояние наведения |
| `shadow.raised` | `0 24px 60px -28px rgba(16,24,40,0.30)` | Модальные окна, всплывающие панели |
| `shadow.inset` | `inset 0 1px 0 rgba(255,255,255,0.6)` | Внутренняя подсветка верхней грани |

**Градиенты:**

| Токен | Применение |
|-------|-----------|
| `gradient.sider` | Тёмный сайдбар: `#16222F → #1E2E3F → #22384C` |
| `gradient.canvas` | Фон рабочей области |
| `gradient.header` | Шапка приложения |
| `gradient.ink` | Тёмные акцентные поверхности |
| `gradient.goldLine` | Золотая разделительная линия с затуханием |

**Поверхности и границы:** `border: #EAEBEE`, `borderStrong: #DFE1E6`, `surfaceSoft: #FAFBFC`, `surfaceTint` — вертикальный градиент от белого.

### 6.3. Система акцентов

```ts
export type AccentKey = 'ink' | 'gold' | 'sage' | 'terracotta' | 'slate' | 'none';
```

| Акцент | Цвет | Семантика |
|--------|------|-----------|
| `ink` | тёмно-синий | Нейтральные информационные блоки |
| `gold` | `#B99A55` | Ключевые управленческие блоки, LLM-аналитика |
| `sage` | `#6F9F86` | Положительная динамика, выполненные меры |
| `terracotta` | `#C06B5A` | Проблемы, просроченные меры, аномалии |
| `slate` | `#6E89A6` | Второстепенные данные |
| `none` | — | Без акцентной полосы |

### 6.4. Хелперы

**`premiumCard(accent, extra)`** — возвращает объект стилей для карточки: радиус, граница, тень, фон, оформление заголовка (высота 52 px, вес 600, для золотого акцента — градиентная подложка) и тела (отступ 18 px).

**`accentDot(color)`** — вертикальная акцентная полоса 4×16 px с градиентом и скруглением, размещается слева от заголовка карточки.

**`accentColorOf(accent)`** — разрешение ключа акцента в конкретный цвет.

**`pageContainer`** — единые отступы и максимальная ширина страницы.

### 6.5. Правила применения

1. Все карточки дашбордов используют `premiumCard` — прямое задание `borderRadius`, `boxShadow`, `border` в компонентах запрещено.
2. Графики ECharts используют палитру из токенов, а не значения по умолчанию.
3. Сайдбар всегда тёмный с золотой подсветкой активного пункта.
4. Заголовок карточки сопровождается `accentDot` соответствующего семантике цвета.

### 6.6. Анти-паттерны

- ❌ Произвольные HEX-цвета в компонентах вместо токенов.
- ❌ Множественные конкурирующие акценты на одном экране — золото должно оставаться редким.
- ❌ Тени, не входящие в набор `PREMIUM.shadow`.
- ❌ Стандартный `Collapse` из Ant Design вместо `CollapsibleCard` в дашбордах.
- ❌ Смешение цветов RAG-палитры (уровни качества) с палитрой акцентов (семантика блоков).

### 6.7. RAG-палитра (`theme/ragPalette.ts`)

Отдельная палитра для окраски **уровней качества** — она намеренно отделена от акцентов оформления, поскольку кодирует данные, а не иерархию интерфейса. Уровни соответствуют пороговым значениям расчётного показателя X.

### 6.8. Доступность: контроль контраста (WCAG 2.1 AA)

Премиальная палитра со сдержанными приглушёнными тонами создаёт риск недостаточного контраста. Чтобы эстетика не вытесняла читаемость, контраст проверяется автоматически.

**Скрипт:** `frontend/scripts/check-contrast.mjs`

```bash
npm run check:contrast
```

**Что проверяется:** все пары «текст на фоне», встречающиеся в интерфейсе, — теги критичности, категории первопричин сбоев, уровни критичности рисков, стандартные плашки Ant Design, полосы диаграммы Ганта в плане задач (включая обе границы градиента), элементы тёмного сайдбара с учётом прозрачности.

**Порог:** коэффициент контрастности ≥ 4,5 : 1 (уровень AA для основного текста).

**Текущее состояние:** 74 проверки, 0 нарушений.

**Стили доступности:** `frontend/src/styles/a11y-overrides.css` — переопределения, доводящие компоненты Ant Design до требуемого контраста без отказа от премиального облика.

> **Почему проверка автоматическая.** Контраст легко ухудшить незаметно: подбор оттенка «чуть мягче» на глаз выглядит удачно, но уводит пару за порог. Скрипт делает регресс доступности видимым сразу, а не после жалоб пользователей.

**Разделение токенов цвета (T-57).** В палитре RAG (`frontend/src/theme/ragPalette.ts`) намеренно разделены два токена: `color` — для **графики** (сектора диаграмм, маркеры, шкалы; порог ≥ 3 : 1, WCAG 1.4.11 «Non-text Contrast») и `strong` — для **текста и плашек** под белым текстом (порог ≥ 4,5 : 1, WCAG 1.4.3). Приглушённый тон читается «дорого» на графике, но как текст не проходил AA (золото давало 2,42 : 1) — отсюда две отдельные ступени. Хелпер `solidTagStyle()` принимает только глубокий тон, делая инвариант «белый текст — только на насыщенном фоне» видимым в месте вызова.

**Типографическая шкала (T-58).** Единый источник размеров текста — объект `TYPE` в `frontend/src/theme/premium.ts`: фиксированные ступени (заголовок страницы и карточки, основной и плотный текст, подписи, микрометки, числовые показатели) с явно заданным межстрочным интервалом. Шкала устранила накопившийся разнобой (14 разошедшихся размеров, включая доли пункта, и три разных интерлиньяжа на одной ступени). Правило: новый текст берёт ступень отсюда, а не задаёт размер по месту.

```
Компонент

apiSlice → HTTP-запрос с JWT в заголовке
   ↓
Backend (проверка роли) → PostgreSQL / Redis / LLM
```

| `constants/qualityModel.ts` | Дерево модели качества ISO 25010: характеристики и подхарактеристики, их коды и иерархия |
| `constants/characteristicGuidance.ts` | Пояснительные тексты по каждой характеристике: что она означает, как интерпретировать значение |
| `constants/subDescriptions.ts` | Описания подхарактеристик |
| `constants/roles.ts` | `ROLE_LABELS` — человекочитаемые подписи ролей, включая legacy-коды; функция `roleLabel()` |
| `constants/uploadSpecs.ts` | Спецификации форматов загружаемых файлов: ожидаемые заголовки, типы, правила валидации |

**Принцип единого источника.** `roles.ts` содержит только подписи; внутренние коды ролей не переименовываются никогда — это обеспечивает стабильность выданных токенов и записей в БД.

## 9. Демо-данные

### 9.1. Состав

| Файл | Содержание |
|------|-----------|
| `data/mockDashboards.ts` | Данные исполнительного и менеджерского дашбордов |

| `data/mockScaleData.ts` | Данные шкал и уровней качества |

### 9.2. Сценарий демо-данных (v2, ТЗ v14)

- **4 информационные системы** × **6 кварталов** × **55 метрик**;
- сценарии подобраны так, чтобы демонстрировать разные типы поведения: улучшение, деградация, стабильность, волатильность;
- `period_sort_key` обеспечивает корректное определение «последнего периода» при любой сортировке;
- ролевая видимость: набор данных различается в зависимости от роли вошедшего пользователя;
- состояние демо-режима сохраняется в `localStorage` под ключами версии v2.

### 9.3. Согласованность

Демо-данные фронтенда согласованы с сидами БД (`backend/scripts/seed_*.py`): одни и те же ИС, периоды и порядки величин. Это позволяет переключаться между `DEMO_MODE=true` (моки) и работой с реальным бэкендом без визуальных расхождений (дефекты DEF-12…DEF-15 закрыты в ТЗ v14).
