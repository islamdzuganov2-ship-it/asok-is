## 1. Краткое резюме

- **Проблема:** функционал ТЗ v17 (рантайм-темы, роль «Исполнитель», карточка эффективности,
  сбои только из ITSM/Excel, авто-refetch кэша) был реализован и закоммичен на ветке
  `worktree-tz-v17-roles-themes-ui` (коммит `0b598b6 "v17"`), но **в `main` не попал**. `main`
  независимо ушёл на `v18` → `17,5` (`0aa7cc3`), где v17-фич нет.
- **Причина «не весь функционал доехал»:** рассинхронизация веток (integration lag), а не потеря
  кода при конфликтах. Предыдущее слияние v17 было выполнено **качественно** (см. §3).
- **Что сделано:** создана ветка `tz-v17-into-main` от актуального `origin/main` (`0aa7cc3`),
  в неё влит `worktree-tz-v17-roles-themes-ui`, **все 6 конфликтов разрешены с сохранением обеих
  сторон**, дерево проверено (tsc/tests/build/contrast). Ветка запушена — готов PR в `main`.

## 4. Корректирующая интеграция `tz-v17-into-main` (6 конфликтов)

Слияние `origin/main (17,5)` ← `worktree-tz-v17-roles-themes-ui`. Автоматически слились без
конфликтов: `main.tsx`, `AdminFlagsPage.tsx`, `ExecutiveDashboard.tsx`, `QualityDynamicsPage.tsx`,
`TaskPlanDashboard.tsx`, `ragPalette.ts`, `premium.ts` и др. Конфликтовали 6 файлов — разрешены
с сохранением **обеих** сторон:

| Файл | main (17,5) | v17 | Резолюция |
|---|---|---|---|
| `backend/.../iam/models.py` | роли `RISK_MANAGER`, `AUDITOR` (BL-007) | роль `ASSIGNEE` (req 6) | **все три** роли + общий `ALL_ROLES` |
| `backend/.../seed_demo.py` | сид всех ролей + `assert` полноты | сид `assignee` (ФИО «Петрова А.С.») | сид **всех** ролей включая assignee; `assert` проходит |
| `frontend/.../App.tsx` | маршрут `risk-economics`, PageLoader UI-10 | ThemeVarsBridge, `antdThemeOf`, `settings`, `my-tasks`, ролевые маршруты | **оба** набора маршрутов и импортов |
| `frontend/.../AppLayout.tsx` | пункт «Риск-экономика» | «Настройка» + меню исполнителя | **оба** пункта |
| `frontend/.../IncidentsAnalyticsPage.tsx` | `numericColumn` (tabular-nums), `KpiCard`* | убран ручной ввод, загрузка Excel/ITSM, donut на `chart.ink` | `numericColumn` + удаление ввода + Excel/ITSM |
| `frontend/.../ManagerDashboard.tsx` | `numericColumn` | `useChartTokens` для графиков | `numericColumn` + chart-токены |

`*` — вариант `KpiCard` в IncidentsAnalyticsPage присутствует в **незакоммиченном** рабочем дереве
`main` (правит параллельная сессия), в `origin/main (0aa7cc3)` его ещё нет; см. §6.

**Дополнительно исправлен дефект интеграции:** тест `designSystem.test.ts` (добавлен в v18) считал
контраст напрямую по `BRAND.ink`/`BRAND.inkSoft`. В v17 эти токены стали CSS-переменными
(`var(--ink)`), и тест падал (2 кейса). Тест переведён на реестр тем и теперь проверяет читаемость
текста **во всех трёх темах** на их поверхностях/полотне (AA ≥ 4.5) — стал строже и защищает
темизацию.

## 6. Открытые риски / следующие шаги

1. **Параллельная сессия правит `main`** (незакоммиченное рабочее дерево: `KpiCard` в
   IncidentsAnalyticsPage, правки `ragPalette`, `LoginPage`, `table.ts`). Интеграция сделана против
   **закоммиченного** `origin/main (0aa7cc3)`. Когда та работа будет закоммичена, при мёрдже PR
   возможен повторный конфликт в `IncidentsAnalyticsPage.tsx` (их `KpiCard` ↔ наше удаление ввода)
   — свести при слиянии, сохранив req 1 (ручной регистрации сбоя нет).
2. **Тёмная тема `graphite`, известное ограничение:** ячейки теплокарты (`LEVEL_COLORS`, светлые
   пастели) с тёмным текстом остаются светлыми и в graphite — на них текст задаётся токеном ink.
   Для safety graphite стоит закрепить фиксированный тёмный ink на статус-подложках (отдельная
   мелкая правка, не блокирует PR; светлые темы не затронуты).
3. **`agents/main-pr` устарел** — его заменяет `tz-v17-into-main`. После мёрджа PR ветку
   `agents/main-pr` можно закрыть/удалить.
4. **Экспериментальные ветки** (`copilot/...`, `agents/template-...`, `Cl_1`) в этот PR не входят
   — их назначение вне ТЗ v17; мёрджить их в `main` без ревью содержимого не следует.

## 7. Политика: PR по завершении задачи

Введена базовая политика (см. `CLAUDE.md`, раздел «Политика веток и PR»): работа ведётся в
отдельной ветке/worktree; по завершении задачи изменения доводятся до `main` **через Pull Request**
с разрешёнными конфликтами и зелёными проверками (tsc/tests/build/contrast). Прямые пуши в `main`
не выполняются.
