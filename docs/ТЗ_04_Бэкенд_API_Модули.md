### 1.3. Архитектурный контракт модуля

Каждый доменный модуль имеет единообразную структуру:

| Файл | Назначение |
|------|-----------|
| `models.py` | Модели SQLAlchemy — доменные сущности |
| `schemas.py` | Схемы Pydantic — контракты API (запрос/ответ) |
| `router.py` | HTTP-эндпоинты FastAPI |
| `service.py` | Бизнес-логика (там, где она нетривиальна: governance, risk, incidents) |
| `deps.py` | Зависимости FastAPI (только в `iam` — аутентификация) |

**Правила зависимостей между модулями:**

1. Модуль не импортирует внутренности другого модуля напрямую — только через публичный интерфейс (`__init__.py`) или порты из `shared/ports.py`.
2. `shared/` не зависит ни от одного доменного модуля (иначе возникает цикл).
3. `iam` — базовый модуль, от него зависят все остальные (проверка прав), обратной зависимости нет.
4. Соблюдение границ проверяется архитектурным тестом (`test_architecture.py`), который анализирует импорты и падает при нарушении.

Обоснование выбора модульного монолита вместо микросервисов — в [ТЗ-01](./ТЗ_01_Архитектура_и_Стек.md), ADR-001.

## 2. Модуль IAM — идентификация и доступ

**Каталог:** `app/modules/iam/`
**Файлы:** `models.py`, `schemas.py`, `router.py`, `security.py`, `deps.py`

### 2.1. Модель данных

**`User`** — учётная запись:

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | UUID | Первичный ключ |
| `username` | str, unique | Логин |
| `password_hash` | str | Хеш bcrypt |
| `role` | str | Код роли |
| `full_name` | str | ФИО |
| `email` | str | Электронная почта |
| `is_active` | bool | Признак активности |

### 2.2. Роли

Определены в `models.py`:

```python
ROLE_ANALYST = "TEST_ANALYST"
ROLE_MANAGER = "QUALITY_MANAGER"
ROLE_ADMIN   = "ADMIN"
ALL_ROLES = ("TEST_ANALYST", "QUALITY_MANAGER", "CTO", "CEO", "ADMIN")
```

Коды `CTO` и `CEO` — legacy, приравнены к уровню `ADMIN`. Подробно — в [ТЗ-02](./ТЗ_02_Ролевая_Модель_и_Безопасность.md).

### 2.3. Безопасность (`security.py`)

- хеширование паролей — **bcrypt**;
- выпуск и верификация **JWT**: access-токен и refresh-токен;
- защита от token type confusion: тип токена проверяется явно, refresh-токен не принимается там, где ожидается access (устранено, S3);
- секреты не имеют небезопасных значений по умолчанию — при отсутствии в продакшене приложение падает на старте (fail-fast, S2).

### 2.4. Зависимости (`deps.py`)

Функции-зависимости FastAPI, извлекающие текущего пользователя из токена и проверяющие роль. Списки допустимых ролей задаются на уровне эндпоинта, например `{"roles": ["ADMIN"]}`.

### 2.5. Эндпоинты

| Метод | Путь | Роль | Описание |
|-------|------|------|----------|
| POST | `/api/v1/auth/login` | — | Аутентификация, выдача пары токенов |
| POST | `/api/v1/auth/refresh` | — | Обновление access-токена по refresh-токену |

**Демо-учётные записи** заданы словарём `DEMO_USERS` в `router.py` и доступны **только при `DEMO_MODE=true`** (устранение S1):

| Логин | Роль |
|-------|------|
| `admin` | `ADMIN` |
| `manager` | `QUALITY_MANAGER` |
| `analyst` | `TEST_ANALYST` |

Пароли заданы в том же словаре; в продуктивной среде `DEMO_MODE=false` полностью отключает этот путь аутентификации.

## 4. Модуль Quality — модель качества

**Каталог:** `app/modules/quality/`
**Файлы:** `models.py`, `schemas.py`, `router.py`, `quality_model.py`, `calculation.py`, `ai_quality_model.py`, `ai_calculation.py`

### 4.1. Назначение

Модуль реализует две модели качества:

1. **ISO/IEC 25010:2023** — базовая модель качества программного продукта: 8 характеристик верхнего уровня и **31 подхарактеристика**. Плоский список всех пар «характеристика — подхарактеристика — формула» задан в `quality_model.py`; расчёт — в `calculation.py`.

2. **ГОСТ Р 59898-2021** — модель качества систем искусственного интеллекта: четырёхуровневая иерархия, 37 подхарактеристик, из них 7 специфичных для ИИ (`ai_quality_model.py`, `ai_calculation.py`). Внедрено инициативой BL-001, этапы E1 и E2.

### 4.2. Модель данных

**`Characteristic`** — характеристика качества: код, наименование, описание, принадлежность к модели (25010 / 59898).

**`SubCharacteristic`** — подхарактеристика: код, наименование, родительская характеристика, уровень иерархии.

**`Metric`** — определение метрики: код, наименование, формула расчёта, привязка к подхарактеристике, поле **`metric_kind`** — машиночитаемый тип формулы (внедрено BL-003).

**`metric_kind`** позволяет расчётному движку выбрать нужную формулу без разбора текстового описания: отношение, доля, среднее, инвертированное отношение и т. д. Таблица соответствия формул стандарта и значений `metric_kind` приведена в приложении к ТЗ модуля качества СИИ.

### 4.3. Расчётный движок (`calculation.py`)

**Базовая формула:**

```
X = val_a / val_b × 100 %
```

**Присвоение уровня качества** по пороговым значениям:

| Уровень | Диапазон X |
|---------|-----------|
| Критический | < 25 % |
| Низкий | 25 – 50 % |
| Средний | 50 – 75 % |
| Высокий | 75 – 100 % |

**Неизмеримые метрики.** Метрика может быть помечена флагом «неизмеримо» (миграция 004). Такие метрики исключаются из расчёта интегрального показателя, а не считаются нулём — иначе отсутствие данных штрафовало бы систему как плохое качество. Правила обработки закреплены в блоке D ТЗ v16 (задача T-55).

**Веса** (`ai_weights`, миграция 007) позволяют задать вклад подхарактеристик в интегральный показатель для модели ГОСТ 59898.

### 4.4. Эндпоинты

| Метод | Путь | Роль | Описание |
|-------|------|------|----------|
| GET | `/api/v1/metrics` | все | Справочник метрик |
| PUT | `/api/v1/metrics/{metric_id}` | `ADMIN` | Изменение определения метрики |
| DELETE | `/api/v1/metrics/{metric_id}` | `ADMIN` | Удаление метрики |
| POST | `/api/v1/metrics` | `ADMIN` | Создание метрики |

## 5. Модуль Assessment — оценка

**Каталог:** `app/modules/assessment/`
**Файлы:** `models.py`, `schemas.py`, `router.py`, `ai_router.py`, `ai_schemas.py`

### 5.1. Модель данных

**`AssessmentPeriod`** — период оценки:

| Поле | Тип | Описание |
|------|-----|----------|
| `id` | UUID | Первичный ключ |
| `system_id` | UUID | Ссылка на ИС |
| `label` | str | Метка периода («Q3 2025») |
| `year`, `quarter` | int | Год и квартал |
| `period_sort_key` | int | Ключ сортировки для определения «последнего периода» |
| `status` | str | Черновик / финализирован |

**`MetricValue`** — значение метрики за период: `metric_id`, `period_id`, `val_a`, `val_b`, рассчитанное `X`, уровень качества, флаг неизмеримости.

**`ProfessionalJudgment`** — профессиональное суждение (миграция 005): характеристика, оценка эксперта, обоснование, автор, дата.

### 5.2. Рабочий процесс оценки

```
Создание периода
      ↓
Внесение значений метрик (ручной ввод / импорт Excel)
      ↓
Расчёт (POST /{period_id}/calculate) → X и уровни по всем метрикам
      ↓
Профессиональные суждения по характеристикам
      ↓
Формирование заключения (с участием LLM)
      ↓
Финализация (POST /{period_id}/finalize)
      ↓
[при необходимости] Переоткрытие (POST /{period_id}/reopen)
```

**Финализация** фиксирует результаты: значения становятся неизменяемыми, оценка попадает в динамику и отчётность. Переоткрытие доступно ограниченному кругу ролей и логируется.

### 5.3. Эндпоинты (`/api/v1/assessments`)

| Метод | Путь | Описание |
|-------|------|----------|
| GET | `/dashboard` | Сводные данные для дашборда оценок |
| GET | `/periods` | Список периодов оценки |
| POST | `/periods` | Создание периода |
| GET | `/periods/summary` | Сводки по периодам (полнота заполнения) |
| GET | `/{period_id}/metrics` | Редактируемые метрики периода |
| PUT | `/{period_id}/metrics` | Пакетное сохранение значений метрик |
| GET | `/{period_id}/calculated` | Рассчитанные показатели периода |
| POST | `/{period_id}/values` | Добавление значения (с бэкофиллом пропусков) |
| POST | `/{period_id}/finalize` | Финализация оценки (закрытие на правку) |
| POST | `/{period_id}/reopen` | Переоткрытие завершённой оценки (T-47) |
| GET | `/{period_id}/judgments` | Суждения по периоду + полнота |
| PUT | `/{period_id}/judgments` | Сохранение пакета суждений |
| GET | `/{period_id}/judgment-conclusion` | Итоговое LLM-заключение по периоду |
| GET | `/judgments-pending` | Пары без внесённого суждения (T-48) |
| GET | `/judgments-filled` | Заполненные суждения |
| GET | `/judgments-status` | Статус заполнения суждений (сводно) |

> `POST /conclusion-feedback` (обратная связь по LLM-заключению) относится к модулю **reporting** (`/api/v1/reports`), а не к оценкам — см. соответствующий раздел.

### 5.3a. Корректировка завершённых оценок (задача T-47)

Завершённая оценка закрыта на правку. Функция `_ensure_editable(period)` проверяет статус периода и отклоняет изменение значений, пока период не переоткрыт.

```
COMPLETE ──[POST /{period_id}/reopen]──► CALCULATED ──[правка значений]──► [POST /{period_id}/finalize] ──► COMPLETE
```

`POST /{period_id}/reopen` возвращает ошибку, если период не был завершён — переоткрывать нечего.

> **Обоснование.** Без явного шага переоткрытия значения за закрытый период менялись бы молча, и показатели дашбордов «уезжали» бы задним числом без следа. Разблокировка делает правку намеренным действием.

### 5.3b. Выдача незаполненных суждений (задача T-48)

`GET /judgments-pending` возвращает пары «характеристика × подхарактеристика», у которых **есть оценка** (рассчитан X либо проставлено «невозможно измерить»), но **нет записи** в `professional_judgments` (пары с уже внесённым суждением вычитаются по этой таблице). По умолчанию выдаётся только **последний период** по каждой ИС (архивные кварталы суждениями не дозаполняют, DEF-14); флаг `all_periods=true` включает архив, параметр `system` фильтрует по системе. Сортировка — «худший балл первым», неизмеримые (`score_pct = -1`) идут вверху.

**Схема ответа** — `PendingJudgmentOut`:

| Поле | Описание |
|------|----------|
| `period_id`, `system_id`, `system_name`, `period` | Привязка строки |
| `characteristic`, `subcharacteristic` | Пара модели качества |
| `score_pct` | Балл подхарактеристики в процентах; **`-1` — «невозможно измерить»** |
| `quality_level` | Уровень качества |
| `expert_comment` | Комментарий эксперта |

**Параметры:** `system` — фильтр по системе; `all_periods` — включить архивные периоды (по умолчанию берётся последний).

**Сортировка:** худший балл первым, значения «невозможно измерить» (`-1`) в начале — работа начинается с проблемных зон.

## 6. Модуль Governance — управление мерами

**Каталог:** `app/modules/governance/`
**Файлы:** `models.py`, `schemas.py`, `router.py`, `service.py`

### 6.1. Назначение

Модуль реализует полный цикл управления корректирующими мерами с разделением полномочий (Segregation of Duties). Внедрён задачей T-10 с переносом состояния из фронтенда в БД (миграция 008).

### 6.2. Модель данных

**`Proposal`** — предложение по мере:

| Поле | Описание |
|------|----------|
| `id` | Первичный ключ |
| `system_id`, `period_id` | Привязка к ИС и периоду |
| `characteristic` | Характеристика, к которой относится мера |
| `title`, `description` | Наименование и описание меры |
| `justification` | Обоснование необходимости |
| `proposed_by` | Автор предложения |
| `status` | Статус в жизненном цикле |
| `deadline` | Плановый срок исполнения |
| `task_meta` | Метаданные задачи (исполнитель, приоритет) |

**Решение** фиксирует: кто принял, какое (утвердить / отклонить / вернуть), обоснование, дату.

### 6.3. Жизненный цикл меры

```
предложена ──► утверждена ──► в работе ──► выполнена
     │              │
     ├──► отклонена │
     │              ↓
     └──► возвращена на доработку
                    │
              [просрочка]
                    ↓
              эскалация ──► решение по эскалации
```

### 6.4. Инвариант SoD

**Ключевое правило:** автор предложения не может принять по нему решение (`proposed_by ≠ decided_by`). Проверка выполняется в `service.py` на уровне бизнес-логики, а не только в интерфейсе. Попытка нарушения возвращает ошибку — это защита от ситуации, когда менеджер качества сам себе утверждает меру.

### 6.5. Эскалация

Просроченные меры эскалируются на уровень выше. Эскалация — отдельный поток со своими эндпоинтами: инициирование, решение по эскалации, разрешение эскалации.

### 6.6. Эндпоинты (`/api/v1/governance`)

| GET | `/proposals` | Список предложений с фильтрами |

## 8. Модуль Reporting — отчёты и дашборды

Алгоритм: если модуль интегрального показателя качества между соседними периодами изменился на **12 процентных пунктов и более**, отклонение считается аномальным. Создаётся уведомление, пользователю предлагается зафиксировать причину.

## 9. Модуль DataIO — импорт и экспорт

**Каталог:** `app/modules/dataio/`
**Файлы:** `importer.py`, `router.py`, `tasks.py`

### 9.1. Синхронный импорт

Небольшие файлы обрабатываются в рамках HTTP-запроса. Формат строгий: заголовки `metric_id | val_a | val_b`.

### 9.2. Асинхронный импорт

Крупные файлы обрабатываются задачей Celery `parse_excel_task` через брокер Redis. Клиент получает `task_id` и опрашивает статус через `GET /tasks/{task_id}`.

### 9.3. Безопасность загрузки

- проверка **сигнатуры файла** (magic bytes), а не только расширения — защита от загрузки исполняемого файла под видом `.xlsx` (устранение S5);
- обязательная аутентификация на всех эндпоинтах загрузки (устранение S4);
- валидация структуры до записи в БД: ошибочные строки собираются в отчёт об импорте и не применяются частично.

### 9.4. Эндпоинты (`/api/v1/excel`)

| Метод | Путь | Описание |
|-------|------|----------|
| POST | `/import-assessment` | Импорт значений метрик оценки |
| POST | `/import-workbook` | Импорт книги Excel целиком |
| POST | `/import/{period_id}` | Импорт в конкретный период |
| POST | `/upload` | Загрузка файла |
| GET | `/tasks/{task_id}` | Статус асинхронной задачи импорта |

Спецификации форматов файлов приведены в приложении F ТЗ v16 и продублированы во фронтенде в `constants/uploadSpecs.ts`.

## 10. Модуль LLM — языковая модель

**Каталог:** `app/modules/llm/`
**Файлы:** `service.py`, `brain.py`, `gate.py`, `knowledge.py`, `prompts.py`, `reasoning.py`, `dataset.py`, `tasks.py`

Подробное описание — в [ТЗ-05](./ТЗ_05_LLM_Интеграция_и_Обучение.md). Здесь приведена структура модуля.

### 10.1. `service.py` — сервис инференса

Загрузка GGUF-модели через `llama-cpp-python`, автообнаружение файлов в каталоге `models/llm/`, отслеживание профиля загруженной модели, генерация ответов с заданными параметрами.

### 10.2. `gate.py` — шлюз правил

Детерминированный движок: вердикт об уровне качества вычисляется **правилами, а не моделью**. LLM получает готовый вердикт и данные, её задача — объяснить вывод человеческим языком. Модель не может переопределить расчёт.

### 10.3. `brain.py` — «резервный мозг»

Внешнее хранилище знаний в `models/llm_brain/`: `brain_meta.json`, `corpus.jsonl`, `feedback.jsonl`, `memory.jsonl`. Ключевое свойство — переносимость между моделями: замена GGUF-файла не приводит к потере накопленных знаний.

### 10.4. `reasoning.py` — многоаспектный анализ

Реализация BL-005: девятишаговая методология формирования выводов о качестве. Два потока — профессиональные суждения и карточки мер.

### 10.5. `prompts.py`, `knowledge.py`, `dataset.py`

Шаблоны промптов, работа с базой знаний для заземления, выгрузка обучающего датасета.

### 13.2. Обработка ошибок

Доменные исключения из `shared/exceptions.py` отображаются в HTTP-коды единообразно:

| Ситуация | Код | Тело ответа |
|----------|-----|-------------|
| Не аутентифицирован | 401 | `{"detail": "..."}` |
| Роль не разрешена | 403 | `{"detail": "..."}` |
| Объект не найден | 404 | `{"detail": "..."}` |
| Нарушение бизнес-правила (в т. ч. SoD) | 409 / 422 | `{"detail": "..."}` |
| Ошибка валидации входных данных | 422 | Стандартный формат FastAPI |

### 13.3. Документация OpenAPI

FastAPI автоматически публикует спецификацию: `/docs` (Swagger UI) и `/openapi.json`. Схемы Pydantic из `schemas.py` каждого модуля служат единственным источником истины для контрактов — фронтенд типизируется по ним.
